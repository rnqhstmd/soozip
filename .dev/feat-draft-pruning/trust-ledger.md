# Trust Ledger — 고아 초안 정리 배선

- 작성일: 2026-08-11
- 모드: 핵심(core) — H1~H4 긴급 감사 (CRITICAL/HIGH만)

## 핵심 모드 긴급 감사

이 변경은 **사용자 파일을 삭제한다.** 감사의 초점은 "무엇이 잘못되면 작업물이 사라지는가"다.

### [CRITICAL] CloudKit 부분 임포트에 의한 전량 삭제 — **미방어. CloudKit 활성화 전 반드시 닫을 것**

아래 "빈 소속 목록" 방어는 조회가 **던질 때만** 작동한다. CloudKit 미러링에서는
`fetch`가 **에러 없이 부분 결과를 돌려준다**:

```
iCloud 계정 변경 → NSPersistentCloudKitContainer가 purge 후 재임포트
→ collections()가 성공적으로 "아직 안 들어온" 목록을 반환
→ 로컬 전용이라 살아남은 초안들이 소속 상실로 판정 → 삭제
```

결과는 CRITICAL과 동일한 전량 삭제인데 **AC-4가 이 경로를 전혀 막지 못한다.**
지금은 CloudKit 미활성이라 발화하지 않지만, 배선은 켜질 때 그대로 살아 있다.

**차단 조건 — CloudKit 엔타이틀먼트를 켜기 전에 아래 중 하나를 반드시 구현한다:**
1. `NSPersistentCloudKitContainer.eventChangedNotification`으로 최초 import 완료를
   확인한 뒤에만 `lostCollection` 판정을 적용한다
2. 또는 런치 시에는 **`maxAge` 경과 기준만** 적용하고, 소속 상실 판정은 임포트가
   안정된 시점(예: 사용자가 모음집 화면에 진입한 뒤)으로 미룬다

S2 스파이크가 막혀 있어 실측 검증이 불가능한 영역이라 지금 기계를 만들지 않았다.
**이 항목이 열린 채로 CloudKit을 켜면 사용자 작업물이 사라진다.**

### [CRITICAL] 빈 소속 목록에 의한 전량 삭제 (조회가 던지는 경우) — 방어됨

`pruneOrphans`는 `knownCollectionIDs`에 없는 소속의 초안을 지운다. 조회 실패를 빈
집합으로 접으면 **전 초안이 고아로 판정되어 통째로 삭제된다.**

- 방어: `pruneOrphanedDrafts`가 조회 실패를 던진다. 삼키지 않는다 (AC-4)
- 검증: `모음집_조회가_실패하면_아무것도_지우지_않는다` — 던지는 것과 초안 2개가
  모두 살아남는 것을 함께 확인
- 구분: 모음집이 **정말 0개**면 지우는 것이 맞다 (AC-5). 초안은 소속 없이 존재할
  수 없으므로 소속이 실재하지 않으면 고아다. 두 경우가 입력은 같아 보이지만
  결과가 정반대여야 하는 것이 이 작업의 핵심

### [HIGH] 삭제 경로 이탈 — 해당 없음

`pruneOrphans`는 `contentsOfDirectory(root)`로 얻은 항목만 `root` 아래에서 제거한다.
경로 구성 요소가 사용자 입력이 아니라 파일시스템 열거 결과라 traversal 표면이 없다.
경로는 `DraftStore.appDefault` 한 곳에서만 만든다 — 쓰는 곳과 지우는 곳이 어긋나면
정리가 아무 일도 안 하거나 엉뚱한 폴더를 건드린다.

### [HIGH] 첫 실행 시 폴더 부재 — 방어됨

`Drafts/`가 아직 없으면 `pruneOrphans`가 `fileExists` 가드로 빈 배열을 돌려준다.
(`Packages/SoozipDraft` 기존 검증)

### [정보] 앱 경계의 에러 삼킴 — 의도적

`.task`의 `catch`가 모든 에러를 삼킨다. 여기까지 오는 에러는 대부분 모음집 조회
실패이고 그때 해야 할 일이 정확히 "아무것도 지우지 않기"라, 실패 모드가 데이터
손실이 아니라 **정리 미수행**이다. 다음 실행에서 재시도된다. 로깅 기반이 아직
없어 기록할 곳도 없다 — Phase 9에서 로깅이 생기면 재검토 대상.

### [MEDIUM] 정리 전체가 메인 스레드에서 돈다 — 미해결

`DraftMaintenance`가 `@MainActor`이고 `.task`가 그 격리를 물려받아,
`contentsOfDirectory` + 고아 폴더 재귀 `removeItem`이 런치 중 서스펜션 없이 돈다.
방치 초안 수십 개가 각각 수 MB 사진 사본을 들고 있으면 런치가 수백 ms~초 단위로
막힌다. MainActor가 정말 필요한 것은 `knownCollectionIDs()`뿐이고 `DraftStore`는
`Sendable`에 nonisolated라, ID 집합만 메인에서 얻고 정리는 벗어나서 돌 수 있다.

지금 안 고친 이유: 초안을 만드는 경로(에디터)가 Phase 3이라 **실측할 데이터가
없다.** 추측으로 비동기화하면 검증 없이 복잡도만 는다. Phase 3에서 실제 초안이
쌓이기 시작하면 런치 프로파일과 함께 처리한다.

## 위험 수용

- [앱 배선 미검증] `SoozipApp`의 `.task` 배선 자체는 자동 테스트로 덮이지 않는다.
  SwiftUI 씬 코드라 단위 테스트 대상이 아니며, 실기기·시뮬레이터 수동 확인도
  이번 범위에서 하지 않았다. 덮인 것은 `DraftMaintenance`까지다 (phase-complete)
- [CloudKit 부분 임포트 미방어] 위 CRITICAL 참조. CloudKit 활성화 전 차단 조건
  2안 중 하나를 구현해야 한다. 지금은 엔타이틀먼트가 꺼져 있어 발화하지 않는다
  (코드 리뷰 후속)
- [메인 스레드 정리] 위 MEDIUM 참조. 실측 데이터가 없어 Phase 3으로 미룸
  (코드 리뷰 후속)
- [Phase 2 범위 축소] 승격 트랜잭션 7단계는 S2 스파이크(초안 미동기화 검증)가
  전제라 착수하지 않았다. 1.5초 디바운스는 호출부(에디터)가 Phase 3이라 보류
  (phase-requirements)
