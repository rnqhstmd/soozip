- 작성일: 2026-08-11
- 모드: 핵심(core) / 표준 프로파일

## 긴급 감사 (H1~H4)

순수 값 타입이고 I/O·영속화·네트워크가 없다. 데이터 소실 경로가 없으므로 감사의
초점은 **"기능이 없는데 초록일 수 있는가"** 하나다.

### [HIGH → 해소] 변환이 `zoom`을 무시해도 14개가 전부 초록이었다

`toScreen`/`toLogical`이 `scale` 대신 `fitScale`을 쓰도록 바꿔 봤다.
**`zoom`은 아무 데도 안 쓰이는 죽은 숫자가 되고 확대가 아예 동작하지 않는데,
당시 테스트 14건이 전부 통과했다.**

원인이 셋 다 같은 뿌리다:

| 테스트 부류 | 왜 못 잡나 |
|---|---|
| 줌 1 상태 | `scale == fitScale`이라 차이가 없다 |
| 왕복·중앙 보존 | **배율에 무관한 성질**이다. 양쪽이 같이 틀리면 성립한다 |
| `절대_배율은_fit_곱하기_줌이다` | `scale`을 **속성으로만** 확인한다 — 그 값이 변환에 쓰이는지는 안 본다 |

- 방어: `줌을_키우면_같은_논리_거리가_화면에서_그만큼_멀어진다` — 화면 **거리**를
  x·y 양축으로 잰다
- 검증: 같은 변이를 다시 넣어 **이 테스트만** 빨간 것을 확인

**이 저장소에서 반복되는 패턴의 또 다른 얼굴이다.** 지금까지는 집합·개수 비교가
연결을 못 봤고, 이번에는 **불변량 테스트가 배율을 못 봤다.** 왕복 항등처럼
"양쪽이 같이 틀리면 성립하는" 단언은 그 자체로는 이빨이 약하다.

## 설계 결정과 그 근거

### 배율·뷰포트에 독립인 것만 저장한다

`zoom`은 **fit 대비 배수**, `center`는 **뷰포트 중앙에 오는 논리 지점**이다.
절대 배율이나 화면 오프셋을 저장하면 뷰포트가 바뀔 때마다 보정이 필요하고,
한 곳이라도 빠뜨리면 화면이 튄다.

결과로 `viewportChanged`가 **아무 계산도 하지 않는다** — 두 값을 그대로 넘기면
`fitScale`만 새 뷰포트로 다시 계산된다. AC-11·13·14가 전부 이 성질에서 나온다.

### fit은 식 하나다

v4 §1.2 표의 "세로는 폭에 맞춰, 가로는 높이에 맞춰"는 두 규칙이 아니라
`min(뷰포트폭/캔버스폭, 뷰포트높이/캔버스높이)`의 결과다. 방향으로 분기하면
정사각형에 가까운 뷰포트에서 어긋난다. 변이 A가 이 주장을 검증한다.

## 코드 리뷰 반영 — 생존 변이 8종

리뷰가 **내 변이 목록에 없던 축**으로 8종을 찾았고 전부 생존했다(15/15 초록).
직접 재현해 확인한 뒤 전부 막았다. 프로덕션 수학 자체는 오류가 없었다.

### [HIGH] 뷰포트 0×0에서 `NaN`이 상태를 영구 오염시킨다

SwiftUI `GeometryReader`는 **첫 레이아웃 패스에서 `.zero`를 준다** — 실제 경로다.

```
viewport .zero → scale 0 → toLogical(0,0) = (nan, nan)
centered(on: nan) → center = nan          ← 클램프가 안 거른다
viewportChanged(정상) → 여전히 nan         ← 복구 경로가 없다
```

**`NaN`은 클램프를 그냥 통과한다.** Swift `min`/`max`는 `y >= x ? y : x` 형태라
`NaN` 비교가 전부 거짓이고, 그러면 `x`가 그대로 반환된다.

- 수정: `fitScale` 유효성 가드 · `toLogical`이 `scale <= 0`이면 `center` 반환 ·
  `zoomed`/`centered`가 비유한값 무시
- **가드 하나는 처음에 검증이 안 됐다.** 0×0만으로는 `fitScale` 가드를 지워도
  `min(0, 0) = 0`이라 결과가 같다. 가드가 실제로 막는 것은 **음수·`NaN`·0 캔버스**라
  그 테스트를 따로 넣었다

### [HIGH] 클램프가 네 변 중 **x 양의 방향 하나만** 고정돼 있었다

AC-9 테스트가 `centered(on: (540+2160, 675))` 하나뿐이었는데, `y = 675`는 캔버스
중심이라 어떤 y 반경에도 안 걸린다. 그래서 **y 클램프를 통째로 지워도, y 반경을
`canvas.width`로 잘못 써도, 하한을 지워도** 전부 초록이었다.

- 수정: 네 방향 파라미터화 테스트. y 반경이 `canvas.height`(1350)라는 사실이
  코드에만 있던 것을 테스트로 끌어냈다

### [HIGH] 클램프 **기준점**이 고정돼 있지 않았다

`let c = canvasCenter`를 `let c = center`(현재 중심 기준)로 바꿔도 전부 초록이었다.

**이 저장소가 이미 겪은 함정과 똑같은 구조다** — 픽스처가 기본값과 같은 값을 써서
두 구현을 구별 못 한다(직전 단위의 `.post` 종횡비와 같다). 기본 `center`가 곧
캔버스 중심이라 **첫 호출로는 갈리지 않는다.**

팬은 드래그 프레임마다 연속 호출되므로, 기준이 따라가면 한 번의 플릭으로
무제한 이탈한다.

- 수정: 연속 2회 팬 테스트

### [MEDIUM] x/y **전치**가 통과했다 — 내가 방금 쓴 경고에 내가 걸렸다

`줌을_키우면_같은_논리_거리가_...`가 `기본거리.x + 기본거리.y`로 **합산**했는데,
전치는 합에 대해 불변이다. 나머지 변환 단언은 전부 왕복이거나 `center`와 같은
점(델타 0)이라, **0이 아닌 오프셋의 절대 화면 좌표를 확인하는 테스트가 하나도
없었다.**

이 파일의 위 항목에 *"양쪽이 같이 틀리면 성립하는 단언은 이빨이 약하다"* 고 써
놓고 같은 형태를 새로 만들었다. 합산은 그 함정의 또 다른 얼굴이다.

- 수정: 성분별 단언으로 분리 + 캔버스 모서리의 절대 화면 좌표 앵커 추가

### [MEDIUM] 3건

- **팬이 줌을 리셋해도 초록이었다.** `centered`를 부르는 테스트 중 줌 값에
  의존하는 단언이 없었다 — 순서가 `zoom → pan`인 조합이 한 번도 없었다.
  300% 확대 중 두 손가락 드래그(§5.9)에서 화면이 통째로 축소되는 결함이다
- **캔버스 치수 하드코딩이 통과했다.** 9:16 프리셋을 한 번도 안 만들었다.
  세로에서는 두 프리셋의 fit이 같아(폭 제약) **가로에서만 드러나는** 종류다
- **`workArea`가 `private`이라 `EDITOR-9`가 같은 사각형을 다시 구현해야 했다** →
  공개. 두 벌로 갈라지면 팬 한계와 레이어 한계가 조용히 어긋난다

### [MEDIUM] ac.md의 "더블탭 fit 복귀는 로직이 없다"가 틀렸다

`zoom = 1`은 배율만 되돌리고 `center`를 둔다. 작업 영역 끝까지 팬한 상태에서는
**캔버스가 정확히 화면 밖에 남는다**(실측: 좌 -390 / 우 0, 뷰포트 폭 390).
사용자는 "맞춤으로 복귀"를 눌렀는데 빈 화면을 본다.

- 수정: `fitted()`를 이 타입에 두고 ac.md 정정. 배선에 맡겼으면 배선 쪽 판단
  하나로 이 버그가 들어왔다

### 재검 결과

변이 10종(기존 9 + 리뷰 8, 중복 제외) **전부 잡힘.**

## 위험 수용

- [팬 오프셋 해석] v4 §1.2는 회전 시 "팬 오프셋 유지"라고만 적혀 있다. **보던
  논리 지점을 유지하는 쪽으로 정했다** — 줌에 "새 fit 기준으로 재계산"이라고
  명시한 것과 같은 처리다(ac.md "해석을 명시한 것")
- [핀치 중심 확대 미구현] `zoomed(to:)`는 뷰포트 중앙 기준이다. 공개 API로
  유도는 가능하지만(`center' = L - (q - V/2)/scale'`), **경계에서 클램프되면
  손가락 아래 지점이 미끄러지고 호출자가 그 사실을 알 방법이 없다.**
  `EDITOR-10`이 소비자와 함께 `zoomed(to:anchoredAtScreen:)`를 설계할 때 함께
  결정한다 — 소비자 없이 지금 API를 만들면 형태를 틀리기 쉽다 (코드 리뷰 LOW-2)
- [팬 한계가 캔버스 가시성을 보장하지 않는다] fit 배율에서 작업 영역 끝까지
  팬하면 캔버스가 화면에서 완전히 사라진다(실측: 좌 -390 / 우 0). §5.9의
  "작업 영역까지 이동 + 고무줄"의 문자적 해석 안이고 고무줄은 `EDITOR-11`
  소관이라 결함으로 세지 않았다. **배선 시 명시적으로 결정할 것** (리뷰 LOW-3)
- [고무줄 되돌림 없음] 작업 영역 밖 요청을 경계로 **자르기만** 한다. §5.9의
  고무줄 효과는 애니메이션이라 배선(`EDITOR-11`)
- [실기기 미확인] 값 타입이라 로직은 전부 덮였지만, 실제 기기 회전 시
  `viewportChanged`가 언제 어떤 크기로 불리는지는 `EDITOR-11` 배선에서 확인한다
