# Trust Ledger — CANVAS-3 사진 소유 관계

- 작성일: 2026-08-11
- 모드: 핵심(core) / 표준 프로파일

## 이 단위가 무엇이었나

로드맵의 `CANVAS-3`(사진 이관)은 **구현이 이미 끝나 있었다** — `CANVAS-1`의 승격
트랜잭션 3단계가 전부 한다. 남아 있던 것은 **검증의 구멍**이었다.

## 긴급 감사 (H1~H4)

### [HIGH] 소유 관계가 측정되지 않고 있었다 — 이번에 막음

`CanvasPhoto`를 보는 테스트가 전부 전역 조회(`fetch`/`fetchCount`)라, **어느 사진이
어느 캔버스 것인지** 아무도 재지 않았다. `LibraryRepositoryTests`의 cascade 3건도
`photo.canvas`를 **테스트가 손으로 걸고** 삭제를 재므로 승격 경로는 밖에 있었다.

- 실측: `CanvasPromoter.attach`에서 `record.canvas = canvas`를 지우고 전체를 돌렸다.
  **254개가 전부 초록이었다.**
- 그 상태의 결과: 주인 없는 `CanvasPhoto`는 캔버스를 지워도 모음집을 지워도 남는다.
  `@Attribute(.externalStorage)`라 **실제 파일이 계속 쌓인다.** `canvas.photos`가
  비어 재편집(`CANVAS-6`)·재렌더가 사진을 못 찾고, `attach` 실패 시의 보상 삭제도
  이 관계를 전제하므로 캔버스만 사라지고 블롭이 남는다
- 방어: 소유를 통과 조건으로 삼는 테스트 3건 (AC-1·2·3)
- 검증: **줄을 지운 채로 먼저 돌려 새 테스트 3건만 빨간 것을 확인**했다
  (162개는 그대로 초록). 그다음 되돌려 전체 초록

### [정보] 같은 종류의 결함이 이 파일에서 두 번째다

직전 코드 리뷰의 `assetId` 연결 끊김도 `Set(photos.map(\.data))` 비교라
못 잡혔다. **집합 비교와 개수 비교는 연결을 보지 못한다** — 이 도메인에서
반복되는 사각지대이므로, 앞으로 `CanvasPhoto`를 보는 단언은 캔버스를 통해
되짚는 형태를 기본으로 한다.

### [정보] 캔버스가 하나뿐인 픽스처는 소유를 못 잰다

`승격된_사진은_그_캔버스에_속한다`만으로는 부족하다 — 캔버스가 하나면 전역 조회와
소유 조회가 같은 답을 낸다. `캔버스가_둘이면_각자의_사진만_갖는다`가 그 자리를
막는다.

## 코드 리뷰 반영

지적 7건 전부 유효했다. **무거운 두 건은 내가 직접 변이시켜 재확인한 뒤 고쳤다.**

### [HIGH] 초안 식별자 → 캔버스 식별자 보존이 미측정이었다

`CanvasPromoter.swift:62-64`의 주석이 계약을 명시한다 — "초안 식별자가 그대로
캔버스 식별자가 된다… 새 UUID로 대체하면 재편집이 원본을 못 찾는데 아무 신호도
없다." **그 문장을 재는 테스트가 없었다.**

- 실측: `CanvasInput(id: canvasUUID)` → `id: UUID()`로 바꾸고 돌렸다.
  **165개가 전부 초록이었다**
- 기존 테스트가 왜 못 잡았나: `UUID가_아닌_초안_식별자는_거부된다`는 **거부 경로만**
  잰다. `첫_캔버스를_승격하면_그것이_모음집_표지가_된다`는
  `a.coverCanvasID == canvas.id.uuidString`이라 **새로 발급된 값끼리 비교해 항상 참**이다
- 결과: 6단계가 초안을 지우므로 초안↔캔버스 대응이 영구 소실. 재시도하면 같은
  작업물의 캔버스가 하나 더 생긴다(`.unique`는 CloudKit 제약상 못 쓴다)
- 수정: `#expect(canvas.id == UUID(uuidString: id))`. 변이를 다시 넣어 **이 단언만
  빨간 것을 확인**했다

### [MEDIUM] 픽스처가 종횡비 이관을 원리적으로 측정 불가능하게 만들고 있었다

**`CanvasAspect.post`의 rawValue는 0이고 `Canvas.aspect`의 기본값도 0이다.**
모든 승격 픽스처가 `.post`로 고정이라, "이관했다"와 "아예 안 넣었다"가 같은
바이트를 냈다.

- 실측: `aspect: draft.meta.aspect` → `aspect: .post`(=이관 안 함)로 바꿔도
  **전부 초록이었다**
- 결과: 스토리(9:16) 초안이 4:5 좌표계 캔버스로 저장된다. `layoutJSON` 안의
  aspect와 `Canvas.aspect`가 갈라진 채 남아 재렌더·재편집의 기하가 조용히 바뀐다
- 수정: `초안준비`·`layout`에 `aspect` 파라미터를 뚫고 **`.story` 초안**으로 재는
  테스트 추가. 픽스처 주석에 "기본값에 기대지 마라"를 박아 뒀다
- 함정 하나 더: 처음 이빨 검사를 `.story`로 변이시켜 돌렸는데 **하필 테스트의
  기대값과 같아 무효한 변이**였다. `.post`로 다시 재서 확인했다

### [LOW] 4건 — 내가 쓴 단언이 약했다

- `owned.allSatisfy { $0.canvas?.id == canvas.id }`는 **실패할 수 없는 줄**이었다.
  비었으면 vacuous하게 참이고, 안 비었으면 SwiftData가 역관계 일관성을 유지하므로
  정의상 참이다 → 삭제하고 `Set(owned.map(\.id)) == Set(assets)`로 교체.
  **캔버스를 통해 `assetId` 계약을 되짚는 단언이 이제 생겼다**
- `#require(canvas.photos)`를 "비지 않았음"의 게이트로 읽으면 안 된다 —
  기본값이 nil이 아니라 `[]`다 → `count == 2`를 따로 넣었다
- to-many에 배열 `==`를 썼다. n=1이라 오늘은 안전하지만 사진 한 장만 더 붙으면
  간헐 실패한다 → `Set`으로 통일
- 주석의 "254개가 전부 초록"이 저장소 전체 수라 사각지대를 실제보다 넓게 말했다.
  이 코드 경로가 있는 앱 타깃은 162개다 → 문구 교정

## 무결성 감사에서 나온 이월 항목 (에디터 배선 전에 처리)

둘 다 **이번 변경이 만든 것이 아니다** — `CANVAS-1`(bca29d0)부터 있던 구조다.
`CanvasPromoter`를 생성하는 곳이 아직 테스트뿐이라(grep 확인) 지금은 잠재이지만,
에디터가 저장 버튼에 `promote()`를 배선하는 순간 살아난다.

### [HIGH · 이월] `createCanvas`가 자체 실패하면 보상 삭제가 아예 안 닿는다

`createCanvas`는 `insert` 뒤 `applyThenReconcileCover`를 부르고, 그 안은
**`save() → reconcile → save()`** 다(첫 save가 없으면 reconcile의 fetch가 방금 만든
캔버스를 못 본다 — 문서화된 의도).

`promote()`는 `let canvas = try library.createCanvas(...)`를 **do/catch 밖**에서
부른다. 보상 삭제는 그 아래 `attach` 실패만 감싼다.

- 발생 조건: `reconcileCover`의 fetch 또는 **두 번째 save**가 던진다
- 결과: **첫 save가 이미 커밋한 캔버스**가 모음집 정식 멤버로 남는다. `canvas`
  참조를 못 받았으므로 보상 코드에 도달조차 못 한다. 그 캔버스는 `renderedPNG`와
  `layoutJSON`은 있고 `CanvasPhoto`만 없어서, **표지로는 멀쩡히 그려지는데
  재편집하면 사진을 못 찾는다.** 다음 아무 쓰기에서 `CoverPolicy`의 정당한
  후보로 잡혀 표지가 될 수 있다
- 기존 항목과의 차이: CANVAS-1·2 ledger의 "4·5단계 쓰기 실패 미검증"은
  **`attach` 경로**만 적었다. `createCanvas`가 2단계 save를 갖고 있고 그 사이
  실패가 **보상 없는 다른 탈출구**로 샌다는 것은 새로 나온 내용이다
- 왜 지금 안 고치나: 고치려면 실패 주입이 필요한데 `ModelContext`가 구체 타입이라
  save 실패를 주입할 수단이 없다(이 저장소의 기존 한계). **테스트 없이 고치면
  고쳤는지 알 수 없다** — 배선 시점에 `LibraryRepository`에 프로토콜 이음매를
  넣는 것과 함께 처리한다

### [MEDIUM · 이월] `promote()`에 멱등성 가드가 없다

`Canvas.id`도 `CanvasPhoto.id`도 `.unique`가 없고(CloudKit 제약), `promote()`는
같은 식별자의 레코드가 이미 있는지 **한 번도 확인하지 않는다.**

- 발생 조건: 6단계 정리 실패로 초안이 남은 상태에서(이미 수용된 위험) **같은
  초안이 두 번째로 승격**된다. 위 HIGH 항목이 터진 뒤에도 같은 상태가 된다 —
  캔버스는 저장됐는데 초안이 그대로 남는다
- 결과: 같은 `id`의 `Canvas`가 둘, 같은 `id`의 `CanvasPhoto`가 **서로 다른 캔버스를
  가리키며** 공존한다. 식별자 계약(`assetId` → `CanvasPhoto.id`)이 깨진다
- `feat-canvas-promotion` ledger의 "정리 실패 후 배너" 항목은 이 상황을 알고
  있었지만 **"혼란스럽다"는 UX 관점에서 멈췄다.** 재저장까지 갔을 때 데이터
  정합성이 깨진다는 결론은 여기서 처음 적는다
- **이건 순수 로직이라 테스트로 덮인다.** 지금 배너에 탭 제스처가 없어 못 누르는
  것뿐이므로, `CANVAS-6`(재편집 세션)이나 에디터 배선보다 **먼저** 넣는 편이
  안전하다. 가드가 있으면 `CANVAS-6`가 "재승격을 어떻게 다룰지"를 침묵으로
  넘기지 못하고 명시적으로 결정하게 된다

## 위험 수용

- [4·5단계 쓰기 실패 미검증] `ModelContext`가 구체 타입이라 `save` 실패를 주입할
  수단이 없다. `CANVAS-1`에서 이월된 한계이며 이번 단위도 해소하지 못했다
- [재편집 시 사진 공유 미정] 같은 `assetId`를 두 캔버스가 쓰는 경우
  (`CanvasPhoto.id`가 중복된다) 는 `CANVAS-6`에서 설계한다. v1 신규 생성 경로에서는
  초안마다 `assetId`가 새로 발급되어 발생하지 않는다
- [고아 `CanvasPhoto` 정리 미구현] 레이어를 지웠을 때 남는 레코드는 `CANVAS-8`
