# PR 컨텍스트: EDITOR-5 — 핸들 히트 판정

## 배경

`EDITOR-4`가 방금 머지되어 선택된 레이어의 핸들(코너 4·변·회전·삭제)이 전부 화면 좌표로 배치되고, `orderedHandles`가 겹침 시 우선순위(삭제 → 코너 TL·TR·BR·BL → 회전 → 변)까지 정해 뒀다. 지금까지는 **"핸들이 화면 어디에 있는가"** 만 정의돼 있고, **"사용자가 화면의 한 점을 눌렀을 때 그중 무엇이 잡히는가"는 정의된 적이 없다.**

삭제 버튼은 좌상단 코너와 **정확히 같은 화면 좌표**에 있다(`EDITOR-4` 결정 2). 이 충돌은 손가락이 그 자리를 **가볍게 눌렀다 떼는지(탭 → 삭제)** 아니면 **누른 채로 끄는지(드래그 → 리사이즈)** 로 갈리는 실제 사용자 의도의 문제다. 순서만으로 풀면 좌상단 코너를 영영 리사이즈할 수 없다.

이 단위는 동시에 **`EDITOR-4` 리뷰에서 Minor로 미뤄진 `orderedHandles`·`edges`의 doc comment 부재를 갚는다.** 그 부재는 이미 비용을 냈다 — 이 단위의 PRD 초안이 코드만 읽고 제스처 축을 못 봐서 "좌상단 코너는 영원히 리사이즈 불가"를 수용한 채 나왔다.

## 요구사항

- **FR-1**: 화면 좌표 한 점을 받아, 44pt 히트 사각형에 드는 모든 핸들을 `orderedHandles` 우선순위 순서로 나열한 **후보 목록**을 낸다. **제스처 종류를 몰라도 조회할 수 있다.**
- **FR-2**: 히트 판정은 핸들 중심 기준 44×44pt 정사각형(중심에서 22pt) 안인지로 결정하며, 그 사각형은 **화면 좌표축에 정렬**된다(레이어 회전을 따라 기울지 않는다).
- **FR-3**: 제스처가 확정되면 후보에서 최종 하나를 고른다 — 탭은 최우선, 드래그는 **삭제를 제외한** 최우선, 남는 후보가 없으면 "핸들 아님".
- **FR-4·5**: 어떤 히트 사각형에도 안 드는 지점, 선택된 레이어가 없는 경우는 항상 "핸들 아님".
- **FR-6**: 판정이 화면 좌표만으로 계산되므로 **줌 50~400% 어디서든 히트 범위는 항상 같은 화면 44pt다.**
- **BR-2**: 경계(중심에서 정확히 22pt)는 **히트로 포함**한다 (`EDITOR-4`의 `<= 40` 관례와 일관).
- **BR-3**: **삭제는 탭에서만 최종 후보로 유효하다.**
- **BR-4**: 삭제와 무관한 겹침은 제스처가 갈라주지 못하므로 `orderedHandles` 순서만으로 정해진다.
- **BR-5**: 레이어 본체 히트 판정은 이 기능의 책임이 아니다 (`EDITOR-10`·`11`).

## 설계 목적

후보 목록 조회(`hitCandidates(at:)`)와 제스처 확정 판정(`hitHandle(at:for:)`)을 **함께** 낸다. `EDITOR-10`은 손가락이 막 닿은 순간(아직 탭/드래그 미확정)에도 "지금 이 지점에 무엇이 겹쳐 있는지"를 즉시 알아야 눌린 핸들을 하이라이트할 수 있고, 확정된 순간에는 결과 하나가 정확히 나와야 한다. 정책(BR-3)은 순수 로직에만 두고 `EDITOR-10`은 결과를 받아쓴다.

`SoozipGeometry` 단독 변경. Layout·Draft·앱·layoutJSON 무영향, 새 의존성 0.
