# EDITOR-9 — 오케스트레이터 직접 검증 원장

> 에이전트 주장과 오케스트레이터 자신의 주장을 **행동 전에** 독립 재계산한 기록.
> `EDITOR-8`에서 에이전트 수치 주장 4건이 거짓이었고 오케스트레이터 자신의 전제도 1건 거짓이었기에 유지한다.

## 2. `clampedToWorkArea`의 비유한 동작 — FR-4 결정의 근거

```
min(max(∞,  −540), 1620) = 1620.0      ← 조용히 유한해진다
min(max(NaN,−540), 1620) = NaN         ← 그대로 통과한다
```

두 비유한 종류가 **서로 다르게** 처리된다. 이것이 "기존 함수를 그대로 쓰면 안 된다"의 근거이고, FR-4를 `canvasCenter` 후퇴로 확정한 이유다.

### ✗ 라벨 오류 1건

설계서 §4-1이 *"AC-11은 둘째 부등호(`0<=0`)만 고정한다"*고 적었으나, 설계 자신의 정의(`overlaps(other) = lower <= other.upper && other.lower <= upper`, self=캔버스)로는 `0 <= 0`이 **첫째** 부등호다. 실측 킬셋도 AC-11이 "첫 부등호 `<` 변이"를 죽이는 것으로 나온다. **실질 주장(한쪽 부등호에 팽팽한 증인이 없다)은 옳고 서수 라벨만 반대다.**

### ✗ 환경 주장 거짓 1건

*"현재 브랜치가 `feat/editor-layer-limits`이고 `SoozipLayout` 3개 파일이 미커밋"* — 실제는 `feat/editor-boundary`, 변경은 로드맵 문서 1건뿐. 에이전트가 세션 시작 스냅샷을 읽었다. 구현에 영향 없음.

## 5. 유한성 가드 — 증인 불가를 실제 Swift로 확정

`swiftc -O`로 가드 없는 구현에 다섯 입력을 넣었다:

| 입력 | x투영 | 결과 |
|---|---|---|
| `center.x = NaN` | `lo=nan hi=nan` | `outside` |
| `size.w = ∞`, `rot = 0` | `lo=nan hi=nan` | `outside` |
| `rotation = NaN` | `lo=nan hi=nan` | `outside` |
| `size.w = ∞`, `rot = π/4` | `lo=nan hi=nan` | `outside` |
| `center.y = ∞` | `lo=nan hi=nan` | `outside` |

**Swift `min`/`max`의 NaN 인자순서 의존도 함께 확인했다** — `min(NaN,1.0)=nan`이지만 `min(1.0,NaN)=1.0`이다. 접기(`lo = min(lo, x)`)에서 NaN이 조용히 탈락할 수 있는 구조인데, FR-3의 모든 경로에서 **코너 4개가 전부 오염**되므로 순서와 무관하게 살아남는다. 부분 오염은 발생 불가다 — 코너 4점이 같은 `(center, size, rotation)`에서 나오므로 한 성분의 비유한이 네 점의 같은 성분을 모두 오염시킨다.

## 8. ⚠️ 위 §5 결론이 구현 후 뒤집혔다 — 이 원장의 가장 중요한 정정

**§5의 측정은 접기 모델(`lo = v[0]`에서 시작해 `lo = min(lo, x)`)로 했는데, 실제 구현은 `reduce(±∞, min/max)`다.** 그 차이가 결론을 통째로 뒤집었다.

실제 코드에 가드 제거 변이를 적용해 `swift test`로 측정한 결과:

| | 접기 모델 (§5의 가정) | 실제 구현 `reduce(±∞, …)` |
|---|---|---|
| 전 원소 `NaN`인 투영 | `lower = NaN`, `upper = NaN` | **`lower = +∞`, `upper = −∞`** (뒤집힌 빈 구간) |
| `contains` 판정 | 거짓 | **공허하게 참** |
| 가드 없는 결과 | `.outside` | **`.inside`** |
| 죽는 테스트 | 0건 | **`레이어_값이_하나라도_비유한이면_완전히_밖이다` (3입력 전부)** |

`.inside`는 세 답 중 **가장 위험한 오판**이다 — "정상 렌더, 고스트 없음"으로 보인다.

**교훈**: 변이 킬셋은 **모델이 아니라 실제 코드에서** 재야 한다. `EDITOR-8`에서 "실행 코드 한 줄 변경이 킬셋 구조를 바꿔 주석 4곳을 낡게 만들었다"는 교훈이 나왔는데, 이번에는 **애초에 모델과 구현이 달랐다**는 형태로 같은 축에서 재발했다.

**그리고 이 정정이 5개 사본 중 2개에만 닿았다** — 프로덕션 doc과 테스트 주석만 고치고 `design.md`·`prd.md`·이 파일을 놓쳐, 2회차 quality 리뷰가 잡았다. 저장소 7번째 "같은 사실이 갈라진다"이며, **정정 자체가 그 패턴을 또 만들었다**는 점이 기록할 값이다.

## 6. §4-5 (유한 입력 오버플로) — 실측으로 유도 확정

`swiftc -O`, `Double.greatestFiniteMagnitude` 투입:

| 입력 | NaN 발생 | Inf 발생 | 분류 |
|---|---|---|---|
| center 거대 · size 거대 · rot 0 | **false** | true | `outside` |
| center 거대 · size 거대 · rot π/4 | **false** | true | `outside` |
| center 0 · size 거대 · rot π/4 | **false** | false | `partial` |

설계서 §4-5의 유도(`|c|,|s| ≤ 1`이라 `px*c`는 안 넘치고, 무한대 항이 최대 하나라 `∞−∞`가 없다)가 맞다. **가드하지 않고 기록만 하는 결정은 유지 가능.**

## 7. §4-6 (회전 시 경계 오차) — 설계서보다 범위가 넓다 ⚠️

`swiftc -O`. 캔버스와 **정확히 같은 크기**인 레이어를 회전시켰다:

| 회전 | 분류 | 기대 |
|---|---|---|
| 0° | `inside` | ✓ |
| 90° | **`partial`** | ✗ |
| 180° | **`partial`** | ✗ |
| 270° | **`partial`** | ✗ |
| 360° | **`partial`** | ✗ |

90° 코너 실측: `(1080, −3.306546e-14)` · `(1080, 1350)` · `(0, 1350)` · `(0, 3.306546e-14)`.

**설계서 §4-6은 이 문제를 90°에만 있는 것으로 적었다.** 실제로는 90의 배수 전부에서 발생하고, **180°·360°는 크기 변경 없이 도달하므로 90°보다 흔하다**(캔버스를 꽉 채운 배경 사진을 뒤집는 조작). `EDITOR-8`의 15° 스냅이 이 각도들을 정확히 도달 가능하게 만들어 뒀고, 바퀴 수 보존 결정 때문에 360°는 0°로 접히지 않는다.

**추가 논점**: `SnapEngine.isAxisAligned`는 `EDITOR-8`에서 **한 바퀴 돈 레이어를 축 정렬로 인정**하도록 허용오차 `0.0001` 라디안을 쓴다. 즉 저장소의 다른 판정은 이미 "360° ≈ 0°"를 허용오차로 처리하는데 **이 단위만 정확 비교라 다르게 답한다.** design-critic에 이 실측을 전달해 판단을 요청했다.
