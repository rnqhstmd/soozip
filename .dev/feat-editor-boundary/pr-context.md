# EDITOR-9 — 경계 (캔버스 밖 클리핑·고스트 판정·레이어 이탈 방지) · PR 배경 자료

## 배경

editor 로직 축에서 **경계만 비어 있었다.** `EDITOR-1`이 캔버스 표면(줌·팬·작업 영역)을, `EDITOR-4~8`이 선택·히트·겹침 방지·리사이즈·회전을 채웠지만, **레이어가 캔버스 밖으로 나갔을 때 무엇이 일어나는가**에 대한 판정이 하나도 없었다.

v4 §5.10은 이 지점에서 **의도적으로 클램프를 거부한다** — *"레이어는 캔버스 밖으로 자유롭게 나갈 수 있고, 캔버스 경계에서 잘려 보인다. 다시 안으로 밀면 잘린 부분이 그대로 돌아온다. 위치를 제한하지 않는다."* 이유도 함께 적혀 있다: *"가장자리에서 잘린 사진, 화면 밖으로 흘러나가는 도형은 콜라주의 기본 문법이다. 중심을 캔버스 안에 가두면 이 표현이 통째로 불가능해진다."*

대신 안전장치는 **딱 하나**다 — 레이어 중심이 작업 영역(캔버스의 2배) 밖으로 나가면 줌 아웃(최소 50%)으로도 볼 수 없어 **영영 잡을 수 없게** 되므로 그 선만 막는다.

**그 사각형은 이미 있었다.** `CanvasSurface.workArea`가 팬 한계에 쓰이고 있었고, 그 doc이 직접 이 단위를 지목했다 — *"`EDITOR-9`(레이어 경계)가 이 사각형을 다시 정의하지 않도록 공개한다. 두 벌로 갈라지면 '팬으로 못 닿는 곳에 레이어가 놓이거나, 레이어가 못 가는 곳까지 팬되는' 어긋남이 조용히 생긴다."* 이 PR은 그 약속을 지킨다 — `workArea`를 재계산하지 않고 그대로 호출한다.

## 요구사항

- **FR-1** [Must] 겹침 **3분류** — `완전히 안` / `부분 겹침` / `완전히 밖`. 입력은 회전 반영 코너 4점. 경계에 닿은 좌표는 안쪽 포함
- **FR-2** [Must] 중심 작업영역 클램프 — `workArea`/`clampedToWorkArea` **그대로 재사용**
- **FR-3** [Must] FR-1 비유한 방어 — 스칼라 **7개**(레이어 5 + 캔버스 2) 중 하나라도 비유한이거나 캔버스 치수가 0 이하면 `완전히 밖`
- **FR-4** [Must] FR-2 비유한 방어 — `center`가 비유한이면 **`canvasCenter`로 후퇴**. `Infinity`와 `NaN`이 같은 결과
- **BR-3** 회전 레이어를 배제하지 않는다(AABB 근사 금지) · **BR-4** `workArea` 재계산 금지 · **BR-6** 경계 규칙 한 벌 · **BR-7** `부분 겹침`은 양의 넓이를 함의하지 않는다
- **BR-5** [Should] 중심을 바꾸는 모든 경로가 클램프를 거쳐야 함 — 강제 방식은 `EDITOR-10`·`EDITOR-11` 이월

## 이 단위에서 밝혀진 것

**AABB 근사가 실제로 틀리는 것을 실측했다.** 중심 `(−60,−60)`·크기 `141.42²`·회전 45°인 다이아몬드는 AABB가 캔버스와 `[0,40]²`에서 겹치지만 **실제 형태는 한 점도 공유하지 않는다**(네 코너가 전부 `x+y ≤ −20`이고 캔버스는 `x+y ≥ 0`). `SnapEngine`은 이 문제를 회전 레이어를 아예 배제해서 피했지만 **경계 판정은 배제할 수 없다** — 회전된 사진도 밖으로 나가고 고스트가 필요하다.

**회전 0에서 `u ≡ x`, `v ≡ y`가 비트 단위로 정확히 성립한다**(`cos(0)=1.0`·`sin(0)=0.0`이 정확값). 그래서 **회전 0인 입력으로는 `x`·`y` 축 삭제 변이를 절대 잡을 수 없다** — 쌍둥이 축이 대신 분리한다. 네 분리축의 유일 증인 중 둘은 회전 30° 입력이다.

**비유한 클램프의 두 종류가 서로 다르게 처리되고 둘 다 방어가 아니었다.** 기존 함수를 그대로 쓰면 `∞ → 1620`(그럴듯한 좌표라 아무도 눈치채지 못한다), `NaN → NaN`(그대로 통과). `NaN`이 레이어 중심에 앉으면 **`JSONEncoder`가 던져 문서 저장 자체가 실패**한다 — `EDITOR-8`이 `rotation` 축에서 발견해 제거한 것과 같은 형태다. `canvasCenter` 후퇴로 둘을 합류시켰고, 그 값이 항상 작업 영역 안이라 **후퇴 경로도 멱등**이다.

**같은 시그니처 두 함수가 만든 무증인 축을 컴파일러로 닫았다.** `clampedLayerCenter`와 `clampedToWorkArea`는 같은 타입·같은 시그니처(`Vec2 → Vec2`)·인접한 이름이라 자동완성에 나란히 뜬다. 배선이 잘못 고르면 저장이 깨지는데 **이 단위의 테스트 22건은 전부 초록이다**(함수를 직접 부르는 단위 테스트라 호출부 선택을 못 본다). `clampedToWorkArea`에서 `public`을 떼어 잘못 고르는 경로 자체를 없앴다 — 패키지 밖 소비자 0건 확인.

**30%는 판정 임계가 아니라 불투명도다.** 로드맵이 `고스트 판정(30%)`으로 적어 면적 임계로 읽힐 수 있었으나 v4 원문은 *"30% 불투명도의 고스트"*다. 이 단위는 **"어디가 밖인가"라는 기하 분류만** 내고 렌더 상수는 `EDITOR-11`이다.

**변이 16종의 킬셋을 실제 `swift test`로 측정했고, 그 과정에서 설계·PRD·주석 세 곳이 함께 틀린 것을 발견했다.** *"레이어 유한성 가드에는 원리적으로 증인이 없다"*는 주장이었는데, 모델은 접기(`lo = min(lo, x)`)였고 구현은 `reduce(±∞, min/max)`였다. 전 원소 `NaN`이면 **뒤집힌 빈 구간**(`lower = +∞`, `upper = −∞`)이 되고 `contains`가 공허하게 참이 되어 **`.inside`**(세 답 중 가장 위험한 오판)가 나온다. **가드에는 증인이 있고, 그 증인을 만드는 것은 씨앗값이다** — 씨앗값을 없애는 리팩터링은 동작을 안 바꾸면서 증인만 지운다.

## 리뷰에서 나온 것

**Critical 0 · 실행 코드 결함 0건.** design-critic MUST-ADDRESS 6건은 전부 사실로 확인돼 설계에 반영됐고(캔버스 치수 가드 누락 · `.partial` 넓이 계약 · 회전 오차 근거 무효 · 두 클램프 시그니처 동일 · AC-13 무효화 · 인계 미수신), 이후 리뷰 2회차의 Important 1건도 **주석 모순**이었다.

**정정이 5개 사본 중 2개에만 닿는 사고가 재발했다.** 위 킬셋 발견 후 프로덕션 doc과 테스트 주석만 고치고 `design.md`·`prd.md`·검증 원장을 놓쳤다. 특히 **설계서가 프로덕션에게 이미 반증된 문장을 적으라고 지시**하는 상태였다 — 그대로 뒀다면 다음 리뷰가 정확한 프로덕션 doc을 거꾸로 "설계 위반"으로 잡는다. 2회차가 잡아 원문 보존 + 정정 블록으로 닫았다.

**security 감사가 도달 가능한 결함 1건을 찾았다.** `LayoutDocument`가 `canvas.w`/`h`를 검증 없이 디코딩해서 `{"w":0,"h":0}` 문서면 작업 영역이 한 점으로 붕괴하고 모든 레이어 중심이 뭉개진다. 이 단위는 **신뢰 경계 차이**(`overlap(canvas:)`은 임의 인자를 받고, `clampedLayerCenter`는 생성 시 확정된 자기 상태를 읽는다)로 문서화하고 **디코딩 검증을 `SoozipLayout` 이월**로 남겼다.

**테스트 168 → 190**(+22), 경고 baseline 유지, 릴리스 빌드 성공.
