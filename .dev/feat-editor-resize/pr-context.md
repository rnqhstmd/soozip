# EDITOR-7 — 리사이즈 (PR 배경 자료)

## 배경

`SoozipGeometry`에는 리사이즈 계산이 이미 있었고 테스트 7건이 "대각 고정점 유지"·"비율 유지"·"하한/상한 근처에서 정지"를 관측 중이었다. 이 단위는 새 함수를 만드는 것이 아니라 로드맵이 명시한 빈틈을 메운다.

1. **회전 90°가 관측된 적이 없었다** — 기존 회전 축은 0과 45°뿐인데 로드맵은 "0°·45°·90° 전부"를 요구했다.
2. **하한 40 / 상한 "캔버스 긴 변 ×4"가 프로덕션에 없었다.** 값이 테스트 파일의 `private let` 두 줄에만 있었고, 그중 `// 캔버스 긴 변 1920 × 4` 주석이 **유도 규칙의 두 번째 기술**이었다. 방치하면 배선 단위가 자기 리터럴을 또 박아, 이 저장소가 다섯 번 겪은 "같은 규칙이 두 곳에 적혀 조용히 갈라진다"가 여섯 번째가 된다.
3. **`clamped`가 정확히 `(0,0)`을 스킵했다** — 코너를 대각 고정점 위로 정확히 끌면 폭·높이가 둘 다 0이 되는데 하한 조건이 `shortSide > 0`이라 클램프가 통째로 건너뛰어졌다. 레이어가 점이 되어 다시 잡을 수 없다 — 설계서가 하한을 둔 이유가 정확히 그 상태다.

## 요구사항

- **FR-1** 대각 고정점 유지가 회전 0°·45°·90° 전부에서 성립
- **FR-2** 하한 40 · 상한(캔버스 긴 변 ×4)이 프로덕션 단일 출처로 신설되고 두 비율(4:5 → 5400 / 9:16 → 7680)로 유도
- **FR-3** 크기가 정확히 0이 되는 입력에서도 하한 40 적용 (버그 수정)
- **FR-4** 고정점 너머로 끌어도 고정점 유지·양수 크기·비율 유지·뒤집힘 없음
- **FR-5** *(Should)* 드래그 좌표·하한·상한 중 하나라도 비유한이면 결과가 원본 프레임을 벗어나지 않음
- **BR-1** **하한이 상한을 이긴다** — 짧은 변은 어떤 입력에서도 40px 미만이 되지 않고, 필요하면 긴 변의 상한 초과를 허용한다

## 이 단위에서 밝혀진 것

**보정 블록이 대수적 항등이다.** `resized(draggingCorner:)`의 마지막 보정은 `center_final = anchorWorld − R(anchorSign × new/2)`로 정리되어 중심 계산이 완전히 소거된다(무작위 300회 실측 편차 1.2e-11). 귀결로 **"고정점이 유지된다"를 재는 단언은 `corner.opposite` 외의 어떤 변이도 죽이지 못한다** — 결과가 유한하기만 하면 통과한다. 실질 관측면은 `size`와 끌린 코너 쪽이다.

**AC가 요구사항을 과소 명세한 곳이 두 군데 있었고 둘 다 실제 결함으로 이어졌다.**
- 비유한 **한계값**은 결과를 오염시키지 않고 클램프만 조용히 무력화한다 — 하한 `.nan`이면 `(2,1)`, 상한 `.nan`이면 `(200898, 100449)`. 둘 다 완벽하게 유한해서 AC-7의 `isFinite`로는 영원히 관측되지 않는다.
- FR-5는 "리사이즈 결과"라고만 쓰고 코너로 한정하지 않는데, `resized(draggingEdge:)`에는 방어가 **0건**이었다. `.right` 변을 `(.infinity, 400)`으로 끌면 `size (NaN, 0)`·`center (NaN, NaN)`이 public API 밖으로 나갔다. **`JSONEncoder`가 `NaN`에서 던지므로 문서 저장 자체가 실패한다.**

**이 단위가 만든 회귀를 같은 단위에서 막았다.** `(0,0)` 붕괴 복원이 극단 비율(`> 4.494e306` 또는 `< 2.2250738585072018e-307`)에서 오늘 유한한 결과를 `(inf, 40)`·`center NaN`으로 바꾼다. `(0,0)`의 올바른 답 `40 × 1e307`은 `Double`로 표현할 수 없어 어떤 구현도 낼 수 없으므로, 정직한 선택지는 원본 후퇴뿐이고 후퇴하려면 검출이 필요하다.
