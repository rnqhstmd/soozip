# PRD: EDITOR-7 — 리사이즈 (코너 드래그 대각 고정점 + 크기 하한·상한)

## 배경

`SoozipGeometry`에는 이미 `LayerFrame.resized(draggingCorner:to:minShortSide:maxLongSide:)`와
`resized(draggingEdge:to:minShortSide:maxLongSide:)`가 구현되어 있고, 기존 테스트 7건이
"대각 고정점 유지"·"비율 유지"·"하한/상한 근처에서 정지"·"변 핸들 한 축만 변경"을 이미 관측 중이다.
이 단위는 새 함수를 만드는 것이 아니라, 로드맵이 명시한 빈틈을 메우는 것이다.

1. 로드맵(`docs/plans/2026-08-11-00-tdd-roadmap-v1.md:120`)은 "회전 0°·45°·90° 전부"를 요구하는데,
   기존 테스트의 회전 축은 0과 π/4(45°)뿐이다 — **90°가 관측된 적이 없다.**
2. 추적 문서(`context/editor/status.md:28`)는 "하한·상한 값 주입은 EDITOR-7"이라고 명시한다.
   **`grep`으로 직접 확인한 결과, 프로덕션 코드 어디에도 `40`·`5400`·`7680` 리터럴이나
   "긴 변×4" 산식이 없다.** `ResizeAnchor.swift`는 `minShortSide`/`maxLongSide`를 매개변수로만 받고,
   `CanvasSurface`에도 긴 변을 유도하는 프로퍼티가 없다. 값은 오직 `ResizeAnchorTests.swift`의
   `private let minSide = 40` / `private let maxSide = 7680`으로만 존재한다.
   이 상태로는 `EDITOR-11`이 자기 리터럴을 또 박게 된다 — 이 저장소는 "같은 규칙이 두 곳에 적혀
   조용히 갈라지는" 패턴을 이미 **5회** 겪었다(`workArea`·`LayerCategory`·`LayerKind`·
   `resizableEdges`·EDITOR-5의 `edges` doc).

이 단위는 **순수 계산 단위**다. `SoozipLayout`(레이어 스토어)이나 SwiftUI 화면은 건드리지 않는다 —
로드맵상 EDITOR-7의 의존은 EDITOR-4(선택 상태)뿐이다.

코드를 손으로 전개하는 과정에서 이 단위가 손대는 바로 그 함수(`resized(draggingCorner:)`가
공유하는 `clamped`)에 로드맵이 요구하는 엣지케이스가 실제로 뚫려 있는 것을 발견했다 —
아래 "산출 근거"에 검산 과정을 전부 남긴다.

## 요구사항

### 기능 요구사항

- **[Must] FR-1**: 코너 드래그 시 대각 반대편 코너가 고정점으로 유지되는 성질이 회전
  **0°·45°·90° 전부**에서 성립한다. (현재 0°·45°만 테스트로 고정되어 있다.)
- **[Must] FR-2**: 하한 40px·상한(캔버스 긴 변 × 4)의 값이 **프로덕션 코드에 단일 출처로 신설**되고,
  캔버스 두 비율(4:5 → 5400 / 9:16 → 7680) 각각에 대해 정확히 유도된다. 그 값을 리사이즈 클램프가
  실제로 사용해 정지한다. **어디에 두는지(예: `LayerFrame`의 정적 상수 / `CanvasSurface`의 파생
  프로퍼티)는 설계의 몫이며 이 PRD는 위치를 못박지 않는다.**
- **[Must] FR-3 (버그 수정)**: 드래그로 계산된 크기가 정확히 0이 되는 입력(코너를 대각 고정점 위로
  정확히 끌었을 때)에서도 하한 40px가 적용된다. **현재는 적용되지 않는다** — "산출 근거" 참조.
  이 지점은 현재 클램프 구조로는 단순 배율 조정만으로 도달할 수 없다는 구조적 제약이 있다.
- **[Must] FR-4**: 코너를 대각 고정점 너머로 끌어도(반대편으로 넘어가도) 고정점은 그대로 유지되고,
  결과 크기는 양수·원본 비율을 유지하며 뒤집히지 않는다.
- **[Should] FR-5**: 드래그 좌표(`worldPoint`)·하한·상한 중 하나라도 비유한(NaN·Infinity)이면
  리사이즈 결과가 원본 프레임을 벗어나지 않는다.

### 비즈니스 규칙

- **[Must] BR-1 (사용자 결정으로 확정)**: **하한이 상한보다 우선한다.** 짧은 변은 어떤 입력에서도
  40px 미만으로 내려가지 않는다. 이를 지키기 위해 필요하다면 긴 변이 상한(캔버스 긴 변 × 4)을
  넘는 것을 허용한다. 근거: 상한을 넘은 레이어는 여전히 선택·조작 가능하지만, 하한 아래로
  내려가면 핸들이 겹쳐 다시 잡을 수 없다.

### 품질 기대

- **[Should] QE-1**: 사용자가 코너 핸들을 화면 끝까지, 또는 반대편 코너를 넘어서까지 끌어도
  레이어가 소실되거나(0크기) 순간적으로 반전되어 보이지 않는다. (AC-4·AC-5로 검증)

## 산출 근거 (손으로 재전개 — 오케스트레이터가 수치로 재검증 완료)

### 1. FR-3 — 0-붕괴 버그 재현

frame = `center (500,400), size (200,100), rotation 0`.
`topRight`를 대각 고정점(`bottomLeft`)의 실제 월드 좌표 `(400,450)` 위로 정확히 끈다.

- `dragLocal = toLocal((400,450)) = (-100, 50)` — `anchorLocal(bottomLeft) = (-100, 50)`과 **정확히 같다.**
- `rawW = |dragLocal.x - anchorLocal.x| = 0`, `rawH = |dragLocal.y - anchorLocal.y| = 0`
- `newW = max(0, 0×ratio) = 0`, `newH = 0`
- `clamped(0, 0, min:40, max:7680)`: `shortSide = 0`. 조건이 `shortSide < 40 && shortSide > 0` →
  `0 > 0`이 거짓이라 **클램프 전체가 스킵된다.** 결과 `(0, 0)`.

**구조적 제약**: `(0, 0)`은 어떤 배수를 곱해도 `(0, 0)`이다 — 곱셈 기반 스케일링(`w *= k; h *= k`)으로는
이 지점에서 40px를 복원할 수 없다. 복원에 필요한 것은 "그 순간의 (0,0) 값"이 아니라 **원본 종횡비**다.
`resized(draggingCorner:)`는 이 값을 `ratio`로 이미 계산해 갖고 있지만(드래그 전 `size.width/size.height`),
공유 헬퍼 `clamped(width:height:...)`는 `width`·`height`만 받고 `ratio`를 별도로 받지 않는다 —
`(0,0)` 시점에는 그 안에서 비율을 되짚을 수 없다.
**이 사실 관계만 남긴다 — 해법(매개변수 추가·호출부 재구성 등)은 설계의 몫이다.**

**다른 `(0,0)` 도달 경로 확인**: 코너 드래그에서 `rawW=0` 또는 `rawH=0`만으로는 `newW=0`이 되지 않는다
(`newW = max(rawW, rawH×ratio)`이므로 `ratio>0`인 정상 프레임에서는 **rawW·rawH가 모두 0이어야만**
`newW=newH=0`이 된다) — 이는 `dragLocal == anchorLocal`, 즉 **드래그 지점이 고정점의 월드 좌표와
정확히 일치할 때만** 성립한다. 다른 경로는 없다.
변 드래그(`resized(draggingEdge:)`)는 `newW = |dragLocal.x| + size.width/2`(변경 축) 또는
`size.height` 그대로(불변 축)라 **원본 크기가 이미 0이 아닌 한** 0에 도달할 수 없다.
원본 프레임 자체가 이미 `(0,0)`인 경우는 `ratio = 0/0 = NaN`이 되어 오히려 **다른 실패 신호
(NaN 전파, FR-5의 방어 대상)로 새며, 이 `(0,0)` 스킵 결함과는 별개 문제다** — 같은 취급으로 묶지 않는다.

### 2. 결정 2 — 프로덕션에 단일 출처 부재 확인

```
grep "7680|5400|minShortSide|maxLongSide" Packages/SoozipGeometry/Sources/
  → 매개변수 이름만 있음, 리터럴 0건
grep "longSide" Packages/SoozipGeometry/Sources/SoozipGeometry/CanvasSurface.swift
  → 매치 없음
```

`CanvasSurface`는 `canvas: Size2`만 들고 있고 `Size2.longSide`는 존재하지만(`Vec2.swift:32`)
그것을 4배 해 상한으로 쓰는 코드는 어디에도 없다.
`context/editor/status.md:28`의 "값 주입은 EDITOR-7"이 아직 미충족임을 코드로 확인했다.

**설계 제약(오케스트레이터 확인)**: `CanvasAspect`(`.post` 1080×1350 / `.story` 1080×1920)는
`SoozipLayout/LayoutDocument.swift:6`에 있고, **`SoozipGeometry`는 `SoozipLayout`을 볼 수 없다**
(단방향 의존). 따라서 유도 코드는 `CanvasAspect`를 참조할 수 없고, `Size2`를 받거나
이미 `canvas: Size2`를 들고 있는 `CanvasSurface`에 붙어야 한다.

### 3. BR-1 / AC-6 — "하한 우선" 재전개 및 수렴성

정책은 "짧은 변은 항상 40 이상, 그 결과 긴 변이 상한을 넘어도 허용"이다.
**원본 비율 유지가 이미 결정된 불변식**(기존 테스트 "코너드래그는 원본 비율을 유지한다")이므로,
하한이 발동하는 조건에서 정답은 구현 방식과 무관하게
**`shortSide = minShortSide`, `longSide = minShortSide × ratio`로 유일하게 결정된다.**

검증 입력: `LayerFrame(center:(0,0), size:(8000,40), rotation:0)`(비율 200:1) — `topRight`를
**자기 자신의 현재 위치** `(4000,-20)`로 끈다(`min:40, max:7680`). `rawW=8000, rawH=40`, `ratio=200`.

검산 수단(적용 순서를 바꿔 확인 — **이것은 검산 방법일 뿐 설계 결정이 아니다**):
상한 먼저 → `longSide=8000>7680`, `k=0.96` → `(7680, 38.4)`.
이어서 하한 → `shortSide=38.4<40`, `k=40/38.4≈1.041667` → **`(8000, 40)`**.

**수렴성**: 같은 원본(비율 200 고정)에서 `topRight`를 훨씬 먼 지점으로 끌어도 `newH=newW/ratio`
관계가 유지되므로 상한 클램프 후 항상 `(7680, 38.4)`(고정)가 되고, 하한 적용 시
`(ratio×minShortSide, minShortSide) = (8000, 40)`으로 **드래그 거리와 무관하게 수렴한다.**

**일반화**: 하한이 발동하는 모든 충돌 사례에서 최종 `longSide = ratio × minShortSide`로 유계다.
`ratio`는 드래그가 만드는 값이 아니라 **원본 프레임이 이미 갖고 있던 값**이므로, "하한 우선"이
설계서가 우려한 "스케일 값이 발산해 렌더가 무너진다"(v4 §5.7)를 재도입하지 않는다.

**부동소수 주의(오케스트레이터 실측)**: 실제 계산값은 `8000.000000000001`이고,
1e9 지점 드래그에서는 `7999.999999999999`다. **AC의 `==` 표기는 저장소 규약대로 `isClose`로
읽어야 한다** — 엄밀 등가로 쓰면 통과 불가능한 테스트가 된다.

### 4. 현재 코드의 하한 누수 (BR-1의 반대 방향)

같은 입력을 현재 순서(하한 → 상한)로 통과시키면 하한 블록은 `40 < 40`이 거짓이라 건너뛰고
상한 블록이 `k=0.96`을 곱해 **`(7680, 38.4)`** 를 낸다 — 짧은 변이 하한 40 아래로 1.6px 샌다.
임계 비율은 `상한/하한` = `7680/40 = 192`(9:16) · `5400/40 = 135`(4:5)다.

## 사용자 시나리오

- **정상 흐름**: 코너 핸들을 끌면 대각 반대편이 고정된 채 비율을 유지하며 커지거나 작아진다.
- **예외 흐름 — 고정점 근접/통과**: 고정점 쪽으로 계속 끌면 40px에서 멈춘다(FR-3).
  더 끌어 반대편으로 넘어가도 고정점은 그대로이고 뒤집히지 않는다(FR-4).
- **엣지케이스 — 하한 도달 후 손가락-레이어 어긋남**: 하한에 닿은 뒤 손가락을 계속 안쪽으로 밀면
  레이어는 40px에 멈춰 있고 손가락만 더 들어간다. **이미 설계서가 받아들인 동작**이다
  (v4 §5.10 "짧은 변 논리 40px에서 정지"). 이 단위가 새로 결정하는 것은 없다.
- **엣지케이스 — 극단 비율에서 상한 초과**: 비율 200:1 같은 아주 가는 레이어는 하한을 지키다
  상한을 넘을 수 있다(BR-1, 사용자 결정). 캔버스보다 훨씬 커 보일 수 있으나 여전히
  선택·삭제·재조작 가능하다.

## 수용 기준

```
AC-1: 회전 90°에서도 코너드래그 시 대각 고정점이 유지된다 (FR-1)

  When: topRight 코너를 (700,300)으로 끈다 (minShortSide: 40, maxLongSide: 7680)
  Then: 결과 프레임의 bottomLeft 코너 좌표가 (450, 300)과 오차 0.01 이내로 같고,
        결과 size가 (500, 250)이다 (원본 비율 200:100=2 유지)
```

```
AC-2: 리사이즈 상한이 캔버스로부터 프로덕션 코드로 유도된다 (FR-2)
  Given: 논리 캔버스 크기 (1080,1350)[4:5]와 (1080,1920)[9:16] 각각
  When: 프로덕션 코드가 그 캔버스로부터 리사이즈 하한·상한 값을 유도한다
        (호출 지점·형태는 설계가 정한다 — 이 AC는 값만 관측한다)
  Then: 유도된 하한이 두 캔버스 모두 40이고, 유도된 상한이 4:5에서 5400·9:16에서 7680이다.
        세 값 모두 테스트 파일의 리터럴이 아니라 프로덕션 코드가 반환한 값이어야 한다
```

```
AC-3: 리사이즈 클램프가 유도된 상한을 실제로 사용해 정지한다 (FR-2)
  Given: LayerFrame(center: (500,400), size: (200,100), rotation: 0),
         AC-2에서 검증된 프로덕션 유도 상한값
  When: topRight 코너를 (99999,-99999)로 끈다 (minShortSide: 40,
        maxLongSide: AC-2가 유도한 값을 그대로 전달)
  Then: 4:5 유도값(5400) 사용 시 결과 size == (5400, 2700)이고,
        9:16 유도값(7680) 사용 시 결과 size == (7680, 3840)이다
```

```
AC-4: 대각 고정점 위로 정확히 끌어도 크기가 0이 아니라 하한 40px에서 멈춘다 (FR-3)
  ⚠ 산출 근거 §1의 "구조적 제약" 참조 — (0,0)에서 배율 조정만으로는 도달 불가능하며
    원본 종횡비를 별도로 참조하는 경로가 필요하다(구현 방식은 설계 결정 사항).
  Given: LayerFrame(center: (500,400), size: (200,100), rotation: 0)
  When: topRight 코너를 대각 고정점(bottomLeft)의 정확한 좌표 (400,450)으로 끈다
        (minShortSide: 40, maxLongSide: 7680)
  Then: 결과 size.shortSide == 40 (0이 아님), size.longSide == 80 (비율 2 유지),
        결과 bottomLeft 코너 좌표는 (400, 450)으로 유지된다
```

```
AC-5: 대각 고정점을 넘어 반대편으로 끌어도 도형이 뒤집히지 않는다 (FR-4)
  Given: LayerFrame(center: (500,400), size: (200,100), rotation: 0)
  When: topRight 코너를 대각 고정점(400,450)을 지나쳐 (300,500)으로 끈다
        (minShortSide: 40, maxLongSide: 7680)
  Then: 결과 bottomLeft 코너 좌표가 (400, 450)로 유지되고, 결과 size가 (100, 50)이며,
        결과 topRight 코너 좌표가 (500, 400)이다 (anchor 기준 우상단 방향 유지)
```

```
AC-6: 하한·상한이 동시에 충돌하면 하한이 우선한다 (BR-1, 확정)
  Given: LayerFrame(center: (0,0), size: (8000,40), rotation: 0)  // 비율 200:1
  When: topRight 코너를 자기 자신의 현재 위치 (4000,-20)로 끈다
        (minShortSide: 40, maxLongSide: 7680)
  Then: 결과 size == (8000, 40) — 짧은 변 40 유지, 긴 변 8000이 상한 7680을 초과한 채 확정된다.
        같은 프레임을 훨씬 먼 지점(예: (999999999,-999999999))으로 끌어도 결과는
        동일하게 (8000, 40)으로 수렴한다 (산출 근거 §3 참조)
        ※ 부동소수 실측값이 8000.000000000001 / 7999.999999999999이므로 isClose로 판정한다
```
