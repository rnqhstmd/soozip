### D-1. 하한 40 / 상한 ×4의 단일 출처

**후보**

| # | 위치 | 평가 |
|---|---|---|
| A | `CanvasSurface`의 파생 프로퍼티 | AC-2의 Given이 `Size2`라 테스트가 무의미한 `viewport`를 지어내야 한다. 더 나쁜 것은 뷰포트·줌과 무관한 값이 `surface`에 붙어 "언젠가 `scale`을 곱한다"가 합리적으로 보이게 되는 것 — 그 순간 하한의 단위가 논리 px에서 화면 pt로 조용히 바뀐다 |
| B | `Size2` 확장 | 순수 값 타입에 리사이즈 **정책**을 얹는다 |
| C | `ResizeLimits` 구조체(`init(canvas:)` 단독) + `resized(…limits:)` 시그니처 교체 | **1회차 기각 근거가 거짓이었다(V-7).** 아래에서 다시 판단 |
| D | **`extension LayerFrame`의 정적 팩토리 + `private` 상수 2종** | 소비자 시그니처와 같은 파일, `Size2`를 받아 세 출처를 다 받는다 |

**선택: D (사용자 확정 1). 기각 근거를 전면 교체한다.**

> **V-7 정정 — 1회차의 "C안은 AC와 충돌한다"는 거짓이었다.** PRD FR-2는 "**어디에 두는지는 설계의 몫이며 이 PRD는 위치를 못박지 않는다**", AC-2 When은 "**호출 지점·형태는 설계가 정한다**"라고 적혀 있다. AC 6건의 `(minShortSide: 40, maxLongSide: 7680)`은 **관측 조건의 값**이지 시그니처 확정이 아니며, `ResizeLimits(canvas: story)`가 `(40, 7680)`을 내므로 **충돌 지점은 0건이다.**

**재판단 후에도 D를 고르는 근거 (전부 비용·범위)**

1. **비용**: `public` 시그니처 2개 변경 + 호출부 9곳 재작성. test-architect가 "사이클 1 GREEN의 증거는 **기존 테스트가 안 깨진다**인데 diff가 커지면 증거가 흐려진다"고 못 박았다 — C안은 그 diff를 최대화한다.
2. **선례**: PRD 결정 3(범위 밖 B)이 "`resized(draggingEdge:)`의 `public` 우회 차단"을 **실사용 호출부가 0건이라 검증할 경로가 없다**는 이유로 이월했다. 같은 논리가 그대로 적용된다.
3. **C도 완전 차단이 아니다**: `ResizeLimits(canvas: Size2(width: 1, height: 1))`이 `(40, 4)`를 낸다. 얻는 것은 "어떤 캔버스에서 유도되었다"뿐이고 "**옳은** 캔버스"는 여전히 규율이다.

> ⚠️ **이 기각은 비용 판단이지 AC 제약이 아니다.** 프로덕션 doc과 이월 표에 "AC가 막았다"를 적지 않는다 — `EDITOR-5`가 코드만 읽고 잘못된 제약을 수용한 채 나온 비용을 이 저장소가 이미 냈다. **`EDITOR-11`은 이 결정을 제약 없이 재검토해야 한다.**

**접근 수준 (V-6 반영)**

- `resizeLimits(canvas:)` → **`public`**. 모듈 밖 소비자가 **확정**돼 있다(`EDITOR-11`은 이 경로 없이 착수 불가).
- 두 상수 → **`private`**. 열면 `canvas.longSide * multiple` 재기술 경로가 생긴다. `HandlePlacement`의 혼재에서 직전 단위가 뽑은 규칙은 "**소비자가 없으면 열지 마라**"이고 그것을 새 멤버에 적용한 결과다.
- **`minShortSide`가 아니라 `shortSideFloor`인 이유는 V-6** — 아래 상세 설계 doc 참조.

**`ResizeAnchorTests.swift:6-7` 처리 — 삭제**

두 `private let` 자체는 순수 함수의 인자값이라 무해하다. **문제는 line 7의 주석이 유도 규칙(`1920 × 4`)의 두 번째 기술**이라는 것이다.

> **V-8 — 축이 하나 이동한다. 기록한다.** 기존 4·5의 단언은 지금 `minSide - 0.01` / `maxSide + 0.01`로 **입력 리터럴 자체**를 기준 삼는다. 교체 후에는 좌·우변이 같은 출처가 되어 "**한계값이 40/7680이다**"라는 축을 잃고, "클램프가 받은 값을 실제로 쓴다"는 축만 남는다. **잃은 축은 AC-2가 리터럴로 받는다.** `96b3c93`("픽스처가 지워버린 두 축 복원")이 정확히 이 조작에서 난 사고다 — red-writer는 AC-2를 생략할 수 없다.

### D-2. `(0,0)` 지점에서 하한을 복원하는 방법

**후보**

| # | 방법 | 평가 |
|---|---|---|
| A | `clamped`에 `ratio: Double`(비옵셔널) | 변 드래그가 `NaN`을 넘기게 되어 **오늘 `(0,0)`을 내는 입력이 `NaN`을 낸다**(회귀) |
| B | 호출부에서 `(0,0)` 처리, 씨앗은 `(ratio, 1)` | **1회차 기각 근거는 허수아비였다(K-1).** 아래 |
| C | 클램프 전면 재작성 | 변 드래그 계약(F-4)까지 새로 정해야 한다 = 정책 결정 |
| D | **`clamped`에 `aspectIfCollapsed: Double?` + 씨앗 `(ratio, 1)`** | 선택 |

> **K-1 정정 — 1회차의 B안 기각 근거("`minShortSide * max(ratio,1)`이 하한 규칙의 두 번째 기술")는 거짓이다.** 씨앗 통찰을 B안에도 적용하면 호출부는 `if newW == 0, newH == 0 { newW = ratio; newH = 1 }` 세 줄이 되고 **하한 규칙은 여전히 `clamped` 한 곳에만 있다.** B와 D는 **결과가 완전히 동일**하다.

**선택: D (유지). 근거 교체.**

1. **응집 — B가 만드는 실제 위험.** B에서는 "`(0,0)`은 곱셈으로 빠져나올 수 없다"는 사실이 호출부에, 그것을 막는 `shortSide > 0` 조건이 `clamped`에 **갈라져** 적힌다. 그러면 "호출부가 `(0,0)`을 처리하니 `shortSide > 0`은 불필요하다"는 삭제가 자연스러워 보이고, **그 순간 변 드래그 경로가 0으로 나눈다**(원본 `size (0, h)` → `k = 40/0 = inf`). D에서는 두 사실이 같은 함수에 나란히 있다.
2. **가시성.** 두 호출이 `aspectIfCollapsed: ratio` vs `nil`로 갈라져 F-4 doc으로 가는 길이 생긴다.
3. **비용 차는 작다.** B는 3줄/시그니처 불변, D는 매개변수 1개 + 변 호출부 1줄.

**씨앗의 정규화 축은 임의다 (K-2 — 감추지 않는다).** `(ratio, 1)`의 `1`은 임의 선택이며 `(1, 1/ratio)`와 정상 범위에서 1e-14 이내로 같다. **극단 비율에서만 갈라진다** — V-2의 오버플로우가 그 갈라짐이다.

**FR-5(NaN) 축과의 분리 유지 확인**: 원본 `(0,0)`은 `ratio = NaN`이라 `clamped`에 닿기 전에 진입 가드가, 변 경로는 `nil`이 씨앗 분기를 닫는다. **분리 유지.**

### D-3. "하한 우선"(BR-1)의 구현

**선택: 블록 순서 교체(상한 → 하한).** (b)"하한 한 번 더"·(c)"단일 최종식"은 규칙을 두 번 적거나 조건을 뭉갠다. **순서가 곧 우선순위이고, 그것이 코드에서 읽히는 유일한 형태다.**

> **V-9 정정 — 1회차의 "두 블록이 둘 다 발동해야만 순서가 결과를 바꾼다"는 부정확하다.** *어느 블록이 발동하는지가 순서에 의존*하기 때문이다. 반례(실측): `(20, 5000)`은 **구 순서에서 둘 다 발동**해 `(30.72, 7680)`, **신 순서에서 하한만 발동**해 `(40, 10000)`.
>
> **올바른 진술**: "**어느 한 순서에서라도 두 블록이 모두 발동하면 결과가 갈릴 수 있다.**" 따라서 무회귀는 "각 순서에서 각각" 확인해야 한다 — **기존 7건 전부에 대해 구·신 양쪽에서 확인했고, 어느 순서에서도 발동 블록이 최대 1개다**(§산술 전개 7).

**`longSide = ratio × minShortSide` 유계 주장**: 두 블록이 모두 비율을 보존하므로 하한 발동 후 `shortSide = minShortSide`, `longSide = ratio × minShortSide`이며 드래그 거리와 무관하게 수렴한다(AC-6의 두 드래그가 증인). **그러나 정상 범위에서만 참이다** — 반례는 §보장하지 않는 것 1·2·3행.

### D-4. 비유한 방어의 위치 — **진입 가드 + 결과 유한성 가드 둘 다**

**1회차는 진입 가드만 골랐다. V-2·V-3이 그 결정을 뒤집는다.**

**결과 가드를 넣는 근거 — 이 단위가 만드는 회귀를 막는 유일한 수단이다 (V-2).**

| 입력 (`center (0,0)`, `rot 0`, `topRight`를 고정점에 정확히) | 오늘 | 씨앗만 도입 | 씨앗 + 결과 가드 |
|---|---|---|---|
| `size (1e307, 1)` (`ratio = 1e307`, **진입 가드 통과**) | size `(0,0)` · center `(-5e306, 0.5)` — **유한** | size **`(inf, 40)`** · center **`(nan, -19.5)`** | `self` — 유한 |
| `size (1, 1e307)` | 유한 | size **`(inf, inf)`** · center **`(nan, nan)`** | `self` — 유한 |

임계는 `ratio > 4.494e306` 또는 `ratio < 2.2250738585072018e-307`. **`(0,0)`의 올바른 답 `(40 × 1e307, 40)`은 `Double`로 표현 불가능하므로, 어떤 구현도 그것을 낼 수 없다 — 정직한 선택지는 후퇴뿐이고, 후퇴하려면 검출이 필요하다.**

**결과 가드가 V-3도 덮는다.** `LayerFrame(center:(500,400), size:(200,100), rotation: .nan)`은 두 진입 가드를 전부 통과하고 결과 네 필드가 `NaN`이 된다(실측). 후퇴시키면 **center·size 4/4가 유한**해진다.

**따라서 프레임 유한성 가드는 별도로 넣지 않는다 — 1회차 근거를 완전히 교체한다.**

> 1회차의 "프레임 가드는 아무것도 사지 못한다"는 **거짓**이었다. 실제 근거는 셋이다:
> ① **결과 가드가 이미 그 경로를 덮는다** — 프레임 가드는 **부분집합**을 더 이른 시점에 잡을 뿐이다.
> ② **`rotation`은 AC-7이 재는 네 필드에 없다** — 후퇴해도 `self.rotation`은 여전히 `NaN`이다.
> ③ **`HandlePlacement.init(:128-133)`이 같은 검사를 하는데 여기는 왜 안 하는가**: `init`은 **후퇴할 `self`가 없다**(무에서 배치를 만든다) → 문 앞에서 거부(`box = nil`)하는 것 외에 방법이 없다. `resized`는 `LayerFrame → LayerFrame`이라 **잘 정의된 후퇴 대상**이 있고, 사후조건이 사전조건보다 **엄격히 넓다**. 같은 코드를 인용하면서 반대 결론을 낸 1회차의 오류를 이 한 줄이 정정한다.
> ④ 비유한 `rotation`의 **라이브 도달 경로를 이 단위에서 확인하지 못했다**(`Layer`/`LayerTransform` 디코딩 경로 미추적) — "없다"가 아니라 "찾지 못했다"로 남기고 이월한다.

**진입 가드를 결과 가드로 대체하지 않는 이유**: 진입 가드만이 잡는 것이 있다 — `maxLongSide = .infinity`/`.nan`은 상한 비교가 전부 거짓이라 **유한한 쓰레기**를 낸다. 그리고 결과 가드만 두면 "어느 입력이 문제였는가"가 사라지고 `clamped` 씨앗 분기의 전제(`aspect`가 유한 양수)를 호출부가 보장한다는 구조가 무너진다.

**`EDITOR-6` 신뢰 원장 HIGH 항목(`fitScale` 오버플로우)과의 관계 — 다른 축. 앞당기지 않는다.**

| | EDITOR-6 이월 | 이 단위 |
|---|---|---|
| 대상 | `fitScale`의 나눗셈 오버플로우 | `resized`의 인자와 결과 |
| 좌표계 | 논리 → **화면** | **논리** |
| 소비자 | `HandlePlacement`, SwiftUI `.position()` | 리사이즈 계산 |

배선 시 인자는 `surface.toLogical(…)`에서 오는데 `toLogical`은 `guard s > 0`이 있어 `scale`이 `NaN`이면 `center`를, `Infinity`면 유한값을 낸다(`CanvasSurface.swift:97-104`) — **그 이월 항목이 이 단위의 입력으로 새지 않는다.**

**사용자에게 어떻게 보이는가**: 그 드래그가 무시되고 레이어가 손대기 전 자리에 그대로 멈춘다.

### D-5. AC-1·AC-5는 특성화다 — 그리고 보정 블록이 무엇을 소거하는가

`toWorld(p) = center + R(p)`, `R` 선형, `Corner.opposite.sign == −Corner.sign`(네 케이스 전수, `LayerFrame.swift:7-23`).

```
nc_world = self.center + R(anchorLocal + cornerSign × new/2)
moved    = nc_world + R(anchorSign × new/2) = nc_world − R(cornerSign × new/2)
         = self.center + R(anchorLocal) = anchorWorld            ← 보정항은 언제나 0
center_final = nc_world + (anchorWorld − moved) = anchorWorld − R(anchorSign × new/2)
```

**두 가지가 동시에 참이다.**
① 보정항은 항상 정확히 0이다(오케스트레이터 무작위 300회 실측, 최대 편차 **1.205e-11**).
② **`center_final` 식에서 `nc_world`가 완전히 소거된다** — 즉 `newCenterLocal`을 **어떻게 계산하든 결과가 같다.**

> **V-1 — 1회차의 "`corner.sign` → 드래그 방향 부호 변이를 AC-5가 죽인다"는 거짓이다.** 그 계산은 보정 블록을 빼고 한 것이다. 보정 포함 실측: AC-5·기존 1·임의 드래그 3건 모두 **차이 정확히 `0.0`**. **등가 변이다.**
>
> **대체 사실(검증됨)**: `Corner.topRight.sign`을 **열거형 정의에서** `(1,−1) → (1,1)`로 바꾸면 AC-5의 `topRight`가 `(500, 450)`이 되어 죽는다. 강도는 "**이 파일 안에서 유일**"이다 — 모듈 전체로는 `HandlePlacementTests.swift:135`도 같은 변이를 죽인다.

**"고정점 유지" 단언이 재는 축은 하나뿐이다.** 위 항등에 의해 `result.corner(corner.opposite) == self.corner(corner.opposite)`가 **드래그 지점·회전·크기·클램프와 무관하게** 성립한다. 따라서 그 단언은 `corner.opposite`가 **가리키는 코너를 바꾸지 않는 모든 변이**(=`toLocal`·`newCenterLocal`·`clamped`의 전 변이)에 대해 공허하다. 공허하지 않은 유일한 축은 `opposite` 자신이며, **AC-1·4·5는 리터럴 대조라 그 축을 잡는다** — 검증: `topRight.opposite → .bottomRight` 변이에서 AC-1의 `size (500,250)`은 통과하고 고정점만 `(450, 0)`으로 죽는다.

        // `sin(-0) = -0.0`이라 `NaN × -0.0 = NaN`이고, 그 뒤로는 비교가 전부 거짓이라
        // **클램프가 통째로 통과한다**(Swift `max(x,y)`는 `y >= x ? y : x`).
        // **후퇴 대상은 `self`다** — 사용자에게는 "그 드래그가 무시된다"로 보인다.
        guard worldPoint.x.isFinite, worldPoint.y.isFinite,
              minShortSide.isFinite, maxLongSide.isFinite else { return self }

        // 비율 유지: 원본 종횡비에 맞춰 더 큰 쪽을 기준으로 삼는다.
        // 비율이 유한한 양수가 아니면 이 함수가 세우는 모든 것이 무너진다 —
        // `newH = newW / ratio`도, 붕괴 복원의 씨앗도. 원본 크기 `(0,0)`이 여기로 온다.
        // PRD 산출 근거 §1이 그 경로를 `(0,0)` 붕괴 결함과 **별개 문제**로 분리했고
        // 이 가드가 분리를 유지한다.
        //
        // **이 두 조건에는 이 단위의 증인이 없다** — AC-7은 `worldPoint`·하한·상한만 잰다.
        // 지워도 아래 결과 가드가 같은 후퇴를 하므로 **동작은 같다**(확인: `size (0,100)`은
        // `newH = rawW/0 = inf` → `k = 0` → `(0, NaN)`). 남기는 이유는 씨앗 분기의 전제를
        // 호출부가 보장하는 구조를 유지하기 위함이다.
        let ratio = size.width / size.height
        guard ratio.isFinite, ratio > 0 else { return self }

### 3. `clamped` — 순서 교체 + 붕괴 복원

```swift
    /// 짧은 변 하한과 긴 변 상한을 **입력 비율을 보존한 채** 적용한다.
    ///
    /// **상한을 먼저, 하한을 나중에 적용한다 (BR-1). 순서가 곧 우선순위다.** 반대로 두면
    /// 비율이 `상한/하한`(9:16에서 192, 4:5에서 135)을 넘는 가는 레이어에서 짧은 변이 하한
    /// 아래로 샌다: `8000×40`을 제자리로 다시 끌면 상한이 `k = 0.96`을 곱해 **38.4**를 만들고
    /// 하한 블록은 이미 지나간 뒤다. 상한을 넘긴 채 두는 것이 의도된 손해다 — 상한을 넘은
    /// 레이어는 여전히 잡히지만, 하한 아래 레이어는 핸들이 겹쳐 다시 잡을 수 없다.
    ///
    /// **어느 블록이 발동하는지 자체가 순서에 의존한다.** `(20, 5000)`은 구 순서에서 둘 다
    /// 발동해 `(30.72, 7680)`, 신 순서에서 하한만 발동해 `(40, 10000)`이다. 따라서
    /// "둘 다 발동할 때만 순서가 문제"라는 요약은 틀렸다 — **어느 한 순서에서라도 둘 다
    /// 발동하면 결과가 갈릴 수 있다.**
    ///
    /// 하한이 발동하면 결과는 **`(비율 × 하한, 하한)`으로 유일하게 결정되고 드래그 거리와
    /// 무관하게 수렴한다** — 두 블록이 전부 비율을 보존하기 때문이다. **단 정상 범위에서만
    /// 참이다**: `shortSide < 2.2250738585072018e-307`이면 `k = 하한/shortSide`가 `Infinity`로
    /// 오버플로우한다(`(2e-307, 1e-307)` → `(inf, inf)`, **정규수만으로 발생**).
    ///
    /// **`aspectIfCollapsed`는 코너 드래그 전용이다.** `(0,0)`에는 어떤 배수를 곱해도
    /// `(0,0)`이라 붕괴 뒤에는 여기서 비율을 되짚을 방법이 없다. 코너 드래그는 원본
    /// 종횡비를 이미 갖고 있으므로 씨앗으로 넘긴다. **씨앗은 `(비율, 1)`이지
    /// `(하한 × 비율, 하한)`이 아니다** — 씨앗이 크기까지 정하면 하한 규칙이 이 함수 안에
    /// 두 번 적히고, 그러면 한쪽만 바뀌는 날이 온다.
    /// ⚠️ **그러나 `1`이라는 정규화 축은 임의 선택이다.** `(1, 1/비율)`과 정상 범위에서
    /// 1e-14 이내로 같고 **극단 비율에서만 갈라진다** — 그 갈라짐이 호출부의 결과 유한성
    /// 가드가 막는 오버플로우다. "비율만 나른다"로 끝내면 이 사실이 숨는다.
    ///
    /// **변 드래그는 `nil`을 넘긴다.** 한 축만 바꾸는 계약이라 되돌릴 "원본 비율"이라는
    /// 개념 자체가 없고, 그 경로가 `(0,0)`에 닿으려면 원본 크기가 이미 `(0,0)`이어야 하는데
    /// 그때 비율은 `0/0 = NaN`이다. `Double`을 강제로 받게 하면 그 `NaN`이 씨앗이 되어
    /// **오늘 `(0,0)`을 내는 입력이 `NaN`을 낸다.** 옵셔널이 그 경로를 타입으로 닫는다.
    ///
    /// ⚠️ **이 함수는 코너·변 드래그가 공유하는데 양축을 함께 곱한다.** 변 드래그의 계약은
    /// "한 축만 바꾼다"인데, 클램프가 발동하면 **불변이어야 할 축까지 바뀐다**:
    /// `50×100` 프레임의 `.right` 변을 로컬 x=0까지 끌면 `(25, 100)`이 하한에 걸려
    /// **`(40, 160)`** 이 된다(높이 100→160). 반대쪽 변 고정은 유지된다.
    /// **`EDITOR-7`은 이 결함을 고치지 않았다 — 그리고 넓히지도 않았다**: 순서 교체는
    /// **발동 집합을 바꾸지 않고**(어느 순서에서도 "발동 없음"의 조건이 `min ≥ 하한 ∧
    /// max ≤ 상한`으로 같다 — 무작위 20,000회 대조 불일치 0건) 발동 시 **이탈량만**
    /// 케이스마다 크거나 작아진다(`(100,100000)`은 신 쪽이 원본에 가깝고 `(20,8000)`은
    /// 구 쪽이 가깝다). 고치려면 "변 드래그에서 하한·상한이 무엇을 뜻하는가"를 새로 정해야
    /// 한다. **`EDITOR-11` 배선 착수 전에 결정할 것.**
    private static func clamped(width: Double, height: Double,
                                aspectIfCollapsed: Double?,
                                minShortSide: Double,
                                maxLongSide: Double) -> (Double, Double) {
        var w = width
        var h = height

        // 붕괴 복원 — 곱셈으로는 빠져나올 수 없는 유일한 지점.
        if w == 0, h == 0, let aspect = aspectIfCollapsed {
            w = aspect
            h = 1
        }

        // 상한 먼저.
        let longSide = max(w, h)
        if longSide > maxLongSide {
            let k = maxLongSide / longSide
            w *= k
            h *= k
        }

        // 하한 나중 — BR-1: 하한이 상한을 이긴다.
        // `shortSide > 0`은 0으로 나누는 것을 막는다. **한 축만 정확히 0인 입력**(원본 크기가
        // `(0, h)`인 변 드래그)은 여기서 여전히 통과한다. 코너 드래그에서 그 상태는
        // **정상 범위에서는** 도달할 수 없다(`newH = newW / 비율`) — 다만 언더플로우로는
        // 도달한다(`비율 = 1e300`, `newW = 1e-30` → `newH = 1e-330` → `0`).
        let shortSide = min(w, h)
        if shortSide < minShortSide, shortSide > 0 {
            let k = minShortSide / shortSide
            w *= k
            h *= k
        }
        return (w, h)
    }
```

`aspect`가 유한·양수라는 전제는 **파일 내 호출부 2개 전수 확인**으로 성립한다 — 비-`nil` 호출부는 `resized(draggingCorner:)` 하나이고 그 진입 가드가 보장한다.

| 5 | **한 축만 정확히 0이면 하한이 적용되지 않는다** | `shortSide > 0` 때문. 변 드래그가 원본 `(0, h)`로 도달. `EDITOR-6` 원장 ASSUMPTION(`:13`)이 경고한 전제이며 이 단위는 **코너 경로만** 닫았다 |
| 6 | **극단 비율 + 먼 드래그의 곱셈 오버플로우** | `ratio = 1e300`은 유한·양수라 진입 가드를 통과하는데 `rawH × ratio = ∞` → `k = 0` → `∞ × 0 = NaN`. **결과 가드가 후퇴로 막는다** |
| 7 | **결과 유한성 가드에 증인이 하나뿐이다** | `극단비율붕괴프레임()` 특성화 1건이 유일하다 — red-writer 필수 |
| 8 | **진입 가드 `ratio` 2조건에 증인이 0건이다** | 원본 `size (0,0)`·`(200,0)` Given이 필요해 AC 밖. 지워도 결과 가드가 같은 후퇴를 하므로 **동작은 같다** — 그래서 관측 불가능하다. 이월 |
| 9 | **`resized(draggingEdge:)`에는 FR-5 방어가 전혀 없다** | 이 단위 AC 밖 — 이월 |
| 10 | **`newCenterLocal` 6줄과 보정 4줄 중 한쪽은 관측 불가능한 죽은 코드다** | 어느 쪽을 지워도 어떤 테스트도 차이를 관측하지 못한다(`+=`→`-=`조차 등가). **이 단위는 정리하지 않는다** — 정리는 안전망 없는 변경이 된다. 이월 |
| 11 | **"고정점 유지" 단언은 `opposite`를 제외한 전 변이에 대해 공허하다** | 자기참조 형태인 **기존 1·2**가 대표 사례다. **AC-1·4·5는 리터럴 대조라 `opposite` 축을 잡는다**(검증: `topRight.opposite → .bottomRight`에서 AC-1 고정점이 `(450, 0)`으로 죽는다) |
| 12 | **하한 값의 다양성 증인이 0점이다** | 기존·신규 테스트가 **예외 없이 하한에 40만 넘긴다.** 상한은 AC-2가 5400/7680을 갈라내고 AC-3이 두 값으로 다른 결과를 관측해 **2점**이다. `shortSideFloor` 개명이 조용한 결합을 컴파일 단계에서 막지만 "하한이 정말 매개변수에서 온다"는 축은 여전히 무증인 — 이월 |
| 13 | **호출부가 `resizeLimits`를 쓴다는 것** | **규율이다.** 구조적 차단은 C안뿐이며 **AC가 막은 것이 아니라 이 단위가 비용으로 미룬 것이다.** `EDITOR-11`이 제약 없이 재검토할 것 |
| 14 | **비유한 `rotation`의 라이브 도달 경로** | **찾지 못했다.** 결과 가드가 후퇴로 덮지만 `self.rotation`은 여전히 비유한이다 — 이월 |
| 15 | **0폭/0높이 레이어는 코너 드래그로 되살아나지 않는다** | `size (0, 100)`은 `ratio = 0`이라 진입 가드가 잡고, 가드를 지워도 결과가 `(0, NaN)`이 되어 결과 가드가 같은 후퇴를 한다 — **가드 탓이 아니라 이 단위에 되살릴 수단이 없다.** **사용자 확정 3으로 수용·이월** |

### F-4 판정 — **② 이번에 고치지 않는다**

> **K-7 정정.** 1회차 근거 "① AC가 없다"는 §9(순서 교체가 변 드래그 결과를 바꾼다)와 같은 단위에 공존해 모순이었다. 정합적 서술은 하나다:
>
> **이 단위는 BR-1이 강제하는 변경만 수용하고, 강제하지 않는 변경은 하지 않는다.**

- 순서 교체는 BR-1("짧은 변은 **어떤 입력에서도** 40px 미만으로 내려가지 않는다")이 **강제**한다 — 변 드래그도 그 문면 안이다.
- 축별 클램프(F-4 수정)는 BR-1이 강제하지 않으며 **새 정책**을 요구한다. 그 결정은 설계의 권한 밖이다.

**"결함을 넓혀 놓고 안 고친다"는 비난은 성립하지 않는다 (V-9).** F-4의 **발동 집합은 불변**이고, 발동 시 불변 축의 **이탈량만** 케이스에 따라 커지거나 작아진다.

| 축 | 오늘 | 이 설계 |
|---|---|---|
| 문서화 | **0줄** | `clamped` doc의 ⚠️ 절에 재현 입력·실측값·발동 집합 불변 증명 |
| 가시성 | 두 호출이 똑같아 보인다 | `ratio` vs `nil`로 **눈에 띄게 갈라진다** |
| 증인 | **0건** | **1건** — `변드래그순서프레임()` 특성화가 `(30,100000)` `.right` → `(40, 40000)`을 고정한다. **불변 축 100000 → 40000이 곧 F-4다** |

### 1. AC-1 — 회전 π/2 (특성화)

`frame(center (500,400), size (200,100), rot π/2)`, `topRight → (700,300)`. `cos(π/2) ≈ 6.12e-17`(0으로 표기, 오차 ≪ 0.01), `sin(π/2) = 1`.

| 단계 | 전개 | 값 |
|---|---|---|
| `anchorLocal` | `(-1×100, +1×50)` | `(-100, 50)` |
| `anchorWorld` | `(500 + (-100)(0) − 50(1), 400 + (-100)(1) + 50(0))` | **`(450, 300)`** |
| `dragLocal` | `c=cos(-π/2)=0, s=sin(-π/2)=-1`; `x = 200(0) − (−100)(−1) = −100`, `y = 200(−1) + (−100)(0) = −200` | `(-100, -200)` |
| `rawW, rawH` | `\|−100+100\| = 0`, `\|−200−50\| = 250` | `0, 250` |
| `newW, newH` | `max(0, 250×2) = 500`, `250` | **`(500, 250)`** |
| clamp | 양쪽 스킵 (**두 순서 동일**) | 무변경 |
| `newCenterLocal` | `(-100 + 250, 50 − 125)` | `(150, -75)` |
| `result.center` | `toWorld((150,-75))` = `(500 + 150(0) − (−75)(1), 400 + 150(1) + (−75)(0))` | **`(575, 550)`** |
| `result.corner(bottomLeft)` | `(575 + (−250)(0) − 125(1), 550 + (−250)(1) + 125(0))` | **`(450, 300)`** = anchorWorld |

보정항 = 0. **AC-1의 Then 두 값 모두 일치.**

## red-writer 필수 인계

1. **AC-1과 AC-5는 처음부터 GREEN이다.** 사이클 0은 프로덕션 0줄이며 두 건 다 통과해야 한다. 하나라도 빨강이면 전개가 틀린 것이니 구현을 고치지 말고 보고하라.
2. **사이클 1은 컴파일 RED이며 동작 RED가 0건이다.** RED의 증거는 실패 개수가 아니라 **진단 텍스트**(`error: type 'LayerFrame' has no member 'resizeLimits'` + 파일:행)다. 기존 123건은 "실행 안 됨"이 되므로 **무영향은 GREEN 시점 개수 127로만 증명된다.**
3. **AC-3은 컴파일 RED, 값은 특성화다.** 심볼이 생기는 순간 `(5400,2700)`·`(7680,3840)`이 즉시 통과한다. 고유 가치는 기존 5의 **부등식**이 못 잡는 과잉 클램프를 정확값으로 잡는 것.
4. **AC-1의 `size == (500, 250)` 절을 생략하지 마라.** `toLocal` 회전 부호 반전과 `abs()` 제거 두 변이의 **단독 방어선**이다.
5. **AC-4의 단언은 `size.width ≈ 80` · `size.height ≈ 40`이다.** `shortSide 40 ∧ longSide 80` 형태는 **씨앗 축 뒤바꿈 변이를 통과시킨다**(실측 `(40,80)`).
6. **AC-4 픽스처의 회전은 반드시 0이다.** 회전이 붙으면 `toLocal`이 ~1e-14를 남겨 `w == 0, h == 0` 분기에 도달하지 못하고, 곱셈 경로가 우연히 같은 값을 내 **씨앗을 관측하지 못한다.** 픽스처 주석에 명시하라.
7. **AC-6은 `isClose` 필수, `==` 금지.** 실측 `8000.000000000001` / `7999.999999999999`. **두 드래그를 모두** 넣어야 수렴이 관측된다. **순서 교체 변이의 단독 방어선**이다.
