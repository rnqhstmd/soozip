# PRD: Phase 1 — 데이터 레이어 (모음집·캔버스 영속성 + 리포지토리)

> 확정: 2026-08-10 / 파이프라인: gx-tdd (mode: all, profile: standard)
> 설계 SSOT: `docs/specs/2026-08-10-moumzip-mvp-design-v4.md` §4 · §6.7~6.9 · §7 · §11.1
> 로드맵: `docs/plans/2026-08-10-00-roadmap.md` Phase 1

## 배경

soozip은 흰 캔버스에 사진·텍스트·도형을 자유 배치해 만든 "캔버스"를 사용자가 만든 "모음집"에 담는 iOS 앱이다. 지금까지는 CloudKit 제약을 검증하기 위한 프로브 모델(`ProbeCollection`/`ProbeCanvas`, `Soozip/Spikes/S2_CloudKitProbe.swift`)만 존재하며, 정식 데이터 계층은 아직 없다.

Phase 1은 이 앱의 영속성 계층 — 모음집·캔버스·사진 3종 모델과 그 위의 리포지토리 — 을 UI 없이 완성하는 단계다. 에디터(Phase 3~5)와 모음집 화면(Phase 6)이 전부 이 계층 위에 얹히므로, 여기서 확정한 모델 구조는 CloudKit 첫 심사 이후 additive-only로만 바뀔 수 있다 — 지금 잘못 정하면 이후 모든 확장이 제약을 받는다.

**현재 제품 상태:** 정식 모델·리포지토리 없음. 프로브 모델만 시뮬레이터에서 CloudKit 제약(기본값/optional, unique 없음, 관계 양방향 optional) 검증을 마쳤다.

## 목표

- 모음집·캔버스·사진 데이터가 CloudKit 동기화 제약을 어기지 않고 저장·조회된다.
- "표지가 다른 모음집의 캔버스를 계속 가리키는" 것과 같은 데이터 정합성 사고가 저장/삭제/이동 어느 시점에도 발생하지 않는다.
- 두 기기에서 동시에 모음집 순서를 바꿔도 정렬 결과가 결정적이다.
- 모음집을 지우면 그 안의 캔버스와 사진이 예외 없이 함께 지워진다.
- 이번 달 활동, 연속 기록 등 "내 정보" 통계 화면(Phase 8)이 그대로 갖다 쓸 수 있는 쿼리가 준비된다.

## 요구사항

### 기능 요구사항

- [Must] FR-1: `Collection` 모델을 정의한다 — 식별자, 이름, 생성일, 정렬 순서(`sortIndex`), 대표 캔버스 식별자(`coverCanvasID`), 소속 캔버스 목록.
- [Must] FR-2: `Canvas` 모델을 정의한다 — 식별자, 비율(4:5/9:16), 제목, 생성일(사용자 지정 기록 날짜), 최종 수정일, 레이아웃 데이터, 소속 사진 목록, 렌더링된 미리보기 이미지(캐시), 소속 모음집.
- [Must] FR-3: `CanvasPhoto` 모델을 정의한다 — 식별자, 사진 원본 데이터, 소속 캔버스.
- [Must] FR-4: 모음집을 생성하면 정렬 순서(`sortIndex`)에 **기존 모음집들의 최댓값 + 1**이 부여된다(첫 모음집은 0). 재배치 없이도 "생성 순서" 정렬이 별도 계산 없이 성립한다.
- [Must] FR-5: 모음집 목록을 정렬 순서 기준으로 조회할 수 있다 — 동일 순서 값이 있으면 생성일 오름차순으로 확정한다.
- [Must] FR-6: 모음집 내 캔버스 목록을 최신순 또는 오래된순으로 조회할 수 있다.
- [Must] FR-7: 캔버스를 저장(신규 생성 또는 갱신)하면, 소속 모음집에 대표 캔버스가 지정되어 있지 않은 경우에 한해 이 캔버스가 대표로 지정된다.
- [Must] FR-8: 캔버스를 삭제하면 **그 캔버스에 속한 사진들**도 함께 삭제되고, 삭제된 캔버스가 대표였다면 대표 지정이 비워지고 남은 캔버스 중 가장 최근 캔버스로 자동 승계된다.
- [Must] FR-9: 캔버스를 다른 모음집으로 이동하면 원래 모음집과 목적지 모음집 양쪽의 대표 캔버스가 각각 재계산된다.
- [Must] FR-10: 모음집을 삭제하면 소속된 모든 캔버스와 그 캔버스들의 사진이 함께 삭제된다.
- [Must] FR-11: 대표 캔버스 식별자가 존재하지 않는 캔버스를 가리키고 있으면(다른 기기에서 삭제된 경우 포함) 빈 값으로 취급해 가장 최근 캔버스로 폴백한다.
- [Must] FR-12: 통계 쿼리 5종을 제공한다 — 모음집 수, 총 캔버스 수, 이번 달 생성된 캔버스 수, 가장 많이 담은 모음집(이름+캔버스 수), 연속 기록 일수.
- [Must] FR-13: iCloud 계정 상태가 미로그인이거나 저장 시 용량 초과 신호가 발생하면, **두 신호 중 하나라도 해당하면 하나의 로컬 모드 판정 결과로 통합**해 반환한다.

### 비즈니스 규칙

- [Must] BR-1: 모음집 이름은 1~20자(이모지 1자 = 1자), 캔버스 제목은 0~40자다. 중복 이름은 허용한다.
- [Must] BR-2: 캔버스 제목이 비어 있으면 목록 표시용으로는 날짜만 노출한다(리포지토리는 원본 빈 문자열을 그대로 반환하고, 날짜 포맷팅은 상위 계층 책임으로 둔다).
- [Must] BR-3: 캔버스 기록 날짜는 미래 날짜도 허용한다 — 리포지토리가 미래 날짜를 거부하거나 보정하지 않는다.
- [Must] BR-4: 캔버스가 0장인 모음집은 대표 캔버스 계산을 수행하지 않는다(대표 식별자는 빈 문자열로 유지).
- [Must] BR-5: 사진 복제는 새 `CanvasPhoto`를 만들지 않는다 — 여러 레이어가 같은 사진 데이터를 공유하는 것은 상위 계층(레이아웃) 책임이며, 리포지토리는 이 공유 관계를 깨지 않는다(중복 삭제 금지).
- [Must] BR-6: 대표 캔버스 재계산에서 "가장 최근 캔버스"는 생성일(기록 날짜, `createdAt`) 기준 최신값이다.
- [Must] BR-7: 모음집 이름(1~20자)과 캔버스 제목(0~40자) 길이 제약은 **리포지토리 계층이 강제**하며, 범위를 벗어나면 생성·저장을 거부한다.
- [Must] BR-8: "가장 많이 담은 모음집" 통계가 동률이면 **가장 먼저 생성된(`createdAt` 오름차순) 모음집**을 반환한다.
- [Must] BR-9: 연속 기록은 기준 시각 `now`를 받아 다음 순서로 계산한다.
  1. **`now`의 오늘보다 미래인 기록 날짜는 계산에서 제외한다.** BR-3이 미래 날짜를 허용하므로, 제외하지 않으면 잘못 입력한 캔버스 1건이 스트릭 전체를 파괴한다.
  2. 남은 저장일 중 가장 최근이 **오늘 또는 어제**이면 거기서 하루씩 거슬러 올라가며 연속 일수를 센다.
  3. 가장 최근 저장일이 그보다 오래됐으면 **0**이다.
  - **오늘 아직 저장하지 않았다는 이유만으로 0이 되지는 않는다**(유예 1일). 이것이 이 규칙이 지키려는 핵심이다.

### 품질 기대

- [Must] QE-1: 모델 3종 모두 CloudKit 제약 체크리스트 5항(기본값/optional, unique 미사용, 관계 양방향 optional, 배열 속성 없음, 스키마 동결 대상)을 어기지 않는다.
- [Should] QE-2: 표지가 잘못된 캔버스를 가리키는 상황(다른 모음집 캔버스를 계속 가리킴)이 저장/삭제/이동 어느 경로로도 재현되지 않는다.

## 사용자 시나리오

이 계층은 UI가 없으므로 시나리오는 리포지토리 API 호출과 그 결과 관점으로 서술한다.

**정상 흐름 — 모음집 생성 순서**
모음집이 하나도 없는 상태에서 A, B, C를 순서대로 만들면, 각각 sortIndex 0, 1, 2를 받는다. 재배치를 한 번도 하지 않아도 정렬 조회 결과는 생성한 순서 그대로다.

**정상 흐름 — 표지 재계산 (저장 시점)**
모음집 A에 캔버스가 없는 상태에서 캔버스를 새로 저장하면, 그 캔버스가 A의 대표로 지정된다. 이후 두 번째 캔버스를 저장해도 대표는 바뀌지 않는다(이미 지정돼 있으므로).

**정상 흐름 — 표지 재계산 (삭제 시점)**
대표로 지정된 캔버스를 삭제하면, 모음집의 대표 지정이 비워지고 남은 캔버스 중 가장 최근 것으로 자동 승계된다. 대표가 아닌 캔버스를 삭제하면 대표 지정은 그대로다.

**정상 흐름 — 표지 재계산 (모음집 이동 시점)**
모음집 A의 대표 캔버스를 모음집 B로 이동하면, A는 대표를 잃고 A에 남은 캔버스 중 최신 것으로 승계하며(없으면 빈 값), B가 비어 있었다면 이동한 캔버스가 B의 새 대표가 된다.

**예외 흐름 — sortIndex 충돌**
두 기기가 동시에 모음집 순서를 바꿔 두 모음집의 `sortIndex`가 같은 값이 되면, 정렬 조회 시 생성일이 이른 쪽이 앞선다.

**예외 흐름 — 대표 캔버스 유실**
대표로 지정된 캔버스가 다른 기기에서 삭제되어 이제 존재하지 않는 식별자를 가리키게 되면, 조회 시 빈 값으로 간주해 최근 캔버스로 폴백한다.

**예외 흐름 — cascade 삭제**
캔버스 3장을 가진 모음집을 삭제하면, 그 3개 캔버스와 각 캔버스에 속한 모든 사진이 함께 삭제되고 데이터베이스에 고아 레코드가 남지 않는다.

**예외 흐름 — 통계 동률·공백**
캔버스 수가 같은 모음집이 둘 이상이면 먼저 생성된 쪽이 "가장 많이 담은 모음집"으로 보고된다. 오늘 아직 캔버스를 저장하지 않았어도, 어제까지 이어진 연속 기록은 0으로 끊기지 않고 그대로 보고된다.

**엣지 케이스 — 이동으로 모음집이 빈 상태가 됨**
모음집 A에 캔버스가 1장뿐이고 그것이 대표일 때 B로 이동하면, A는 캔버스가 0장이 되어 대표 계산 자체를 하지 않는다(BR-4).

## 영향 범위

- **영향받는 기존 기능:** `Soozip/Spikes/S2_CloudKitProbe.swift`의 `ProbeCollection`/`ProbeCanvas`는 이번 Phase의 정식 모델로 대체되며 이후 삭제 대상이다(로드맵에 이미 명시).
- **기존 사용자 영향:** 없음 — 아직 출시 전이며 실사용 데이터가 없다.
- **하위 호환성:** 이번에 확정하는 모델 구조가 CloudKit 첫 심사 이후에는 additive-only 제약을 받으므로, 필드 이름·타입·관계 방향을 이번 범위에서 신중히 확정해야 한다.

## 수용 기준

### 모델 · CloudKit 제약

- AC-1: Given `Collection`·`Canvas`·`CanvasPhoto` 3개 모델이 정의된 상태에서, When 각 모델의 전 속성을 검사하면, Then 모든 속성이 기본값을 갖거나 optional이다. → [QE-1]
- AC-2: Given 3개 모델 정의를 검사할 때, When `@Attribute(.unique)` 사용 여부를 확인하면, Then 어떤 속성에도 unique 제약이 없다. → [QE-1]
- AC-3: Given `Canvas.collection`과 `Collection.canvases`, `Canvas.photos`와 `CanvasPhoto.canvas` 관계를 검사할 때, When 각 관계의 양방향성을 확인하면, Then 양쪽 모두 optional 관계로 선언되어 있다. → [QE-1]
- AC-4: Given 3개 모델 정의를 검사할 때, When 배열 타입 속성을 확인하면, Then `sortIndex`는 `Int`, `coverCanvasID`는 `String`으로 선언되어 있고 관계가 아닌 배열 속성(예: 문자열 배열)은 존재하지 않는다. → [QE-1]
- AC-5: Given 빈 `ModelContainer`가 초기화된 상태에서, When `Collection()`, `Canvas()`, `CanvasPhoto()`를 각각 인자 없이 생성하면, Then 컴파일 및 실행이 성공한다(암묵적 이니셜라이저에 의존하지 않고 명시적 `init()`을 가진다). → [QE-1]

### 표지 재계산 — 저장 시점

- AC-6: Given 캔버스가 0장인 모음집 A가 존재할 때, When 새 캔버스 C1을 A에 저장하면, Then A의 `coverCanvasID`가 C1의 식별자로 설정된다. → [FR-7, BR-4]
- AC-7: Given 모음집 A의 `coverCanvasID`가 이미 C1로 설정된 상태에서, When 새 캔버스 C2를 A에 저장하면, Then A의 `coverCanvasID`는 여전히 C1이다(C2로 바뀌지 않는다). → [FR-7]

### 표지 재계산 — 삭제 시점

- AC-8: Given 모음집 A가 캔버스 C1(대표), C2를 갖고 C1이 C2보다 최근에 생성됐을 때, When C1을 삭제하면, Then A의 `coverCanvasID`가 C2의 식별자로 갱신된다. → [FR-8, BR-6]
- AC-9: Given 모음집 A가 대표 캔버스 C1과 비대표 캔버스 C2를 가질 때, When C2를 삭제하면, Then A의 `coverCanvasID`는 변경 없이 C1을 유지한다. → [FR-8]
- AC-10: Given 모음집 A가 대표 캔버스 C1 하나만 가질 때, When C1을 삭제하면, Then A의 `coverCanvasID`가 빈 문자열이 된다. → [FR-8, BR-4]

### 표지 재계산 — 모음집 이동 시점

- AC-11: Given 모음집 A(대표 C1, 그 외 C2 보유, C2가 C1보다 오래됨)와 빈 모음집 B가 있을 때, When C1을 A에서 B로 이동하면, Then A의 `coverCanvasID`는 C2로 갱신되고 B의 `coverCanvasID`는 C1로 설정된다. → [FR-9]
- AC-12: Given 모음집 A가 대표 캔버스 C4와 비대표 캔버스 C3을 보유하고 모음집 B는 이미 대표 C9가 지정돼 있을 때, When C3을 A에서 B로 이동하면, Then A의 `coverCanvasID`는 C4를 그대로 유지하고 B의 `coverCanvasID`도 C9를 그대로 유지한다. → [FR-9]
  - *(개정: 원안은 A가 비대표 C3 한 장만 갖는다고 했으나, FR-7상 저장 시점에 C3이 표지가 됐을 것이므로 그 상태가 성립하지 않는다. A에 표지 C4를 두어 "비대표 이동은 양쪽 표지를 건드리지 않는다"는 의도를 모순 없이 검증한다.)*
- AC-13: Given 모음집 A가 대표 캔버스 C1 하나만 보유할 때, When C1을 A에서 B(빈 모음집)로 이동하면, Then A의 `coverCanvasID`는 빈 문자열이 되고 A의 캔버스 수는 0이 되어 이후 표지 계산 대상에서 제외된다. → [FR-9, BR-4]

### sortIndex 부여·타이브레이크

- AC-14: Given 모음집이 하나도 없는 상태에서, When 모음집 A, B, C를 순서대로 생성하면, Then 각 모음집의 `sortIndex`는 A=0, B=1, C=2이고, `sortIndex` 오름차순으로 조회한 목록도 [A, B, C] 순서와 동일하다. → [FR-4, FR-5]
- AC-15: Given 두 모음집 A, B가 동일한 `sortIndex` 값을 갖고 A가 B보다 먼저 생성됐을 때, When 정렬 순서로 목록을 조회하면, Then A가 B보다 앞에 나온다. → [FR-5]

### cascade 삭제

- AC-16: Given 모음집 A가 캔버스 2개(각각 사진 2장씩 보유)를 가질 때, When A를 삭제하면, Then 데이터 저장소에서 A에 속했던 캔버스 2개와 사진 4개가 모두 조회되지 않는다. → [FR-10]
- AC-17: Given 캔버스 C1이 사진 3장을 가질 때, When C1을 삭제하면, Then C1에 속했던 사진 3장이 모두 조회되지 않는다. → [FR-8]

### 대표 캔버스 폴백

- AC-18: Given 모음집 A의 `coverCanvasID`가 이미 삭제되어 존재하지 않는 캔버스 식별자를 가리킬 때, When A의 표지 캔버스를 조회하면, Then 빈 값으로 간주되어 A에 남은 캔버스 중 가장 최근 것이 반환된다. → [FR-11]

### 통계 쿼리

- AC-19: Given 모음집이 3개 존재할 때, When 모음집 수를 조회하면, Then 3이 반환된다. → [FR-12]
- AC-20: Given 캔버스가 총 5개 존재할 때, When 총 캔버스 수를 조회하면, Then 5가 반환된다. → [FR-12]
- AC-21: Given 이번 달 생성일을 가진 캔버스 2개와 지난달 생성일을 가진 캔버스 1개가 존재할 때, When 이번 달 생성 캔버스 수를 조회하면, Then 2가 반환된다. → [FR-12]
- AC-22: Given 모음집 A(캔버스 3개)와 모음집 B(캔버스 1개)가 존재할 때, When 가장 많이 담은 모음집을 조회하면, Then A의 이름과 캔버스 수 3이 반환된다. → [FR-12]
- AC-23: Given 모음집 A와 B가 각각 캔버스 2개씩(동수)을 가지고 A가 B보다 먼저 생성됐을 때, When 가장 많이 담은 모음집을 조회하면, Then A의 이름과 캔버스 수 2가 반환된다. → [FR-12, BR-8]
- AC-24: Given 오늘·어제·그저께 각각 캔버스를 1장 이상 저장했고 3일 전에는 저장 기록이 없을 때, When 연속 기록 일수를 조회하면, Then 3이 반환된다. → [FR-12]
- AC-25: Given 어제·그저께 캔버스를 1장 이상 저장했고 오늘은 아직 저장하지 않았을 때, When 기준 시각을 오늘로 하여 연속 기록 일수를 조회하면, Then 2가 반환된다(0이 아니다). → [FR-12, BR-9]
- AC-25a: Given 오늘·어제·그저께 캔버스를 저장했고 **기록 날짜가 2년 뒤인 캔버스가 1건 섞여 있을** 때, When 기준 시각을 오늘로 하여 연속 기록 일수를 조회하면, Then 3이 반환된다(미래 캔버스가 계산을 오염시키지 않는다). → [FR-12, BR-9]
- AC-25b: Given 가장 최근 저장일이 **3일 전**이고 그 앞으로 이틀이 더 연속될 때, When 기준 시각을 오늘로 하여 연속 기록 일수를 조회하면, Then 0이 반환된다(유예는 어제까지다). → [FR-12, BR-9]

### 로컬 모드 격하 감지

- AC-26: Given iCloud 계정 상태가 "로그인 안 됨"으로 주어질 때, When 로컬 모드 판정을 요청하면, Then 로컬 모드로 판정된다. → [FR-13]
- AC-27: Given 저장 시도 중 용량 초과 신호가 주어질 때, When 로컬 모드 판정을 요청하면, Then 로컬 모드로 판정된다. → [FR-13]
- AC-28: Given iCloud 계정 상태가 "정상 로그인됨"으로 주어지고 용량 초과 신호가 없을 때, When 로컬 모드 판정을 요청하면, Then 로컬 모드가 아닌 것으로 판정된다. → [FR-13]

### 입력 제약

- AC-29: Given 21자 길이의 모음집 이름이 주어질 때, When 모음집 생성을 시도하면, Then 생성이 거부된다. → [BR-1, BR-7]
- AC-30: Given 41자 길이의 캔버스 제목이 주어질 때, When 캔버스 저장을 시도하면, Then 저장이 거부된다. → [BR-1, BR-7]
- AC-31: Given 동일한 이름("여행")을 가진 모음집이 이미 존재할 때, When 같은 이름으로 새 모음집을 생성하면, Then 생성이 성공한다(중복 거부되지 않는다). → [BR-1]
- AC-32: Given 오늘보다 미래인 기록 날짜가 주어질 때, When 캔버스를 저장하면, Then 저장이 성공하고 기록 날짜가 그대로 보존된다. → [BR-3]

## 제외 범위

- 모든 UI(모음집 화면·에디터·설정 등, Phase 3·6~9) — 이번 범위는 리포지토리 API와 모델뿐이다.
- 초안(`Drafts/`) 저장소 — 이미 `Packages/SoozipDraft`로 완료됨. 초안 → `Canvas` 승격 트랜잭션 7단계는 Phase 2.
- 편집 중 제거된 사진 레이어의 `CanvasPhoto` 정리(저장 시점 고아 정리) — 이는 승격 트랜잭션의 일부로 Phase 2 범위.
- 실기기 2대 CloudKit 동기화 재확인 — 하드웨어(개발자 계정 + 기기 2대) 부재로 이번 범위에서 제외. 로드맵 게이트에는 남아 있으나 Phase 1 완료 조건에서는 별도 트래킹.
- 표지 이미지(`renderedPNG`) 자체의 렌더링 로직 — 렌더링은 Phase 3~5(에디터)의 책임이며, 이 계층은 이미 렌더링된 데이터를 저장·조회만 한다.
- 모음집/캔버스 이름·날짜 UI 유효성 검사 문구, 경고 다이얼로그("캔버스 N장이 함께 삭제됩니다") — Phase 6 UI 몫.

## 확정 이력

| 항목 | 결정 | 근거 |
|---|---|---|
| `sortIndex` 부여 | 생성 시 기존 최댓값 + 1 (첫 모음집 0) | 재배치 전에도 정렬 조회만으로 생성 순서가 성립 |
| 연속 기록 | 오늘 저장이 없어도 어제까지 이어진 연속 유지 | 앱을 늦게 열었다는 이유로 기록이 끊긴 것으로 보이지 않게 |
| 최다 모음집 동률 | `createdAt` 오름차순(먼저 생성된 쪽) | 결정론적이라 단위 테스트가 안정적 |
| 길이 제약 | 리포지토리가 강제 거부 | UI가 없는 지금 리포지토리가 최후 방어선 |
| 로컬 모드 격하 | 두 신호를 하나의 판정으로 통합 | 호출부가 단순해지고 AC-26~28이 그대로 성립 |

**오케스트레이터 수정 1건:** FR-8의 "소속 **모음집의** 사진들도 함께 삭제되고"를 "그 캔버스에 속한 사진들"로 정정했다. 사진은 모음집이 아니라 캔버스에 속한다(`CanvasPhoto.canvas`). AC-17은 원문에서 이미 맞게 쓰여 있어 AC와 FR이 어긋나 있었다.
