# Trust Ledger — EDITOR-2 레이어 스토어

- 작성일: 2026-08-12
- 모드: 핵심(core) / 표준 프로파일

## 긴급 감사 (H1~H4)

순수 값 타입이고 I/O가 없다. 데이터 소실 경로가 없으므로 초점은 **"불변식이
정말 깨질 수 없는가"** 와 **"기능이 없는데 초록일 수 있는가"** 둘이다.

### [설계] z를 저장하지 않고 인덱스에서 파생시킨다

v4 §5.11이 "재정렬 시 0부터 다시 촘촘히 매긴다"를 요구하는데, z를 필드로 들고
조작마다 재번호하면 **조작 6종(맨 앞·앞·뒤·맨 뒤·삽입·삭제) 중 한 곳에서라도
빠뜨리면 구멍이 생긴다.**

배열 순서를 진실로 삼으니 **재번호 코드 자체가 없어졌다.** `layers` 게터가
인덱스를 z로 채워 내보낼 뿐이라 촘촘함이 깨질 수 없다.

`CanvasSurface`(EDITOR-1)의 "배율·뷰포트에 독립인 것만 저장한다"와 같은 원리다 —
**불변식을 지키는 코드를 쓰는 대신, 불변식이 성립할 수밖에 없는 표현을 고른다.**

### [설계] 식별자를 세션 한정으로 둔다

`layoutJSON`(v4 §8)에 레이어 id 필드가 없다. 넣으면 저장 형식이 바뀌고
`JSONContractTests`가 막는다. 재편집으로 열 때마다 새로 발급하면 되므로
영속화할 이유가 없다.

**`PhotoLayer.assetId`는 키가 될 수 없다** — 복제본이 공유한다(v4 §5.12.1).
사진 하나를 3번 복제하면 레이어 4개가 같은 값을 갖는다.

### [정보] 변이 A는 어떤 행위 테스트로도 잡을 수 없다

`sorted { $0.z < $1.z }`로 2차 키를 지워도 전부 초록이다. **실측했다** —
같은 키 원소를 n = 3·8·21·40·100·1000으로 넣어 봤고, 혼합 키 64개도 함께
확인했다. **Swift의 현재 `sorted(by:)`는 전부 안정적이었다.**

그런데 표준 라이브러리 문서는 **"정렬 알고리즘이 안정적이라고 보장되지 않는다"**
고 명시한다. 즉:

- 테스트 `z가_전부_같으면_입력_배열_순서가_유지된다`는 **요구사항을 고정한다** —
  같은 파일이 열 때마다 다른 순서로 보이면 안 된다
- 2차 키는 **관찰된 동작이 아니라 문서화된 비보장에 대한 방어**다
- 둘의 차이는 stdlib 구현이 바뀌어야만 관찰된다. 그때 이 테스트가 잡는다

**"테스트가 약하다"와는 다른 범주다.** 요구사항은 덮여 있고, 방어가 중복일
뿐이다. 중복을 걷어내면 보장되지 않은 동작에 의존하게 된다.

(같은 이유로 `LibraryRepository.canvases(in:)`가 `(createdAt, id)`를 키로 쓴다.
그쪽은 SwiftData의 to-many 순서가 **실제로 뒤집히는 것을 실측**해서 넣은 것이라
근거가 더 강하다.)

## 코드 리뷰 반영 — 생존 변이 3종 + 항등식 테스트 1건

리뷰가 **내 변이 목록에 없던 3종**을 찾았고 전부 생존했다. 전부 재현해 확인 후 막았다.

**세 개의 뿌리가 하나다** — 테스트 픽스처가 전부 `fill` 태그가 서로 다른 shape
레이어라서, **(a) 타입 다형성** 과 **(b) 값 동등성 대 식별자 동등성** 두 축이
동시에 관찰 불가였다. `ac.md`가 두 축을 설계 근거로 명시해 놓고(문제 1: `assetId`
공유 / v4 §5.2: 5종 공통 경로) **픽스처가 둘 다 지워 버렸다.**

### [HIGH] `Layer.transform` setter를 5종 중 4종에서 no-op으로 만들어도 초록

z를 단언하는 테스트 12곳이 **전부 shape 픽스처**였다. 사진을 쓰는 유일한
테스트는 z를 보지 않았고, 그 픽스처는 `z: 0` 기본값이라 첫 항목에서 두 구현이
구별되지 않았다 — **"픽스처가 기본값과 같아서 구별 못 한다"의 세 번째 재발이다**
(`.post` rawValue 0, 기본 `center` = `canvasCenter`에 이어서).

실패 시나리오: z가 `[10, 0, 7]`인 문서를 열어 저장하면 shape만 `0,1,2`로
채워지고 나머지는 원본 z가 그대로 나간다. 재편집으로 다시 열면 그 z로
재정렬되어 **사용자가 맞춰 놓은 겹침 순서가 뒤집힌다.**

- 수정: 5종을 한 번에 담고 `z: 99`를 주는 테스트. **기본값 0을 주면 안 된다**

### [HIGH] `remove`/`move`가 식별자 대신 값 동등성으로 지목해도 초록

**이 단위가 존재하는 이유 자체가 무방비였다.** 복제본은 `assetId`뿐 아니라
크기·회전·투명도·색까지 전부 승계하므로(v4 §5.12.1) **값으로는 원본과 완전히
같다.** 값으로 지목하면 복제본을 지울 때 원본까지 사라지고, 복제본을 앞으로
보내면 원본이 움직인다.

AC-1 테스트는 `Set(entries.map(\.id)).count == 3`만 봤다 — **식별자가 다르다는
것은 증명하지만 조작이 그것을 존중한다는 것은 증명하지 않는다.** 이 저장소가
이미 기록한 "집합/개수 비교가 관계를 못 본다"와 같은 형태다.

- 수정: 내용이 완전히 같은 레이어 3개에서 **id 순열**로 단언

### [MEDIUM] AC-8이 항등식이었다 — 정보를 0비트 담고 있었다

```swift
#expect(z값들(store) == Array(0..<store.entries.count))
```

`layers`가 z를 인덱스에서 채우므로 **좌변은 언제나 `[0,1,…,n-1]`이다.** 조작이
어떻게 망가져도 초록인 항등식인데, 주석에는 "이 단위의 핵심 불변식"이라고
적혀 있었다.

내가 설계 결정으로 "촘촘함이 깨질 수 없게 만들었다"고 해 놓고, **그 깨질 수
없는 성질을 테스트로 다시 확인**하고 있었다. 파생으로 보장한 것을 재확인하는
단언은 정보가 없다 — 확인해야 할 것은 **조작이 낸 순서**다.

- 수정: 매 단계 기대 태그열을 함께 단언. z 촘촘함은 그 위에 얹어 확인

### [MEDIUM] `entries`가 낡은 z를 노출했다

`layers`는 z를 인덱스로 채우는데 `entries[i].layer.transform.z`는 문서에서
읽은 원본이었다. 같은 레이어가 두 표현에서 다른 z를 갖고, **식별자를 얻으려면
어긋난 쪽을 써야 했다.**

`EDITOR-4`의 "같은 지점을 탭하면 z-order 최상단 선택"(v4 §5.11)이 `entries`를
순회하며 `max { $0.layer.transform.z }`를 쓰면 **맨 아래를 최상단으로 고른다.**

- 수정: 저장은 z를 0으로 눕히고 `entries`도 인덱스에서 채운다. **두 표면이
  같은 규칙을 쓴다** — `Equatable`도 순서만 보게 되어 정의가 분명해졌다

## 브랜치 밖 발견 (main에 이미 존재)

### [정보] `Layer.encode`의 키 순서가 실행마다 다르다

리뷰가 확인했다 — 같은 값을 두 번 인코딩하면 서로 다른 바이트가 나온다
(`transform` 내부 키 순서까지 흔들린다). `singleValueContainer`로 payload를 쓴 뒤
같은 encoder에서 `keyedContainer`를 다시 얻는 패턴 때문이다. 값 수준 왕복과
`JSONEncoder(.sortedKeys)`는 안정적이다.

`CanvasPromoter`가 "layoutJSON은 초안의 원본 바이트 그대로"라고 방어하는 것과
같은 뿌리다. **초안 자동저장(`CANVAS-5`)이 사용자 변경 없이도 매번 다른 바이트를
쓴다** — 디스크 쓰기가 무의미하게 발생하고, 변경 감지를 바이트로 하면 오작동한다.
`CANVAS-5`에서 다룰 것.

## 위험 수용

- [상한 미강제] 스토어는 타입별 상한(`photo` 8 · `drawing` 5 · 나머지 30)을
  강제하지 않는다. 판정은 `LayoutDocument.validate()`에 이미 있고 삽입 차단은
  `EDITOR-3`이다. **지금 `insert`는 무제한이므로 배선 전에 반드시 `EDITOR-3`이
  와야 한다**
- [선택 상태 없음] 무엇이 선택됐는지 스토어는 모른다 — `EDITOR-4`
- [실행 취소 없음] v4에 undo/redo 요구가 없어 v1 범위 밖이다. 넣게 되면
  스토어가 값 타입이라 스냅샷 방식이 자연스럽다
- [`insert(above:)` 없음] `TOOL-3`의 "z는 원본 바로 위"(v4 §5.12.1)는 현 API로
  가능하지만 호출부가 목표 인덱스를 직접 계산해 `sendBackward`를 반복해야 한다.
  위치 지정 로직이 스토어 밖으로 샌다. **`TOOL-3`이 소비자와 함께 넣는다** —
  지금 만들면 형태를 틀리기 쉽다 (코드 리뷰 LOW-6)
- [레이어 내용 수정 API 없음] v4 §5.2의 "이동·핀치·회전·투명도"가 이 스토어를
  통과하려면 `update(_ id:transform:)`류가 필요하다. `EDITOR-7`(리사이즈)·
  `EDITOR-8`(회전)이 스토어를 다시 열게 된다 (코드 리뷰 LOW-7)
