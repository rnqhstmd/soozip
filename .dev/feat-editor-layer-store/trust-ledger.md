# Trust Ledger — EDITOR-2 레이어 스토어

- 작성일: 2026-08-12
- 모드: 핵심(core) / 표준 프로파일

## 긴급 감사 (H1~H4)

순수 값 타입이고 I/O가 없다. 데이터 소실 경로가 없으므로 초점은 **"불변식이
정말 깨질 수 없는가"** 와 **"기능이 없는데 초록일 수 있는가"** 둘이다.

### [설계] z를 저장하지 않고 인덱스에서 파생시킨다

v4 §5.11이 "재정렬 시 0부터 다시 촘촘히 매긴다"를 요구하는데, z를 필드로 들고
조작마다 재번호하면 **조작 6종(맨 앞·앞·뒤·맨 뒤·삽입·삭제) 중 한 곳에서라도
빠뜨리면 구멍이 생긴다.**

배열 순서를 진실로 삼으니 **재번호 코드 자체가 없어졌다.** `layers` 게터가
인덱스를 z로 채워 내보낼 뿐이라 촘촘함이 깨질 수 없다.

`CanvasSurface`(EDITOR-1)의 "배율·뷰포트에 독립인 것만 저장한다"와 같은 원리다 —
**불변식을 지키는 코드를 쓰는 대신, 불변식이 성립할 수밖에 없는 표현을 고른다.**

### [설계] 식별자를 세션 한정으로 둔다

`layoutJSON`(v4 §8)에 레이어 id 필드가 없다. 넣으면 저장 형식이 바뀌고
`JSONContractTests`가 막는다. 재편집으로 열 때마다 새로 발급하면 되므로
영속화할 이유가 없다.

**`PhotoLayer.assetId`는 키가 될 수 없다** — 복제본이 공유한다(v4 §5.12.1).
사진 하나를 3번 복제하면 레이어 4개가 같은 값을 갖는다.

### [정보] 변이 A는 어떤 행위 테스트로도 잡을 수 없다

`sorted { $0.z < $1.z }`로 2차 키를 지워도 전부 초록이다. **실측했다** —
같은 키 원소를 n = 3·8·21·40·100·1000으로 넣어 봤고, 혼합 키 64개도 함께
확인했다. **Swift의 현재 `sorted(by:)`는 전부 안정적이었다.**

그런데 표준 라이브러리 문서는 **"정렬 알고리즘이 안정적이라고 보장되지 않는다"**
고 명시한다. 즉:

- 테스트 `z가_전부_같으면_입력_배열_순서가_유지된다`는 **요구사항을 고정한다** —
  같은 파일이 열 때마다 다른 순서로 보이면 안 된다
- 2차 키는 **관찰된 동작이 아니라 문서화된 비보장에 대한 방어**다
- 둘의 차이는 stdlib 구현이 바뀌어야만 관찰된다. 그때 이 테스트가 잡는다

**"테스트가 약하다"와는 다른 범주다.** 요구사항은 덮여 있고, 방어가 중복일
뿐이다. 중복을 걷어내면 보장되지 않은 동작에 의존하게 된다.

(같은 이유로 `LibraryRepository.canvases(in:)`가 `(createdAt, id)`를 키로 쓴다.
그쪽은 SwiftData의 to-many 순서가 **실제로 뒤집히는 것을 실측**해서 넣은 것이라
근거가 더 강하다.)

## 위험 수용

- [상한 미강제] 스토어는 타입별 상한(`photo` 8 · `drawing` 5 · 나머지 30)을
  강제하지 않는다. 판정은 `LayoutDocument.validate()`에 이미 있고 삽입 차단은
  `EDITOR-3`이다. **지금 `insert`는 무제한이므로 배선 전에 반드시 `EDITOR-3`이
  와야 한다**
- [선택 상태 없음] 무엇이 선택됐는지 스토어는 모른다 — `EDITOR-4`
- [실행 취소 없음] v4에 undo/redo 요구가 없어 v1 범위 밖이다. 넣게 되면
  스토어가 값 타입이라 스냅샷 방식이 자연스럽다
