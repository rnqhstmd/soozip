# PR 컨텍스트: EDITOR-6 — 핸들 겹침 방지

## 배경

`EDITOR-4`가 핸들을 화면 좌표에 배치했고 `EDITOR-5`가 겹쳤을 때 "무엇이 잡히는가"를 정의했다. **둘 다 겹침을 전제한 사후 규칙**이다. 이 단위는 애초에 안 겹치게 배치를 조정하는 예방책이다.

v4 §5.7: "레이어가 작아져 핸들이 서로 겹치기 시작하면(짧은 변 < 88pt) **변 핸들을 먼저 숨기고**, 더 작아지면(< 56pt) 코너 핸들을 박스 바깥으로 밀어낸다. 안쪽에 그리면 핸들끼리 붙어 어느 것을 잡았는지 알 수 없다."

`EDITOR-5`가 그 증상을 실제로 문서화했다 — 초소형 레이어에서 네 코너가 서로의 44pt 히트 사각형 안에 들면 **우하단 코너 정중앙(2.83pt)을 눌러도 드래그는 항상 좌상단을 잡는다.**

## 요구사항

- **FR-1**: 판정값(`shortSide × scale`)이 88 미만이면 변 핸들을 배치에서 전부 제외한다 — `edgeHandles`·`edges`·`orderedHandles` 셋 모두에서 사라지고 히트 후보에서도 자동으로 빠진다.
- **FR-2**: 56 미만이면 코너 4개를 화면 축 방향 22pt씩 **바깥**으로 민다. 방향은 **박스 화면 중심 → 코너 벡터의 성분 부호**(성분이 0이면 `Corner.sign` 성분별 폴백).
- **FR-5**: 삭제 ✕는 `topLeft`를 되짚는 계산 프로퍼티라 함께 밀린다.
- **FR-6**: 회전 핸들은 이 정책의 영향을 받지 않는다.
- **BR-1**: 경계는 `<` — 정확히 88이면 변이 **있고**, 정확히 56이면 코너가 **안 밀린다**.
- **BR-4**: 88·56·22를 `hitSize`(44)에서 파생하지 않는다.

## Audit Summary

- 총 4건 (CRITICAL: 0, **HIGH: 1**, MEDIUM: 3) — security-auditor
- **[GAP/HIGH]** `fitScale`이 나눗셈 결과의 오버플로우를 막지 않아 `NaN` 좌표 경로가 존재한다(비정규수 canvas). **`EDITOR-4`부터의 구멍이며 이 단위가 넓히지 않는다** — 실제 결함은 doc이 "NaN이 될 수 없다"고 단정한 것이었고 **정정 완료**. 가드 도입은 AC 밖이라 `EDITOR-11` 착수 전 판단으로 이월.
- **[MEDIUM ×3]** `photo` 전체 파이프라인 미관측 · `ResizeAnchor.clamped`가 `shortSide == 0`을 스킵 · 위 HIGH의 문서 미반영(정정됨).
- **[검증: 정확함]** 설계 자기진단 3항목(밀기가 항상 바깥 · 마주보는 쌍 정확히 44 · `EDITOR-5` §1-h 인계 폐쇄)이 **코드에서 전부 사실 확인**. 임계값 단일 출처도 grep으로 확인.
- 코드 품질: Critical 0 · **Important 6(전부 동작 불변) → 전건 폐쇄** 후 프로덕션 실행 코드 0줄로 정리. 가장 큰 발견은 **AC-6의 단언이 구조적으로 실패할 수 없었던 것**(계산 프로퍼티를 자기 자신과 비교).
