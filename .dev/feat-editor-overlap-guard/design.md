# 설계서: EDITOR-6 — 핸들 겹침 방지 (변 핸들 숨김 + 코너 화면-바깥 이동)

- 작성일: 2026-08-16 (2회차 — 밀기 방향 재결정 반영)
- PRD: `.dev/feat-editor-overlap-guard/prd.md` · 코드 맵: `.dev/feat-editor-overlap-guard/codemap.md`
- 설계 SSOT: `docs/specs/2026-08-10-moumzip-mvp-design-v4.md` §5.7
- 선행: `EDITOR-5` (PR #13, `main` = `c3b9187`)

## 설계 규모

**대형** — 프로덕션은 `HandlePlacement.swift` 하나지만, 기존 테스트 **17건이 영향**받고 **9건이 깨지며 1건은 관측 자체가 소멸**한다. 픽스처 재설계가 작업의 절반이다.

## 배경 및 목적

`EDITOR-4`가 핸들을 화면에 배치했고 `EDITOR-5`가 "겹쳤을 때 무엇이 잡히는가"를 정의했다. **둘 다 겹침을 전제한 사후 규칙**이다. 이 단위는 애초에 안 겹치게 배치를 조정하는 예방책이다.

- 판정값 = `frame.size.shortSide × surface.scale` (화면 pt, 회전 무관)
- **88 미만** → 변 핸들 전부 배치에서 제외
- **56 미만** → 코너 4개를 화면 축 방향 22pt씩 **바깥**으로

목적은 `EDITOR-5`가 문서화한 증상의 제거다 — 초소형 레이어에서 네 코너가 서로의 44pt 사각형 안에 들어 "우하단 정중앙(2.83pt)을 눌러도 항상 좌상단이 잡히는" 상태.

## 확정된 결정

### 결정 3-정정의 근거 (오케스트레이터 검산)

초안은 `Corner.sign`(**로컬** 부호)을 화면 델타로 쓰려 했다. 15° 눈금 24개 중 **안쪽으로 미는** 회전:

| 프레임 | 개수 | 구간 |
|---|---|---|
| 정사각 200×200 | **13** | 90°~270° 전 구간 |
| 세로긴 100×300 | **12** | 75°~240° |
| 가로긴 300×100 | **12** | 120°~285° |

`EDITOR-8`이 15° 스냅이라 전부 도달 가능하다. 최악은 회전 π · 화면 폭 44pt — 밀린 좌상단·우상단이 **정확히 같은 점**이 되어 정책이 없던 겹침을 만든다.

| 케이스 | `Corner.sign` | 화면 델타 부호 (채택) |
|---|---|---|
| AC-5·7·13 (회전 0) | 기준값 | **동일** |
| AC-10 (45°) TL | (283.3553, 257.2893) | **(327.3553, 257.2893)** |
| 88×300 · π, TL·TR 간격 | **0** (둘 다 (270,403)) | **88** ((314,447)·(226,447)) |

## 상세 설계

### 1. 상수 3종 (`rotateGap`·`flipThreshold` 인접, 전부 `internal`)

```swift
    /// 판정값이 이 값 **미만**이면 변 핸들을 배치에서 뺀다 (FR-1·BR-1).
    ///
    /// 판정값은 `frame.size.shortSide * surface.scale` — **화면 pt**다(결정 1).
    /// 논리 px로 재면 줌아웃해서 핸들이 실제로 겹쳐도 정책이 안 깨어난다.
    ///
    /// **`hitSize`에서 파생하지 않는다**(BR-4). 88 = 2×44는 "히트 사각형 두 개가
    /// 나란히 들어가는 최소 폭"이라는 **유래**일 뿐이다. `hitSize * 2`로 적으면
    /// 터치 타깃을 48로 키우는 순간 겹침 정책이 96으로 조용히 따라 움직여,
    /// 손댄 적 없는 레이어에서 변 핸들이 사라진다.
    ///
    /// **경계는 이전 상태다 — 정확히 88이면 변이 있다.** `flipThreshold`의 `<= 40`과
    /// `hitSize`의 `<= 22`가 "경계 포함" 관례를 세웠으나 v4 §5.7 원문이 `< 88pt`를
    /// 명시한다. 이 한 군데만 반대라는 것을 모르면 `<=`로 "통일"하는 변경이
    /// 자연스러워 보인다.
    ///
    /// **`internal`이다 — `hitSize`와 같은 이유다.** `public`으로 열면 호출부가
    /// `size.shortSide * scale < 88`을 재기술하는 가장 짧은 경로가 생기고, 그것이
    /// 정확히 "유일한 반영 지점"이 막으려는 것이다.
    static let edgeHideThreshold: Double = 88

    /// 판정값이 이 값 **미만**이면 코너를 박스 바깥으로 민다 (FR-2·BR-1).
    /// 정확히 56이면 밀지 않는다.
    ///
    /// **`edgeHideThreshold`보다 작아야 한다.** 뒤집으면 "코너는 밀렸는데 변은
    /// 남아 있는" 구간이 생겨 밀린 코너와 제자리 변이 오히려 더 붙는다 —
    /// 정책이 목적의 반대로 동작한다. **타입은 이 순서를 강제하지 않는다.**
    static let cornerPushThreshold: Double = 56

    /// 코너를 미는 화면 거리(pt). 축마다 독립으로 더한다 (FR-2).
    ///
    /// **`hitSize / 2`가 아니다.** 값이 22로 같은 것은 우연이 아니지만(반쪽만큼
    /// 벌리면 마주보는 코너의 사각형이 정확히 맞닿는다) 결합을 만들지 않는다.
    /// `hitSize` doc의 "반쪽을 별도 상수로 두지 않는다"는 **히트 판정 축**의
    /// 이야기이고, 이것은 **배치 축**의 다른 22다.
    static let cornerPush: Double = 22
```

### 2. `init` — 판정값과 두 게이트

```swift
    public init(frame: LayerFrame, edges: Set<Edge>, on surface: CanvasSurface) {
        guard /* 기존 .isFinite 가드 5종 — 그대로 */ else { self.box = nil; return }

        // 판정값 = **화면에서 잰 짧은 변**(pt) — 결정 1·2 · FR-7.
        //
        // `Size2.shortSide`를 그대로 쓴다. "짧은 변"을 여기서 다시 정의하면 두 벌이 된다.
        //
        // **회전을 반영하지 않는다.** 화면 축 바운딩 박스로 재면 로컬 100×300을 45°
        // 돌렸을 때 짧은 변이 100 → 282.8로 뛰어(× 0.5 = 141.4), 크기를 건드리지
        // 않았는데 **회전만으로 정책이 꺼진다.**
        //
        // **NaN이 될 수 없다**(BR-3). 가드가 크기의 유한성을 보장하고 `scale`은
        // `fitScale`(무효 입력에서 0) × `zoom`(`zoomed(to:)`가 비유한을 거부하고
        // [0.5,4]로 클램프)이라 항상 유한하다.
        let screenShortSide = frame.size.shortSide * surface.scale

        let showsEdges = screenShortSide >= Self.edgeHideThreshold      // BR-1: 경계는 이전 상태
        let pushCenter = screenShortSide < Self.cornerPushThreshold
                       ? surface.toScreen(frame.center) : nil

        let topLeft     = Self.screenCorner(.topLeft,     of: frame, on: surface, pushedFrom: pushCenter)
        let topRight    = Self.screenCorner(.topRight,    of: frame, on: surface, pushedFrom: pushCenter)
        let bottomRight = Self.screenCorner(.bottomRight, of: frame, on: surface, pushedFrom: pushCenter)
        let bottomLeft  = Self.screenCorner(.bottomLeft,  of: frame, on: surface, pushedFrom: pushCenter)

        // **크기 축이 종류 축보다 앞에서, 통째로 자른다** (FR-1 · FR-8).
        // `filter { showsEdges && edges.contains($0) }`로 적으면 결과는 같지만 크기
        // 축이 변마다 따로 판정되는 것처럼 읽혀, "짧은 축의 변만 숨긴다" 같은 스펙에
        // 없는 변형이 다음 사람에게 자연스러워 보인다. 전부 아니면 전무다.
        let edgeHandles = showsEdges
            ? Self.edgeOrder.filter(edges.contains).map {
                  PlacedEdge(edge: $0, position: surface.toScreen(frame.edgeMidpoint($0)))
              }
            : []

        // ── 아래 회전 핸들 블록은 한 줄도 바뀌지 않는다 (FR-6) ──
        // **밀린 코너를 쓰지 않는다.** topLeft/topRight의 중점을 넣으면 코너가 밀리는
        // 순간 회전 핸들이 22pt 더 위로 딸려 올라간다(AC-9: (270,247) → (270,225)).
        // v4 §5.7 원문은 코너만 명시한다 — 범위를 넓히지 않는다.
        let up = Vec2(x: sin(frame.rotation), y: -cos(frame.rotation))
        let topScreen = surface.toScreen(frame.edgeMidpoint(.top))
        let flipped = topScreen.y <= Self.flipThreshold && up.y <= 0
        // ... (현행 그대로)
    }
```

**`pushedFrom: Vec2?`인 이유**: 발동 여부와 기준점을 **한 값으로 묶어** 호출부가 "밀기는 켰는데 중심을 안 넘긴" 상태를 만들 수 없게 한다. 네 호출이 같은 기준을 쓰는 것이 마주보는 쌍의 대칭성이 성립하는 전제다.

### 3. `screenCorner` — 밀기 방향 (결정 3-정정의 핵심)

```swift
    /// 코너 하나의 최종 화면 좌표. `pushedFrom`이 `nil`이면 정책 밖이라 변환만 한다.
    ///
    /// **`Corner.sign`을 화면 델타로 쓰지 마라.** 그것은 **로컬** 좌표의 부호이고
    /// (`LayerFrame.swift:7`), 화면 델타로 직접 쓰면 **회전 범위의 절반에서 안쪽으로
    /// 민다.** 실측(15° 눈금 24개 중 안쪽으로 미는 회전): 정사각 200×200 **13개**
    /// (90°~270° 전 구간) · 세로긴 100×300 **12개**(75°~240°) · 가로긴 300×100
    /// **12개**(120°~285°). `EDITOR-8`이 15° 스냅이라 전부 도달 가능하다.
    ///
    /// 최악은 회전 π · 화면 폭 44pt다 — 밀린 좌상단과 우상단이 **정확히 같은 점**이
    /// 되어, 겹침을 막으려는 정책이 없던 겹침을 만든다(간격 88 → 0).
    ///
    /// **회전 0에서는 두 규칙이 같은 값을 낸다.** 그래서 AC-5·7·13만 보고
    /// `Corner.sign`으로 되돌리는 변이는 **회전 0 픽스처를 전부 통과한다.**
    /// 죽이는 것은 회전이 있는 셋뿐이다 — `반회전프레임()`(간격 88 → 0) ·
    /// `AC-10`(45°, x가 +22 대신 −22가 되어 44pt 어긋남) · `인접겹침프레임()`.
    ///
    /// **`dx.sign`(`FloatingPointSign`)을 쓰지 않는다** — `(-0.0).sign == .minus`라
    /// `-0.0`이 들어오면 폴백을 건너뛰고 조용히 한쪽으로 쏠린다. `dx == 0`은
    /// `-0.0`에도 참이다.
    ///
    /// **폴백은 성분별이다.** 전체 벡터가 (0,0)일 때만 폴백하면, 논리 크기 (0, 300)
    /// (폭 0)에서 좌상단·우상단이 **정확히 같은 점**으로 남는다 — 델타의 x만 0이라
    /// "(0,0)이 아니므로 폴백 없음"이 되어 x 밀기가 0이 되기 때문이다.
    /// **성분이 0인 축에는 "안쪽"이 없다** — `|0| → 22`이므로 어느 부호를 골라도
    /// 중심에서 멀어진다.
    private static func screenCorner(_ corner: Corner, of frame: LayerFrame,
                                     on surface: CanvasSurface,
                                     pushedFrom screenCenter: Vec2?) -> Vec2 {
        let p = surface.toScreen(frame.corner(corner))
        guard let c = screenCenter else { return p }
        let dx = p.x - c.x, dy = p.y - c.y
        let sx = dx == 0 ? corner.sign.x : (dx < 0 ? -1.0 : 1.0)
        let sy = dy == 0 ? corner.sign.y : (dy < 0 ? -1.0 : 1.0)
        return Vec2(x: p.x + sx * cornerPush, y: p.y + sy * cornerPush)
    }
```

**정사각형 45°는 폴백의 증인이 아니다.** `Double`에서 `cos(.pi/4) = 0.7071067811865476`, `sin(.pi/4) = 0.7071067811865475`로 **서로 다르다.** 200×200·45°의 TL 화면 델타 x는 정확히 0이 아니라 약 **−5.6e-15**이고, 부호 경로(−22)와 폴백 경로(`Corner.sign.x = −1` → −22)가 **같은 값**을 낸다. 정확히 0이 나오는 것은 회전이 0·π/2 배수이고 **한 축의 크기가 정확히 0**일 때뿐이다.

### 4. `Box`에 상태 플래그를 추가하지 않는다

`rotateFlipped`는 "어느 분기를 탔는지"가 좌표만으로 복원되지 않아 존재한다. 이 정책은 다르다 — `edgeHandles.isEmpty`와 코너 좌표가 이미 완전한 관측면이다. `cornersPushed: Bool`을 저장하면 좌표와 어긋날 수 있는 **두 번째 표현**이 생긴다. 추가하지 않는다.

## 기존 테스트 영향 처리

**전략**: 픽스처의 목적이 *크기와 무관*하면 **정책 중립 크기로 키워 단언을 글자 그대로 보존**하고, 목적이 *작음 그 자체*면 그 목적이 EDITOR-6 이후 무엇으로 대체되는지 따진다. 키우는 방식은 **탐침이 걸린 앵커 핸들의 논리 좌표를 고정한 채 크기를 키우고 중심을 역산**한다 — 44pt 경계를 인코딩한 탐침 리터럴이 `EDITOR-5`의 핵심 자산이라 그것을 움직이지 않는 것이 최우선이다.

## 타입이 보장하는 것 / 보장하지 않는 것

> 1회차에서 "밀기 방향이 바깥"은 **회전 0 근방에서만 참인 테스트 고정 사항**이었다. 화면 델타 부호로 바꾼 지금 **그것은 구조가 보장한다.**

### 구조가 보장한다

| 보장 | 근거 |

### red-writer 필수 인계
