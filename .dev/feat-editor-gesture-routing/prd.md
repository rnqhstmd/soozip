# PRD: EDITOR-10 — 제스처 라우팅 (팬·줌·드래그 배타를 순수 상태 기계로)

- 대상 패키지: `Packages/SoozipGeometry` (Foundation only). 선택 여부는 `Bool`로만 받아 `SoozipLayout`에 대한 상향 의존을 만들지 않는다 — `HandleGesture`·`clampedLayerCenter`가 이미 같은 자리에 있다.
- 설계 SSOT: `docs/specs/2026-08-10-moumzip-mvp-design-v4.md` §5.9(제스처 우선순위 표) · §13(리스크: "핀치와 핸들 드래그가 동시에 인식됨 → 먼저 시작된 쪽만 유지")
- 의존: `EDITOR-1`(캔버스 표면, 완료)

## 배경

9:16 캔버스를 화면에 맞추면 세밀한 배치가 어려워 캔버스 자체의 핀치 줌·팬이 필요하다. 그런데 그 줌·팬은 레이어 핀치·드래그와 같은 손가락 수·같은 동작 형태를 쓰므로 **"지금 이 터치의 임자가 캔버스인가 레이어인가"**를 가르는 규칙이 없으면 둘이 동시에 반응해 "레이어가 순간이동"한다(§13). 지금 이 규칙을 구현한 곳은 스파이크 하나(`Soozip/Spikes/S1_GestureProbe.swift`)뿐이고, 그마저 "2손가락 드래그"를 아예 다루지 않고 `guard selected == nil`로만 가르는 임시 코드다.

이 단위는 그 라우팅 규칙을 SwiftUI와 무관한 **순수 상태 기계**로 만든다. 실제 `DragGesture`/`MagnifyGesture`/`RotationGesture`를 SwiftUI에 붙이는 작업, 그 원시 터치 값을 읽어 "이게 핀치인지 2손가락 드래그인지"를 계산하는 작업은 `EDITOR-11`(렌더 배선)의 몫이다 — `HandleGesture`가 "이 타입은 제스처를 인식하지 않는다"고 이미 선을 그은 것과 같은 경계다.

추가로, 로드맵 189행이 강제한다: `clampedLayerCenter` 호출을 강제하는 구조적 게이트가 아직 없고, 이 부채는 6번째 연속 이월이다(`EDITOR-7` PRD가 "5번째는 허용하지 않는다"고 적었는데 `EDITOR-8`이 그 5번째를 실행했다). EDITOR-10은 "레이어 이동"의 라우팅 주체이므로 이 부채의 자연스러운 수신자다.

## 범위

- 라우팅을 "한 번에 하나만 활성"으로 묶는 배타 잠금 상태(§13 "먼저 시작된 쪽만 유지")
- 레이어 중심을 바꾸는 공개 경로를 `clampedLayerCenter`의 계약으로 봉쇄하는 구조적 요구(부채 해소, 수단은 미지정)

## 이 단위에서 확정한 판단 6건

**1. 라우팅 확정 시점 — 제스처 시작 시 잠기고, 끝날 때까지 다시 판정하지 않는다.** §13이 "핀치와 핸들 드래그가 동시에 인식됨 → 먼저 시작된 쪽만 유지"라고 일반 규칙으로 적어 뒀다. 이 단위는 "판정 함수"가 아니라 "판정 결과를 하나만 붙잡고 있는 상태"를 만든다 — 활성 라우팅이 있는 동안 손가락 수가 바뀌거나(1↔2) 새 시작 신호가 들어와도 무시하고 기존 결과를 유지한다. 그래야 §13이 우려하는 "순간이동"이 구조적으로 막힌다.

**2. 두 손가락 드래그 vs 핀치·회전 구분 — 이 단위가 계산하지 않는다.** 실제 제스처 배선은 EDITOR-11의 몫이고, `HandleGesture`의 선례("이 타입은 제스처를 인식하지 않는다… 인식을 끌어오면 순수 값 계산에 시간이 들어온다")가 같은 경계를 반복한다. 이 단위는 **이미 분류된** 세 종류 입력(1손가락 드래그 / 2손가락 핀치·회전 / 2손가락 드래그)만 받는다.

**3. 더블탭 — 이 우선순위 표에 포함하지 않는다.** fit 복귀는 선택 여부와 무관하게 항상 같은 동작이라 "누가 임자인가"를 다툴 대상이 없다. 인식(탭 두 번의 시간·거리 판정)도 시간 축이 필요해 이 순수 패키지의 철학(시계를 붙잡지 않는다)과 맞지 않는다 — `EDITOR-11`이 `.onTapGesture(count: 2)`로 바로 `CanvasSurface.fitted()`를 부른다.

**4. 고무줄 — 이미 갈라져 있다.** 경계를 자르는 하드 클램프는 `CanvasSurface.centered(on:)`가 이미 `clampedToWorkArea`를 거쳐 처리한다(`EDITOR-1`). 되돌아오는 **시각적** 감쇠만 `EDITOR-11` 몫으로 이미 문서화돼 있다(`context/editor/status.md:31`). 이 단위가 새로 받을 것이 없다.

**5. 핸들 드래그와 레이어 이동의 관계 — 이 단위는 "레이어가 임자다"까지만 정한다.** §5.9 표의 "레이어 이동" 셀은 코너 드래그(리사이즈)·회전 핸들 드래그·몸통 드래그(이동)를 전부 묶은 굵은 분류다 — 2손가락 열의 "레이어 크기·회전"도 리사이즈·회전을 한 셀로 묶은 것과 같은 결이다. 그 안에서 무엇을 할지는 이미 완결된 `HandleHitTest.hitHandle(at:for:)`가 가른다. 이 단위는 그 세부를 재구현하거나 대체하지 않는다.

**6. 상태 기계가 값을 바꾸는가 — 판정만 한다.** `CanvasSurface`·`LayerFrame`의 실제 좌표·배율·각도는 이 단위가 계산도 갱신도 하지 않는다. 부채 해소(FR-5)는 "값을 바꾸는 코드를 이 단위가 갖는다"가 아니라 "값을 바꾸는 코드가 나중에 생길 때 `clampedLayerCenter`의 계약을 벗어날 수 없게 봉쇄한다"는 뜻이다 — 판정 전용 원칙과 충돌하지 않는다.

> 위 6건과 별개로, 표를 문자 그대로 따르면 파생되는 실제 UX 질문이 하나 더 있었다 — "선택된 레이어 밖 빈 캔버스를 드래그하면 무엇이 움직이는가." **사용자 결정으로 확정됐다 — 아래 "확정 이력" 참조.**

## 요구사항

### 기능 요구사항

라우팅 결과는 다음 넷 중 하나다: **레이어 이동** / **레이어 크기·회전** / **캔버스 팬** / **캔버스 줌**. 입력 손가락 패턴은 다음 셋으로 한정된다(이미 분류되어 들어옴 — BR-3): **1손가락 드래그** / **2손가락 핀치·회전** / **2손가락 드래그**.

- [Must] FR-1: v4 §5.9 표를 그대로 판정한다 — `(선택 여부, 손가락 패턴)` 조합 6가지 전부가 표와 정확히 일치하는 결과를 낸다.
- [Must] FR-2: 배타 잠금 유지 — 라우팅이 한 번 확정(활성)되면, 같은 연속 터치 세션 동안 손가락 수가 바뀌거나(1↔2) 선택 상태가 바뀌어도 **외부에서 다시 판정을 요청하지 않는 한** 활성 결과는 그대로 유지된다.
- [Must] FR-3: 새 시작 신호 거부 — 활성 라우팅이 있는 상태에서 "시작" 신호가 다시 들어오면(손가락 수 변화든, 같은 손가락 수 안에서의 재분류든) 무시하고 기존 활성 결과를 그대로 반환한다("먼저 시작된 쪽만 유지", §13).
- [Must] FR-4: 종료 후 재판정 — "종료" 신호를 받으면 유휴 상태로 돌아가고, 그 다음 "시작" 신호는 그 시점의 최신 선택 상태로 새로 판정한다.
- [Must] FR-5: 레이어 중심 변경의 공개 경로 봉쇄 — 이 부채는 6번째 연속 이월이고 `EDITOR-7` PRD의 "5번째는 허용하지 않는다"는 약속이 `EDITOR-8`에서 이미 깨졌다. "레이어 이동" 라우팅 결과가 실제 레이어 중심 값으로 이어지는 **공개 경로는 유한하게 좁혀져야 하며**(그 경로를 무엇으로 만들지는 설계가 정한다), 그 경로는 예외 없이 `CanvasSurface.clampedLayerCenter(_:)`와 동일한 계약 — **작업 영역 밖 좌표는 경계로 잘리고, 비유한 좌표(`∞`/`NaN`)는 캔버스 중심으로 후퇴한다** — 를 만족해야 한다. 클램프를 거치지 않고 레이어 중심을 바꿀 수 있는 두 번째 공개 경로가 존재해서는 안 된다. **강제 수단(타입 설계/그 밖의 방법)은 이 PRD가 지정하지 않는다** — AC-16·17이 요구하는 입력→출력 계약과, BR-7이 요구하는 "경로 유일성"만 지정한다.

### 비즈니스 규칙

- [Must] BR-1: 판정 전용 — 이 단위는 `CanvasSurface`·`LayerFrame`의 실제 값(좌표·배율·각도)을 계산하거나 갱신하지 않는다. **AC 불필요** — 출력이 4가지 라우팅 결과 중 하나뿐인 타입 시그니처가 이미 보장한다(EDITOR-9의 "타입이 막는다" 선례와 동일).
- [Must] BR-2: 핸들 세부 판정은 이 단위 밖 — "레이어 이동"·"레이어 크기·회전" 라우팅 안에서 코너/변/회전/삭제/몸통 중 무엇이 걸렸는지는 `HandleHitTest`가 판정한다. **AC 불필요** — 이 단위의 입력·출력에 핸들 개념 자체가 없어 재기술이 불가능하다.
- [Must] BR-3: 손가락 패턴 분류는 입력으로 이미 확정되어 들어온다 — 이 단위는 스케일·회전 변화량 같은 원시 수치를 계산하지 않는다. **AC 불필요** — 입력 타입에 원시 수치 필드가 없다.
- [Must] BR-4: 터치 위치는 라우팅 입력이 아니다 — 선택 있음 + 1손가락 드래그는 어디를 짚었든 항상 레이어 이동이다. **AC 불필요** — 입력 타입에 좌표 필드가 없어 "레이어 밖을 짚었다"는 전제 자체를 테스트로 재기술할 수 없다(BR-2·BR-3과 같은 형식). 이 결정은 프로덕션 주석의 설계 기록으로 남긴다. **사용자 확정** — 아래 "확정 이력" 참조.
- [Must] BR-5: 손가락 수 0개 또는 3개 이상은 유효한 입력이 아니다 — v4 §5.9 표가 정의하지 않는다. **AC 불필요** — 입력 타입이 그 값 자체를 표현할 수 없게 한다(illegal states unrepresentable).
- [Must] BR-6: "레이어" 라우팅 결과(레이어 이동/레이어 크기·회전)는 그 시점에 실제로 조작 가능한 레이어가 있다는 것을 보장하지 않는다 — 라우팅이 활성화된 뒤 선택이 사라져도(FR-2, AC-9) 잠긴 결과를 그대로 낸다. 이 단위는 레이어 식별자를 입력으로 받지 않으므로(선택 여부만 `Bool`) 대상 레이어의 존재 자체를 확인할 수단이 없다. **인계**: 소비자(`EDITOR-11`)는 "레이어" 라우팅 결과를 받았을 때 대상 레이어가 이미 삭제됐을 수 있음을 전제하고, 없으면 크래시 없이 조용히 무시해야 한다. **AC는 AC-9가 겸한다** — 이 단위 쪽 관측(잠금 유지)은 AC-9로 검증되고, 소비자 쪽 처리는 이 단위의 테스트 범위 밖이다.
- [Must] BR-7: 레이어 중심을 바꿀 수 있는 공개 경로는 `clampedLayerCenter`의 계약을 만족하는 것 하나여야 한다 — 클램프를 거치지 않는 두 번째 경로를 만들지 않는다. **"경로가 유일한가"는 개별 입출력 테스트로 관측되지 않는 구조적 요구라 별도 AC를 두지 않는다** — 인수 검증 단계에서 공개 API 표면을 직접 확인한다. AC-16·17은 "그 유일 경로가 존재할 때 지켜야 하는 계약"만 검증한다.

## 수용 기준

> **AC 총 17건.** 번호는 1부터 연속이며 빈 번호가 없다.

### FR-1 — 우선순위 표 판정

**AC-1: 선택 있음 + 1손가락 드래그 → 레이어 이동** → FR-1
- Given: 선택된 레이어가 있다
- When: 1손가락 드래그가 시작된다
- Then: 라우팅 결과는 **레이어 이동**이다

**AC-2: 선택 있음 + 2손가락 핀치·회전 → 레이어 크기·회전** → FR-1
- Given: 선택된 레이어가 있다
- When: 2손가락 핀치·회전이 시작된다
- Then: 라우팅 결과는 **레이어 크기·회전**이다

**AC-3: 선택 있음 + 2손가락 드래그 → 캔버스 팬** → FR-1
- Given: 선택된 레이어가 있다
- When: 2손가락 드래그가 시작된다
- Then: 라우팅 결과는 **캔버스 팬**이다 — 선택이 있어도 2손가락 드래그는 레이어를 건드리지 않는다

**AC-4: 선택 없음 + 1손가락 드래그 → 캔버스 팬** → FR-1
- Given: 선택된 레이어가 없다
- When: 1손가락 드래그가 시작된다
- Then: 라우팅 결과는 **캔버스 팬**이다

**AC-5: 선택 없음 + 2손가락 핀치·회전 → 캔버스 줌** → FR-1
- Given: 선택된 레이어가 없다
- When: 2손가락 핀치·회전이 시작된다
- Then: 라우팅 결과는 **캔버스 줌**이다

**AC-6: 선택 없음 + 2손가락 드래그 → 캔버스 팬** → FR-1
- Given: 선택된 레이어가 없다
- When: 2손가락 드래그가 시작된다
- Then: 라우팅 결과는 **캔버스 팬**이다 — AC-3과 함께 "2손가락 드래그는 선택 여부와 무관하게 항상 캔버스 팬"임을 양쪽에서 고정한다

### FR-2 — 배타 잠금 유지

**AC-7: 손가락이 1→2로 늘어도 잠금이 유지된다** → FR-2
- Given: 선택 있음 상태에서 1손가락 드래그로 라우팅이 **레이어 이동**으로 활성화되어 있다
- When: 같은 세션 안에서 두 번째 손가락이 추가로 닿는다(종료 신호는 아직 없다)
- Then: 활성 라우팅은 여전히 **레이어 이동**이다

**AC-8: 손가락이 2→1로 줄어도 잠금이 유지된다** → FR-2
- Given: 선택 없음 상태에서 2손가락 드래그로 라우팅이 **캔버스 팬**으로 활성화되어 있다
- When: 같은 세션 안에서 손가락 하나가 떨어진다(종료 신호는 아직 없다)
- Then: 활성 라우팅은 여전히 **캔버스 팬**이다

**AC-9: 선택이 도중에 사라져도 잠금이 유지된다** → FR-2 · BR-6
- Given: 선택 있음 상태에서 1손가락 드래그로 라우팅이 **레이어 이동**으로 활성화되어 있다
- When: 같은 세션 도중 선택된 레이어가 없어진다
- Then: 활성 라우팅은 여전히 **레이어 이동**이다 — 진행 중인 판정은 선택 상태 변화를 다시 읽지 않는다. (이 결과를 받는 소비자가 대상 레이어 부재를 어떻게 처리하는지는 BR-6 인계 참조)

### FR-3 — 새 시작 신호 거부

**AC-10: 레이어 이동 활성 중 핀치 시작 시도는 거부된다** → FR-3
- Given: 라우팅이 **레이어 이동**으로 활성 중이다
- When: 종료 신호 없이 "2손가락 핀치·회전 시작" 신호가 다시 들어온다
- Then: 라우팅 결과는 여전히 **레이어 이동**이다

**AC-11: 캔버스 줌 활성 중 1손가락 드래그 시작 시도는 거부된다** → FR-3
- Given: 라우팅이 **캔버스 줌**으로 활성 중이다
- When: 종료 신호 없이 "1손가락 드래그 시작" 신호가 다시 들어온다
- Then: 라우팅 결과는 여전히 **캔버스 줌**이다

**AC-12: 2손가락 드래그로 시작된 라우팅은 핀치·회전 재진입에도 유지된다** → FR-3
- Given: 라우팅이 **캔버스 팬**(2손가락 드래그로 시작)으로 활성 중이다
- When: 종료 신호 없이 "2손가락 핀치·회전 시작" 신호가 재진입한다(같은 두 손가락이 벌어지거나 돌기 시작해 재분류된 것처럼 보이는 상황)
- Then: 라우팅 결과는 여전히 **캔버스 팬**이다 — 같은 손가락 수 안에서의 재분류도 거부 대상이다

**AC-13: 2손가락 핀치·회전으로 시작된 라우팅은 드래그 재진입에도 유지된다** → FR-3
- Given: 라우팅이 **레이어 크기·회전**(2손가락 핀치·회전으로 시작, 선택 있음)으로 활성 중이다
- When: 종료 신호 없이 "2손가락 드래그 시작" 신호가 재진입한다
- Then: 라우팅 결과는 여전히 **레이어 크기·회전**이다

### FR-4 — 종료 후 재판정

**AC-14: 종료 후에는 최신 상태로 새로 판정한다** → FR-4
- Given: 선택 없음 상태에서 1손가락 드래그가 **캔버스 팬**으로 활성화됐다가 종료 신호를 받아 유휴 상태가 됐다. 그 사이 사용자가 레이어를 선택했다
- When: 새 1손가락 드래그 시작 신호가 들어온다
- Then: 이번 라우팅 결과는 **레이어 이동**이다 — 이전 세션의 판정이 이어지지 않는다

**AC-15: 유휴 상태에서 종료 신호를 중복 수신해도 안전하다** → FR-4
- Given: 활성 라우팅이 없는 유휴 상태다
- When: 종료 신호가 (중복으로) 들어온다
- Then: 크래시나 예외 없이 유휴 상태를 유지한다(멱등)

### FR-5 — 레이어 중심 변경 경로의 계약

> `CanvasSurface.clampedLayerCenter(_:)`의 기존 계약(`LayerCenterClampTests.swift`로 확인)을 그대로 이 단위가 봉쇄해야 할 경로의 계약으로 못박는다. 새 수치를 발명하지 않는다.
>
> ⚠️ **이 두 AC의 테스트는 반드시 새로 만든 공개 경로를 통과해야 한다.** `clampedLayerCenter`를 직접 호출해 같은 값을 확인하면 `LayerCenterClampTests`의 복제일 뿐이고, 부채는 해소되지 않은 채 해소된 것처럼 보인다 — 7번째 이월이 통과로 위장된다.

**AC-16: 작업 영역 밖 좌표는 캔버스 경계가 아니라 작업 영역 경계로 잘린다** → FR-5
- Given: 캔버스 `1080×1350` 표면에서 "레이어 이동" 라우팅이 확정된 뒤, 레이어 중심을 `(99999, 99999)`로 옮기려는 시도가 이 단위가 봉쇄한 공개 경로로 들어온다
- When: 그 경로를 통해 최종 중심을 얻는다
- Then: 결과 중심은 정확히 `(1620, 2025)`다(작업 영역 = 캔버스의 2배 범위 경계). 캔버스 경계 `(1080, 1350)`으로 자르는 결과가 나오면 이 AC는 실패다

**AC-17: 비유한 좌표는 캔버스 중심으로 후퇴하고, 두 비유한 종류가 같은 결과로 수렴한다** → FR-5
- Given: 같은 공개 경로에 center `(∞, 999)`가 들어오는 경우와 `(540, NaN)`이 들어오는 경우 둘 다 있다
- When: 각각 최종 중심을 얻는다
- Then: 두 경우 모두 결과는 정확히 `(540, 675)`(= 캔버스 중심)다 — 경계로 잘리거나(`(1620, 999)`) 비유한이 그대로 통과하면(`(540, NaN)`) 이 AC는 실패다
