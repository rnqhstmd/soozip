# Trust Ledger — CANVAS-1·2 승격 트랜잭션

- 작성일: 2026-08-11
- 모드: 핵심(core) / 표준 프로파일

## 긴급 감사 (H1~H4)

이 변경은 **사용자의 작업물을 옮기고, 옮긴 뒤 원본을 지운다.** 감사의 초점은
"어느 지점에서 실패하면 작업물이 사라지는가" 하나다.

### [CRITICAL] 초안을 먼저 지우면 저장 실패 시 작업물이 증발한다 — 방어됨

v4 §6.6이 "2~5가 전부 성공해야 6을 실행한다"고 못박은 이유가 이것이다.

- 방어: 6단계(초안 삭제)가 `createCanvas` 성공 **이후**에만 실행된다
- 검증: 실패 주입 4건 — 렌더(2) · 사진 읽기(3) · 소속 부재(4) · 검증(1) 각각에서
  초안 폴더가 남고 `Canvas`가 생기지 않는 것을 확인

### [HIGH] 반쯤 만들어진 캔버스 — 방어됨

사진을 읽다가 실패하면 `Canvas`는 만들어졌는데 사진이 빠진 레코드가 남을 수 있다.

- 방어: **DB에 쓰기 전에 사진을 전부 읽는다.** 읽기가 끝난 뒤에야 `createCanvas`를
  부르므로, 읽기 실패는 아무것도 안 만든 상태에서 빠져나온다
- 검증: `사진_읽기가_실패하면_초안이_남고_아무것도_생기지_않는다`

### [MEDIUM] 같은 사진이 레이어 수만큼 저장된다 — 방어됨

복제 레이어는 `assetId`를 공유한다(BR-5). 레이어마다 `CanvasPhoto`를 만들면 같은
2000px 사진이 4벌 저장되어 용량이 4배가 된다.

- 방어: `assetId` 기준으로 중복 제거 후 읽는다
- 검증: `같은_assetId를_공유하는_복제_레이어는_사진을_하나만_만든다`

### [정보] 6단계 실패를 되돌리지 않는다 — 의도적

2~5가 다 됐는데 폴더 삭제만 실패했다고 `Canvas`를 롤백하면 **사용자는 정리 실패
때문에 저장을 잃는다.** 고아 초안을 남기는 쪽이 낫다.

## 구현 중 발견 — AC에 없던 결과

### [후속 과제] 정리 실패가 남긴 초안은 7일간 "이어서 만들까요?" 배너를 띄운다

6단계가 실패하면 초안 폴더가 남는데, `pruneOrphans`는 그걸 **바로 치우지 못한다** —
소속 모음집이 아직 살아 있고 `maxAge`(7일)도 안 지났기 때문이다. 그동안
`DraftBannerPolicy`가 그 초안을 보고 배너를 띄운다.

사용자가 배너를 누르면 **이미 저장된 캔버스의 초안**이 열린다. 혼란스럽다.

**쉬운 해법이 없다는 것이 이 항목의 요점이다.** "저장된 캔버스에 초안이 있다"는
상태는 **재편집(`CANVAS-6`)에서는 정상**이라, 초안 존재만으로는 두 경우를 구분할
수 없다. 구분하려면 초안 메타에 세션 종류(신규/재편집)를 넣거나, 승격 성공 시각을
기록해야 한다.

- 지금 안 고친 이유: `CANVAS-6`(재편집 세션)이 이 구분을 어차피 설계해야 하고,
  그때 두 경우를 함께 보는 편이 정확하다
- 발화 조건: 6단계 실패는 파일 삭제 실패라 드물다 (권한·잠금·볼륨 오류)

## 코드 리뷰 반영 (/code-review high)

지적 7건 전부 유효했다. 전부 수정.

### [HIGH] 레이어와 사진의 연결이 끊겨 있었다

`CanvasPhoto` 선언부의 계약은 "레이어의 `assetId`가 이 `id`를 가리킨다"인데,
`attach`가 **`assetID`를 버리고 새 UUID를 발급**했다. 승격 후에는 `layoutJSON`의
`assetId`가 아무것도 못 가리켜 **저장된 데이터만으로는 어느 레이어가 어느 사진인지
복원할 수 없다** — 재편집도 재렌더도 그때부터 불가능해진다.

**내 테스트가 구조적으로 못 잡는 자리였다.** `Set(photos.map(\.data))` 비교는
바이트가 다 있으면 통과하므로 연결이 끊겨도 초록이다.

- 수정: `CanvasPhoto.id = UUID(assetId)`. `assetId`가 UUID가 아니면 던진다
- 검증: 저장된 `layoutJSON`을 디코딩해 각 레이어의 `assetId`로 `CanvasPhoto`를
  되짚는 테스트를 넣었다. **연결을 끊고 돌려 실제로 그 테스트만 빨개지는 것을
  확인했다** — 나머지 161개는 전부 초록이었다

### [MEDIUM] 3건

- `collectionNotFound`가 **캔버스 식별자**를 담고 있었다. 에러가 맥락을 들어야
  호출부가 문구를 만든다는 규칙인데 페이로드가 거짓이었고, **테스트가 그 버그를
  굳히고 있었다**(같은 잘못된 값을 기대) → 실제 모음집 식별자로 교정
- `UUID(uuidString:) ?? UUID()`가 **조용히 다른 식별자를 발급**했다. 승격 전후로
  같은 캔버스가 다른 것이 되는데 아무 신호가 없다 → 던지도록 변경
- **`attach` 실패 시 사진 없는 캔버스가 남았다.** `createCanvas`가 표지 재계산
  때문에 이미 저장을 끝낸 뒤라, 여기서 손을 떼면 빈 캔버스가 모음집 표지가 될 수도
  있고 재시도하면 같은 식별자가 하나 더 생긴다 → 보상 삭제 추가

### [LOW] 3건

- **AC-4가 구현도 검증도 안 돼 있었다.** "바이트 단위로 같다"고 적어 놓고 디코딩본을
  재인코딩했고, 테스트는 값만 비교했다 → `DraftStore.readLayoutData`를 추가해 원본
  바이트를 그대로 넣고, 테스트도 바이트로 비교
- `DraftStoreError`가 `PromotionError` 계약 밖으로 샜다 → `layoutUnreadable`로 감쌈
- AC-13 테스트의 주석이 실제 동작과 달랐고(폴더를 미리 지운다고 썼지만 클로저를
  주입) FR-3(초안 생존) 단언이 빠져 있었다 → 둘 다 교정

## 위험 수용

- [렌더러 미구현] 2단계 렌더러를 주입받는다. 실제 렌더(`ImageRenderer`)는
  `MEDIA-3`이고 에디터 표면에 딸려 있어 지금 만들 수 없다. **주입이 아니면
  `CANVAS-2`(렌더 실패 시 초안 보존)를 아예 테스트할 수 없다** (ac.md)
- [정리 실패 후 배너] 위 후속 과제 참조. `CANVAS-6`에서 함께 처리 (implement)
- [4·5단계 쓰기 실패 미검증] `attach` 실패 시 보상 삭제를 넣었지만 **테스트로
  덮지 못했다** — `ModelContext`가 구체 타입이라 save 실패를 주입할 수단이 없다.
  Phase 1의 fetch 실패와 같은 한계다 (code-review 후속)
- [재편집 승격 미구현] 기존 `Canvas` 갱신 경로는 `CANVAS-6`. 지금은 신규 생성만
  다룬다 (ac.md 범위 밖)
