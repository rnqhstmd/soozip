# Trust Ledger — EDITOR-8 (회전: 15° 스냅)

## 통합 감사 (review · security-auditor)

**판정: CRITICAL 0 · HIGH 2 · MEDIUM 5**

이 프로젝트는 로컬 전용 iOS 앱이고 이 단위는 순수 기하 계산이라 통상적 웹 보안 축(SQLi·XSS·authn/authz)은 해당 없다. 실제 위험 축은 **데이터 손실**(비유한 값이 `rotation`에 앉으면 `JSONEncoder`가 던져 문서 저장 실패) · **정책 위반** · **미검증 가정** · **누락 시나리오**다.

### [RISK/HIGH] `degrees(fromRadians:)`의 public 노출이 NaN 합성 경로를 남긴다
- 근거: 원장 C-1 — `1e308 / (π/180)` = `inf`, `normalized(inf)` = `NaN`. `RotationSnap` 내부는 이 합성을 쓰지 않지만(결정 ⑥), `public`이라 호출부가 출력을 다시 `normalized(degrees:)`/`snapped(degrees:)`에 먹이는 것을 **코드로 막을 방법이 없다**. 방어는 doc 주석뿐이다.
- **현재 도달 가능성 없음(실측)**: `LayerStore.swift`에 `select`/`deselect`/`insert`/`remove`/z-order 4종/`count`/`remaining`/`canInsert`만 있고 **rotation·x·y·scale·opacity 쓰기 함수가 전무하다.** `EDITOR-11`이 배선하는 순간 재현되는 잠재 위험이다.
- 권고: `EDITOR-11` 착수 시 "`degrees(fromRadians:)` 출력을 판정 함수에 재투입 금지"를 코드 리뷰 체크리스트에 명문화하거나 ast-grep 규칙으로 정적 검출.

### [POLICY/HIGH] `LayerStore` transform 쓰기 경로가 5번째 연속 이월
- 근거: `EDITOR-7` PRD가 "5번째는 허용하지 않는다"고 못 박았는데 `EDITOR-8`이 그 5번째를 실행했다. PRD 이월표(`prd.md`)에 **사실은 투명하게 기록**됐으나, 기록이 정책 위반을 해소하지는 않는다.
- 회전은 순수 기하라 이 경로 없이 단위가 닫히는 것은 사실이다. 그러나 "`EDITOR-11` 착수 시 반드시"는 **강제 메커니즘 없는 텍스트 약속**이며, 같은 형태의 약속이 이미 4회 실패했다.
- 권고: `EDITOR-11` PRD/설계 착수 조건에 구조적 게이트(실패하는 placeholder 테스트 등)로 격상.

### [GAP/MEDIUM] 설계서 위험 11건 중 "드러나는 곳: 없다" 6건이 실제로 테스트 미커버
- #3(단위 오용 붕괴) · #4(결정 A·⑤의 증인이 AC 밖) · #5(`folded` 클램프 증인 1건) · #7(두 임계 혼동 무방비) · #9(`>= gridStepDegrees` 반례) · #10(라디안 극단 미발화, 증인 0건).
- 권고: "이 6개 항목의 유일 증인 테스트를 삭제·약화하는 변경은 별도 승인 필요"를 체크리스트화.

### [GAP/MEDIUM] AC 없는 동작 변경 2건이 테스트로만 기록된다
- `entersSnap(359, 1)` 랩어라운드 미발화 · `isAxisAligned(2π − 0.00005)` 신규 후보 편입.

### [ASSUMPTION/MEDIUM] `axisAlignToleranceRadians`(0.0001 rad) 값을 고정하는 테스트가 없다
- 이번 단위가 만든 결함이 아니다. BR-5("두 임계는 별개 규칙, 통합 금지")가 **규율로만** 지켜진다.
- 권고: `axisAlignToleranceRadians == 0.0001` 상수 단언 추가를 다음 회전 관련 단위에서 검토.

### [ASSUMPTION/MEDIUM] `entersSnap`의 `>= gridStepDegrees` 반례가 정규화 통과 후에도 남는지 미실측
- 원장 C-7이 `idx ≈ 4.5e15`에서 인접 그리드 차가 `8.0`임을 실측했으나, 정규화를 통과한 뒤의 잔존 여부는 미측정이다. 실사용 도달 조건이 약 1.9e14 바퀴라 즉시 조치 불요. doc에 "미실측"으로 명시되어 있다.

### [잘못된 전제를 에이전트에 전달함] "이 저장소는 `Double ==` 선례가 0건이다"

## 리뷰 2회차 (quality-reviewer)

**판정: Critical 0 · Important 5 · Minor 3 — 전부 `[동작불변]`, 실행 코드 결함 0건**

**5건 중 4건이 1회차 코드 교체(`isAxisAligned`가 `normalized` 재사용)의 미완결 파급이다.** 교체가 변이 킬셋 구조를 바꿨는데 주석이 따라가지 못했다.

오케스트레이터 실측:
```
folded(-0.00005)      = 6.283135307179586
folded(2π - 0.00005)  = 6.283135307179586   ← 비트 동일
folded(2π)            = 0.0
```
교체 후 `turn - n` 항 제거 변이를 **통과하는 것은 `2π` 하나뿐**이고 **3건이 죽인다**(교체 전에는 `2π−0.00005` 1건이 유일 증인이었다). 그리고 `[0,2π)` 정규화 후 0 근접 비교 변이가 **같은 변이로 붕괴**했다.

| # | 문제 | 처리 |
|---|---|---|
| 1 | `min` 두 항 설명이 옛 본체(`abs(truncatingRemainder)`) 기준이라 거짓 | 실측표로 교체 |
| 2 | "유일한 테스트" 주장이 거짓 — 고유 킬을 잃음 | 존치 근거를 **접기 안의 분기 차이**로 교체(음수 보정 vs 무보정) |
| 3 | 별개로 열거한 두 변이가 같은 변이로 붕괴 | 둘로 병합 + 표 열 이름 정리 |
| 4 | 교체가 만든 **교차 파일 수치 결합**(`turn` ↔ private `turnRadians`)이 미기록 | 불변식과 실패 양상 기록 |
| 5 | `Self.` 근거 문장이 자기모순("`radians`가 아니라"인데 괄호에 `radians`) | 가려지는 쪽 이름(`degrees`) 기준으로 정정 |

**근본 원인 해소**: 변이 킬셋 서술이 프로덕션 doc과 테스트 주석 **두 곳**에 있어 코드 한 줄 교체가 두 곳을 동시에 낡게 만들었다. 축 정렬 축에 **"프로덕션이 원장 / 테스트는 포인터"** 패턴을 적용해 이중 기술을 제거했다. (왕복 실측표에 1회차가 이미 적용한 패턴과 같다.)

**검증**: 리뷰 3회차 대신 오케스트레이터가 **변이를 직접 재측정**해 doc의 킬셋 주장이 실측과 일치함을 확인했고, 낡은 표현 잔존(`하나만이`·`유일한 테스트`·`나머지가 그대로`)이 0건임을 grep으로 확인했다. 실행 코드는 두 파일 모두 불변이다.

## 코드 리뷰 3회차 (오케스트레이터 직접)

파이프라인 종료 후 오케스트레이터가 **프로덕션 코드를 처음부터 끝까지 직접 읽고** 리뷰했다.
그전까지는 에이전트 보고와 설계가 예측한 변이만 측정했다 — **그것이 이 공백을 만든 원인이다.**

### [test-coverage/HIGH] 라디안 API의 흡착 성공 경로가 완전히 무증인이었다

실측: 아래 변이 넷이 **165건 전부를 통과**했다.

| 변이 | 결과(수정 전) |
|---|---|
| `snapped(radians:)`가 흡착 성공 시 되변환을 생략하고 입력 반환 | **생존** |
| 흡착 성공 시 `0` 반환 | **생존** |
| `guard core.snapped` 제거 — 항상 미흡착 | **생존** |
| `entersSnap(fromRadians:)` 항상 `true` | **생존** |

특히 "0 반환"은 **라디안 API로 스냅할 때마다 레이어가 0°로 붕괴**하는 동작이다 — 사용자가 15°로 맞추려 하면 매번 0°로 튄다. 그런데 어떤 테스트도 잡지 못했다.

**원인**: 라디안 테스트 4건의 입력이 전부 **미흡착 케이스**(`1e308`·`NaN`·`Infinity`·정확히 3°)였다. 흡착에 성공하는 입력이 하나도 없어 성공 분기의 반환값도 흡착 플래그도 아무도 재지 않았다.
**`EDITOR-11`이 호출할 것이 정확히 이 API다.**

**왜 2회의 quality 리뷰·spec 리뷰 2회·보안 감사·인수 검증이 모두 놓쳤나**: 전부 **설계서가 예측한 변이만** 측정했다. 설계는 AC-17을 "무조건 되변환하는 구현이 `inf`를 낸다"로 정당화했고 그것은 사실이지만, **반대 방향(되변환을 안 하는 구현)은 아무도 세지 않았다.**

**조치**: 테스트 3건 추가(프로덕션 코드 0줄). 추가 후 변이 넷이 전부 죽는 것을 실측 확인했다.
- `라디안_경로도_그리드로_흡착된다` — 성공 분기의 값과 플래그
- `도_경로와_라디안_경로가_같은_판정을_낸다` — "어댑터는 규칙을 갖지 않는다" 계약 고정
- `라디안_진입_판정도_같은_구간에_머무는_동안_재발화하지_않는다` — 진입 판정의 거짓 분기

### [docs/LOW] 2회차 정정이 만든 새 부정확 1건

`SnapEngine.swift`의 `isAxisAligned` doc이 *"`internal`인 이유 … 같은 파일의 다른 상수들이 `internal`인 이유와 같다"*고 적었으나, **이 파일에 `internal` 상수가 없다** — `axisAlignToleranceRadians`와 `AABB`는 `private`이고 유일한 `internal` 선언이 이 함수 자신이다. 1회차 doc은 `HandlePlacement.edgeHideThreshold`(실제 `internal`)를 근거로 들었는데 2회차 재작성이 그 근거를 잃었다.
**"정정이 새 부정확을 만든다"의 세 번째 사례다.** 올바른 참조로 정정했다.

### 문제없음을 확인한 것

- `isAxisAligned` 교체의 동등성 — 실측 범위(지정 18 + 무작위 20만)에서 동일. 다만 `turn - n`에 반올림이 1회 추가되므로 **비트 동등이 아니라 "실측 범위에서 동일"**이다.
- `snapped(radians:)`의 멱등성 — `radians(fromDegrees: 15)`를 되먹이면 도로 `14.999999999999998`이 되지만 다시 15°로 흡착돼 같은 값을 낸다.
- 비유한 전파 — 네 반환 경로 모두에서 입력으로 정직하게 후퇴.

### 이 사건의 교훈 (다음 단위로)

**설계서가 예측한 변이만 측정하면 설계서가 보지 못한 축은 영원히 무증인으로 남는다.**
이 단위는 변이 측정을 성실히 했지만 **측정 대상 목록을 설계서에서 받아왔다.**
다음 단위는 공개 API마다 **성공 분기·실패 분기 각각에 증인이 있는지**를 목록과 무관하게 기계적으로 확인할 것.
