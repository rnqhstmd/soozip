## 틀린 것으로 확인된 주장 2건

### A. "도 공간 `d/15 -> rounded -> *15` 는 오버플로 경계가 없다" — 거짓

실측:

| `d` | `d/15` | `idx*15` | 유한? |
|---|---|---|---|
| `gFM` = `1.7976931348623157e308` | `1.198462e307` | **`inf`** | **아니오** |
| `1e308` | `6.666667e306` | `1e308` | 예 |
| `gFM/2` | `5.992310e306` | `8.988466e307` | 예 |

`d = gFM`에서 되곱이 넘친다. 결과가 안전한 이유는 **곱셈이 안 넘쳐서가 아니라** `abs(gFM - inf)` = `inf`이고 `inf < 3`이 거짓이라 **입력으로 후퇴하기 때문**이다.
FR-8은 여전히 성립하지만 설계서의 유도("15 x ulp/2 < ulp(gFM)이라 gFM으로 되반올림된다")는 **사실이 아니다**. doc에 그대로 적으면 다음 사람이 잘못된 논증을 물려받는다.

### B. "`floor` 기반 정규화는 `1e308`에서 `[0,360)` 밖이라 빨강" — 거짓

실측 (`d = 1e308`):

- `d - floor(d/360)*360` = **`0.0`** -> `[0,360)` **안** -> **범위 단언을 통과한다**
- `fmod(d, 360)` = **`296.0`** (올바른 값)

즉 **AC-17에 범위 단언(`0 <= r && r < 360`)만 걸면 `floor` 변이가 죽지 않는다.** 설계서 구현순서 사이클 2의 RED 근거가 이 지점에서 무효다.
`floor` 변이를 죽이려면 **값 자체(`296.0`)를 단언해야 한다.** `fmod`은 정확 연산이라 이 값은 결정적이다.

# 2차 재검증 (design-critic + test-architect 지적 대상)

**두 에이전트 모두 Bash가 없어 실측을 못 했다.** 아래는 오케스트레이터가 **Swift(`swiftc -O`)로 직접 실행**한 결과다 — Python이 `fmod(inf, y)`에서 예외를 던져 Swift 의미론이 정답이다.

## 확인된 지적 (전부 사실)

### C-1. `degrees(fromRadians:)`가 FR-8을 위반하고, 합성이 NaN을 만든다
```
1e308 / (pi/180) = inf            (유한 입력, 비유한 출력)
normalized(inf)  = nan            (truncatingRemainder(inf,360)=NaN -> 두 if를 모두 통과)
```
**유한 라디안 입력 `1e308`이 정규화 합성에서 NaN이 된다.** `LayerTransform.rotation`에 NaN이 앉으면 `JSONEncoder`가 던져 문서 저장이 실패한다.

### C-2. 단위 오용이 컴파일되고 조용히 파괴적이다
`snapped(degrees:)`에 라디안을 넣으면:

| 입력 | 결과 |
|---|---|
| `15°` = `0.261799` rad | `(true, 0.0)` |
| `45°` = `0.785398` rad | `(true, 0.0)` |
| `90°` = `1.570796` rad | `(true, 0.0)` |
| `170°` = `2.967060` rad | `(true, 0.0)` |
| `171.9°` = `3.000221` rad | `(false, 3.000220984178253)` |

**`|r| < 3 rad`(약 ±171.9°) 전 구간이 0으로 붕괴한다.** 반환값이 완벽히 유한하고 `snapped: true`라 정상 동작으로 보인다.

### C-3. `entersSnap` 랩어라운드 오발화 (결정 (b) raw 비교)
```
snapped(359) = (true, 360.0)   snapped(1) = (true, 0.0)
(b) raw: |360 - 0| = 360 >= 15  -> 발화 (오작동)
(a):     now && !before = false -> 미발화 (정답)
```
`359° -> 1°`는 **같은 0°/360° 그리드**인데 (b) raw가 재발화한다. v4 §5.8.2가 금지한 그것이다.

### C-4. `entersSnap(fromDegrees: .nan, toDegrees: 17)` = `true`
`snapped(NaN)` = `(false, NaN)` -> `before.snapped == false` -> `return true`(발화). FR-7이 "진입 판정"까지 요구하는데 AC가 0건이다.

### C-5. `min(folded, turn - folded)` -> `folded` 변이가 AC-11·AC-12를 둘 다 통과한다
`turn - folded` 가지의 **증인이 0건**이다. 유일한 증인은 `2π - 0.00005`이며 계획된 테스트 어디에도 없다.

### C-6. `normalized(1e308)` = `296.0`, `floor` 변이 = `0.0`
범위 단언(`0 <= r < 360`)은 두 구현 모두 통과 -> **공허**. 값 `296.0`을 단언해야 죽는다.

### C-7. `|before - now| >= gridStepDegrees`의 반례 실재
`idx ≈ 4.5e15` 구간에서 인접 그리드 후보의 차가 **8.0**이다 (ulp 증가로 되곱이 어긋난다).
"다르면 최소 15"는 **거짓**. 실사용 영향은 없으나(약 1.9e14 바퀴) 구조적 단언은 좁혀야 한다.

## architect 주장 중 새로 틀린 것으로 확인된 것

### C-8. 왕복이 "정확"하다는 주장 — 거짓
`degrees(fromRadians: radians(fromDegrees: d))`:

| d | 왕복 결과 | 정확? |
|---|---|---|
| `12` | `12.0` | ✅ |
| `3` | `3.0` | ✅ |
| **`15`** | **`14.999999999999998`** | ❌ |
| `2.9` | `2.9` | ✅ |
| `17` | `17.0` | ✅ |
| `16` | `16.0` | ✅ |
| **`29`** | **`29.000000000000004`** | ❌ |
| `373` | `373.0` | ✅ |

architect는 `12`만 확인하고 일반화했다. **`12`가 정확한 것은 우연이다.**
다행히 추가 테스트 (iii)의 입력이 `12°`라 그 테스트는 성립한다 — 그러나 **다른 값으로 바꾸면 깨질 수 있다는 사실을 doc에 남겨야 한다.**

### C-9. 도 공간 흡착은 유한 입력에서 절대 비유한을 못 낸다 (test-architect 지적 확인)

| 입력 | 결과 |
|---|---|
| `greatestFiniteMagnitude` | `snapped=false`, 유한 |
| `1e308` | `snapped=true`, 유한 |
| `1e300` | `snapped=true`, 유한 |

-> **AC-17 흡착 축을 도 API로 재면 공허하다.** 라디안 API로만 유효하다.

# 3차 재검증 (설계 2회차의 신규 주장)

## 확인

### C-10. `Self.` 한정자가 필수다 — 매개변수가 정적 함수를 가린다
```
probe4.swift:5:16: error: cannot call value of non-function type 'Double'
    static func f(radians: Double) -> Double {
        return radians(fromDegrees: 12)   // Self. 없음
```
`snapped(radians:)`·`entersSnap(fromRadians:)` 안에서 매개변수 `radians`가 정적 함수 `radians(fromDegrees:)`를 가린다. **변환 호출에는 반드시 `Self.`를 붙여야 컴파일된다.** 설계서 주장 그대로다.

## 설계서가 "미실측"으로 남긴 것 중 실측한 것

### C-11. `normalized(radians: 1e308)` = **`5.720858487389101`**
유한하고 `[0, 2π)` 안이다. 설계서는 "미실측이라 값 단언을 못 한다"며 **유한성 + 범위 단언만** 계획했으나, **값 단언이 가능하다.**
`truncatingRemainder`가 정확 연산이라 이 값은 결정적이다 — 범위 단언보다 죽이는 변이가 많다(예: period를 `2π`가 아닌 다른 유한값으로 바꾸는 변이 중 결과가 우연히 범위 안에 드는 것).

### C-12. period 오배선은 범위 단언으로도 잡힌다
`folded(1e308, period: 360)` = `296.0` -> `[0, 2π)` 밖 -> 빨강. 설계서 사이클 2의 서술이 맞다.

### C-13. `normalized(radians: 4.0)` = `4.0`
IEEE 보장대로 항등. `period = π` 변이를 죽이는 증인으로 유효하다.

## 설계서 사이클 1 RED 근거 중 틀린 것

### D-1. "AC-4·7·8이 바퀴 수 보존의 증인" — 부분적으로 거짓

- **AC-8(`359 -> 360`)은 어떤 정규화 변이도 죽이지 못한다.** `359 < 360`이라 `truncatingRemainder`도 `[0,360)` 정규화도 **항등**이다. AC-8의 실제 킬은 `.rounded(.down)`(변이 D)이다.
- **AC-4(`-13 -> -15`)는 `[0,360)` 변이만 죽인다.** `truncatingRemainder`는 부호를 보존해 `-13`이 그대로라 변이 B를 통과한다.
- **AC-7(`373 -> 375`)만이 두 정규화 변이를 모두 죽이는 유일한 증인이다.**

-> doc에 "AC-4·7·8이 함께 지킨다"고 적으면 **누군가 AC-7을 중복으로 보고 지울 때 보호가 사라진다.**

### D-2. AC-18은 공허하지 않다 — 확정

변이 C(`15 -> 15.0003`)에서 **AC-18만** 죽는다. test-architect가 손계산으로 예측한 `ε ∈ (0, 0.0004)` 생존 구간이 실측으로 확인됐다(AC-7의 증폭 25가 지배: `25 x 0.0003 = 0.0075 < 0.01` = `isClose` 임계).

### D-3. AC-5(`7°` 미흡착)는 측정한 8개 변이 중 어느 것도 죽이지 못했다

임계를 5로 키워도 `7°`는 가장 가까운 그리드 `0°`에서 7° 떨어져 여전히 미흡착이다. 죽이려면 임계를 8 이상으로 키워야 한다.
test-architect의 "저출력" 판정이 맞다. **제거 대상은 아니다** — 임계 대폭 확대 변이의 유일한 방어선이다.

### D-4. AC-6의 `#expect(r.snapped)` 보강이 실제로 작동한다

변이 E(항상 미흡착)에서 AC-6이 죽는다. 보강이 없었다면 `(false, 30)`을 내는 변이가 통과했다.

| 변이 | 죽는 테스트 |
|---|---|
| X `min(folded, turn - folded)` -> `folded` | **`#D 한_바퀴에_거의_근접한_회전도_축_정렬이다`만** |
| Y `[0,2pi)` 정규화 후 0 근접 비교(자기 유발 회귀) | `#A 미세_음수_회전은_축_정렬로_유지된다` · `#B 미세_음수_회전_레이어가_스냅_후보에_포함된다` · `#D` |
| Z 호출부 `others.filter` 제거 | 기존 `회전된_레이어는_후보에서_제외된다` |

## 확인된 것

- **변이 X가 M5를 실증한다.** `turn - folded` 항의 유일한 증인이 `#D`이며, 설계가 예측한 그대로 `#A`와 `#C`는 그 변이를 통과한다(`-0.00005`는 나머지가 그대로이고 `2π`는 나머지가 `+0.0`이라 둘 다 `folded < tol`을 만족한다).
- **변이 Y가 PRD 배경이 지목한 자기 유발 회귀다.** 세 테스트가 함께 잡는다.
- **`#B`(간접 관측)는 고유 킬이 없다** — 변이 Y에서 `#A`와 함께 죽는다. test-architect의 "고유 킬셋 미발견, 존재 이유는 경로 커버리지" 판정이 맞다. **다만 공허하지는 않다**(두 구현이 실제로 갈린다).
- **호출부 배선은 기존 테스트가 이미 지킨다**(변이 Z) — 새 테스트가 필요 없다.

## SnapEngine.swift 실제 변경 (6줄)

```
- private func isAxisAligned(_ f: LayerFrame) -> Bool { abs(f.rotation) < 0.0001 }
+ private let axisAlignToleranceRadians: Double = 0.0001
+ func isAxisAligned(radians r: Double) -> Bool {
+     let turn = 2 * Double.pi
+     let folded = abs(r.truncatingRemainder(dividingBy: turn))
+     return min(folded, turn - folded) < axisAlignToleranceRadians
+ }
- guard isAxisAligned(moving) else { return [] }
+ guard isAxisAligned(radians: moving.rotation) else { return [] }
- let peers = others.filter(isAxisAligned).map(AABB.init)
+ let peers = others.filter { isAxisAligned(radians: $0.rotation) }.map(AABB.init)
```

# 리뷰 반영 중 발견 — 경로 의존 패키지의 낡은 `.build` 캐시

리뷰 항목 3(접기 규칙 통합)을 적용하자 `SoozipLayout`·`SoozipDraft` 빌드가 실패했다:

```
SnapEngine.swift:108:13: error: cannot find 'RotationSnap' in scope
```

`RotationSnap.swift`는 `Packages/SoozipGeometry/Sources/SoozipGeometry/`에 실재하고, `SoozipGeometry` 자체 테스트(165건)는 통과한다.
원인은 **`Packages/SoozipLayout/.build`·`Packages/SoozipDraft/.build`가 낡은 파일 목록을 들고 있던 것**이다(`SoozipDraft -> SoozipLayout -> SoozipGeometry` 경로 의존).

`rm -rf`로 두 `.build`를 지우고 재빌드하니 95건·26건 전부 통과.

## 왜 지금에서야 드러났는가

`RotationSnap.swift`는 사이클 1에서 추가됐지만, **`SnapEngine`이 그것을 참조한 것은 이번 리뷰 반영이 처음**이다. 그전까지는 두 파일이 서로를 모르는 상태라 낡은 파일 목록이 문제가 되지 않았다.

**교훈**: 같은 모듈 안에서 **새 파일을 처음 교차 참조할 때** 경로 의존 패키지의 캐시가 드러난다. `swift test --package-path X`와 `cd X && swift test`가 서로 다른 답을 내는 순간이 있었는데(전자 통과, 후자 실패), 그것도 캐시 상태 차이였다.
**`./scripts/test.sh`가 세 패키지를 각각 `cd` 후 실행하므로 이 경로를 덮는다** — 단일 패키지 명령만 믿으면 놓친다.
