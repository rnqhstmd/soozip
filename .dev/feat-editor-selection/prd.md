# PRD: EDITOR-4 — 선택 상태 + 바운딩 박스 (핸들 배치, 변 핸들 타입별 3분할)

- 작성일: 2026-08-15
- 단위 ID: `EDITOR-4` (`docs/plans/2026-08-11-00-tdd-roadmap-v1.md`)
- 설계 SSOT: `docs/specs/2026-08-10-moumzip-mvp-design-v4.md` §5.7 · §5.11

## 배경

v1 로드맵상 에디터 도메인 네 번째 단위다. `EDITOR-1`(캔버스 표면)·`EDITOR-2`(레이어 스토어)·`EDITOR-3`(타입별 상한)이 구현되어 319개 테스트를 통과하고 있다.

지금까지는 레이어를 "스토어에 담고 상한 안에서 관리"하는 것까지만 가능하고, **사용자가 특정 레이어 하나를 조작 대상으로 지정하는 개념 자체가 없다.** 선택이 없으면 이동·크기 조절·회전·삭제가 어느 레이어에 적용될지 결정할 방법이 없어, 이 단위가 없으면 `EDITOR-5`·`6`·`7`·`8`이 전부 착수 불가능하다.

두 가지가 이미 코드에 빚으로 남아 있다.

- **`ResizeAnchor`가 레이어 타입을 전혀 보지 않는다.** `resized(draggingEdge:)`가 photo에도 그대로 수행된다. "사진을 한 축으로 늘이면 얼굴이 찌그러진다"(v4 §5.7)는 정책이 코드 어디에도 없다.
- **`LayerStore`가 이 단위를 미리 경고해 뒀다.** `entries` 주석은 "`EDITOR-4`가 선택 대상을 고를 때 낡은 z를 보면 맨 아래 레이어를 최상단으로 고른다", `move` 주석은 "선택된 레이어가 다른 경로로 지워진 뒤 속성바 버튼이 눌리는 경합이 실제로 있다"고 적혀 있다.

## 목표

- 레이어를 선택하면 **그 종류에 맞는 핸들 구성**(코너·변·회전·삭제)이 정확히 결정되고 배치 위치가 정의된다.
- **사진을 한 축으로만 늘여 찌그러뜨리는 실수를 애초에 할 수 없게 만든다** — `photo`·`stamp`·`drawing`에는 변 핸들이 존재하지 않는다.
- 성공 지표: `EDITOR-5`~`8`이 이 단위의 "선택 상태"와 "핸들 배치" 결과를 그대로 입력으로 받아 착수할 수 있다.

## 요구사항

### 기능 요구사항

- [Must] FR-1: 레이어를 선택하면 이전 선택은 자동 해제된다 (단일 선택).
- [Must] FR-2: 선택을 해제하면 어떤 레이어도 선택되지 않은 상태가 된다.
- [Must] FR-3: 선택된 레이어가 스토어에서 제거되면 선택 상태는 자동으로 "선택 없음"이 된다.
- [Must] FR-4: 선택된 레이어의 z-order가 변경돼도 같은 레이어가 계속 선택 상태를 유지한다.
- [Must] FR-5: 선택된 레이어의 종류에 따라 핸들 구성이 결정된다 — `photo`·`stamp`·`drawing`은 변 핸들 없이 코너 4·회전·삭제만, `shape`는 변 4(좌우상하) 추가, `text`는 변 2(좌우만) 추가.
- [Must] FR-6: 코너 핸들 4개는 레이어 프레임의 네 모서리에 **회전을 반영해** 배치된다.
- [Must] FR-7: 변 핸들은 지원되는 각 변의 중점에 **회전을 반영해** 배치된다.
- [Must] FR-8: 회전 핸들은 바운딩 박스 상단 중심에서 화면 좌표 기준 28pt 위, 레이어 회전을 반영한 방향에 배치된다.
- [Must] FR-9: 박스 상단의 화면 좌표가 **뷰포트 상단(화면 y = 0)** 으로부터 40pt 이내이면, 회전 핸들은 박스 하단 중심에서 28pt 아래로 뒤집어 배치된다. (결정 4)
- [Must] FR-10: 삭제 버튼은 **좌상단 코너 핸들과 동일한 지점**에 배치된다 (결정 2 — 오프셋 없음).

### 비즈니스 규칙

- [Must] BR-1: "선택"은 **특정 레이어 자체**를 가리키며 배열상의 순번을 가리키지 않는다. z-order 조작으로 자리를 옮겨도 선택은 계속 같은 레이어를 가리킨다.
- [Must] BR-2: **종류 축에서는** 변 핸들 제공 여부(개수·방향)가 레이어 종류에 의해서만 결정되며, 같은 종류는 회전·색상과 무관하게 항상 동일한 구성을 갖는다. ⚠️ **크기 축은 이 단위의 몫이 아니다** — `EDITOR-6`이 "짧은 변 < 88pt면 변 핸들 숨김"을 이 위에 필터로 얹는다(v4 §5.7). 따라서 이 단위의 API를 "핸들 존재의 유일한 문지기"라고 적으면 `EDITOR-6` 시점에 그 주석이 거짓이 된다. (결정 5)
- [Must] BR-3: 회전 핸들 뒤집기의 40pt 임계는 **뷰포트 상단 기준 화면 좌표**이며, 줌 배율(50~400%)과 무관하게 항상 동일한 화면상 거리에서 판정된다.
- [Must] BR-4: 바운딩 박스는 레이어의 현재 회전값을 그대로 반영해 레이어와 함께 회전한다.
- [Must] BR-5: 뒤집기 판정의 "박스 상단" 기준점은 **레이어 로컬 좌표계의 상단 중앙을 현재 회전값으로 변환한 지점**이다 (결정 3). 회전 핸들이 실제로 놓이는 지점과 판정 기준이 같은 자리여야 한다.

### 품질 기대

- [Should] QE-1: 어느 줌 배율에서 작업하든 회전 핸들이 캔버스 상단 근처에서 뒤집히는 시점이 동일한 시각적 여백으로 느껴진다.

## 사용자 시나리오

- **정상 흐름**: `shape`를 탭해 선택 → 코너 4·변 4·회전·삭제 구성 결정 → 다른 `photo`를 탭 → `shape` 선택 해제되고 `photo`가 선택되며, `photo`는 변 핸들 없이 코너·회전·삭제만.
- **예외 흐름**: 레이어 A가 선택된 상태에서 속성바 삭제가 눌리는 동시에 다른 경로로 A가 이미 사라지는 경합. 선택 조회는 항상 "없음"을 반환해야 하며 사라진 레이어를 대상으로 조작이 이어지면 안 된다.
- **엣지**: 아무것도 선택되지 않은 상태에서는 제공되는 핸들이 전부 비어 있다.
- **엣지**: 레이어가 40pt 경계에 걸쳐 있을 때 뒤집기 판정이 줌 배율과 무관하게 일관돼야 한다.
- **엣지**: 90° 회전된 레이어의 "상단"은 원래 좌/우 변이 된다 — 회전 핸들은 레이어 로컬 상단 기준을 그대로 따라간다 (BR-5).

## 영향 범위

- **영향받는 기존 기능**: `LayerStore`(EDITOR-2/3)의 삭제·z-order API가 선택 상태와 연동된다. `LayoutDocument`·layoutJSON 코덱은 영향 없음.
- **기존 사용자 영향**: 없음 — 신규 로직 단위이며 `EDITOR-11` 배선 전까지 사용자에게 보이지 않는다.
- **하위 호환성**: layoutJSON 스키마 변경 없음. 선택 상태는 `Entry.id`처럼 **편집 세션 안에서만 살고 영속화되지 않는다.**

## 수용 기준

- **AC-1**: 다른 레이어 선택 시 기존 선택이 자동 해제된다
  - Given: 레이어 A가 선택되어 있다
  - When: 레이어 B를 선택한다
  - Then: 선택 상태의 대상은 B 하나이며 A는 더 이상 선택되어 있지 않다
  - → [FR-1]

- **AC-2**: 선택 해제 시 선택된 레이어가 없다
  - Given: 레이어 A가 선택되어 있다
  - When: 선택 해제를 호출한다
  - Then: 선택 조회 결과가 `nil`이다
  - → [FR-2]

- **AC-3**: 선택된 레이어 삭제 시 선택이 자동 해제된다
  - Given: 레이어 A가 선택되어 있고 스토어에 존재한다
  - When: 스토어에서 A를 제거한다
  - Then: 선택 조회 결과가 `nil`이다
  - → [FR-3, BR-1]

- **AC-4**: 선택되지 않은 레이어 삭제는 선택을 바꾸지 않는다
  - Given: 레이어 A와 B가 있고 A가 선택되어 있다
  - When: 스토어에서 B를 제거한다
  - Then: 선택된 레이어는 여전히 A다
  - → [FR-3, BR-1]

- **AC-5**: z-order 재정렬 후에도 식별자 기준으로 선택이 유지된다
  - Given: 레이어 A(맨 뒤)와 B(맨 앞)가 있고 A가 선택되어 있다
  - When: A에 "맨 앞으로"를 적용한다
  - Then: 배열 순서가 바뀐 뒤에도 선택된 레이어는 여전히 A다
  - → [FR-4, BR-1]

- **AC-6**: 사진·도장·펜 레이어는 변 핸들을 제공하지 않는다
  - Given: `photo`, `stamp`, `drawing` 레이어가 각각 선택되어 있다
  - When: 각각의 핸들 구성을 조회한다
  - Then: 세 경우 모두 변 핸들 개수가 0이고, 코너 핸들 4개·회전 핸들 1개·삭제 버튼 1개는 포함된다
  - → [FR-5, BR-2]

- **AC-7**: 도형 레이어는 변 핸들 4개를 전부 제공한다
  - Given: `shape` 레이어가 선택되어 있다
  - When: 핸들 구성을 조회한다
  - Then: 변 핸들 집합이 `{left, right, top, bottom}` 4개다
  - → [FR-5, BR-2]

- **AC-8**: 텍스트 레이어는 변 핸들을 좌우만 제공한다
  - Given: `text` 레이어가 선택되어 있다
  - When: 핸들 구성을 조회한다
  - Then: 변 핸들 집합이 `{left, right}` 2개이고 `top`·`bottom`은 포함되지 않는다
  - → [FR-5, BR-2]

- **AC-9**: 코너 핸들 위치가 레이어 회전을 반영한다
  - Given: 중심 (500,500), 크기 (200,100), 회전 90°(π/2)인 레이어가 선택되어 있다
  - When: `topLeft` 코너 핸들 위치를 계산한다
  - Then: 그 위치가 (550, 400)이다
  - → [FR-6, BR-4]

- **AC-10**: 변 핸들 위치가 레이어 회전을 반영한다
  - Given: 중심 (500,500), 크기 (200,100), 회전 90°(π/2)인 `shape` 레이어가 선택되어 있다
  - When: `left` 변 핸들 위치를 계산한다
  - Then: 그 위치가 (500, 400)이다
  - → [FR-7, BR-4]

- **AC-11**: 회전 핸들 기본 위치 (뒤집기 없음)
  - Given: 뷰포트 상단으로부터 화면 좌표 기준 100pt 떨어진 위치에 회전 0°인 레이어가 선택되어 있다
  - When: 회전 핸들 위치를 계산한다
  - Then: 회전 핸들의 화면 좌표 y값이 박스 상단의 화면 좌표 y값보다 28 작다
  - → [FR-8]

- **AC-12**: 40pt 이내에서 회전 핸들이 뒤집힌다
  - Given: 뷰포트 상단으로부터 화면 좌표 기준 20pt 떨어진 위치에 회전 0°인 레이어가 선택되어 있다
  - When: 회전 핸들 위치를 계산한다
  - Then: 회전 핸들의 화면 좌표 y값이 박스 하단의 화면 좌표 y값보다 28 크다
  - → [FR-9, BR-3, BR-5]

- **AC-13**: 뒤집기 임계는 줌 배율과 무관하게 동일한 화면 거리 기준으로 판정된다
  - Given: 뷰포트 상단으로부터 화면 좌표 기준 30pt 떨어지도록 줌 100%와 줌 400% 각각에서 레이어를 배치한다 (두 줌에서 **논리 y가 서로 다르다** — 논리좌표로 40을 비교하는 구현은 여기서 갈린다)
  - When: 두 줌 배율에서 각각 회전 핸들 뒤집기 여부를 계산한다
  - Then: 두 경우 모두 "뒤집힘"으로 판정된다
  - → [BR-3, QE-1]

- **AC-14**: 선택 없음 상태에서는 핸들이 없다
  - Given: 스토어에 레이어가 있지만 아무것도 선택되어 있지 않다
  - When: 핸들 구성을 조회한다
  - Then: 코너·변·회전·삭제 핸들이 전부 비어 있다
  - → [FR-1, FR-2]

- **AC-15**: 뷰포트 상단 근처의 180° 회전 레이어에서도 회전 핸들이 화면 안에 남는다
  - Given: 표면(`1080×1350` / 뷰포트 `540×700`, scale 0.5)에 중심 (540, 5) · 크기 200×100 · 회전 `π`인 레이어가 선택되어 있다 (박스 상단의 화면 y가 정확히 40이라 뒤집기 임계에 걸린다)
  - When: 회전 핸들 위치를 계산한다
  - Then: 회전 핸들의 화면 y가 68이고 0보다 크다 (화면 안)
  - → [FR-8, FR-9, BR-6]
  - **리뷰(quality-reviewer)에서 발견된 동작 결함으로 추가됨.** 아래 BR-6 참조

### BR-6 (리뷰 반영 추가)

- [Must] BR-6: **뒤집기는 회전 핸들 방향(`up`)이 화면 위를 향할 때만 적용된다.**
  `up = (sin r, −cos r)`는 레이어와 함께 회전하므로 회전 90°~270°에서는 화면 **아래**를 향한다. 그 구간에서는 안 뒤집은 위치가 이미 툴바에서 멀어지는 방향이고, 뒤집은 위치는 **항상 판정선보다 위**가 되어 — **뒤집기가 막으려던 상황(화면 밖·툴바 가림)을 뒤집기가 만든다.**
  실측: scale 0.5, 회전 `π`에서 뒤집으면 `rotate.y = −38`(화면 밖), 안 뒤집으면 68(화면 안).
  AC-11·12·13은 전부 회전 0이고 π/2 케이스는 `up.y = 0`이라 이 구간이 드러나지 않았다.

| 4 | 뒤집기 40pt의 **기준선** | **뷰포트 상단(화면 y = 0).** v4 §5.7의 문면은 "캔버스 상단"이지만 그 목적은 "위에 그리면 화면 밖이거나 툴바에 가린다"이고, **줌+팬에서 둘이 갈라진다.** 실측: 뷰포트 390×844·`post`에서 줌 400%·`center.y=1200`이면 캔버스 상단의 화면 y ≈ −1311이라, 툴바 바로 아래(화면 y=20) 레이어의 판정값이 1331 > 40 → 뒤집히지 않고 회전 핸들이 화면 y = −8(화면 밖)에 놓인다. 목적을 택했다 |
| 5 | `resizableEdges`의 의미 | **종류 축의 문지기로 한정.** `EDITOR-6`이 크기 축 필터(88pt/56pt)를 위에 얹으므로 "핸들 존재의 유일한 문지기"라고 적으면 그 시점에 주석이 거짓이 된다 |

## G-W-T 게이트 결과

**GATE PASS** — AC 14건 전부 `Given:`/`When:`/`Then:` 세 절을 갖추고, Then 절이 자동 테스트로 검증 가능한 구체값(`nil`, 개수, 좌표, 집합, 부등식)을 포함한다. 모호 표현(올바르게/적절히/정상적으로) 0건.

AC-9·AC-10의 좌표는 `LayerFrame.toWorld`의 실제 회전 규약(표준 회전 행렬)으로 직접 계산해 검증했다 — topLeft 로컬 (-100,-50)을 90° 회전하면 (50,-100), 중심을 더해 (550,400). left 변 중점 로컬 (-100,0)은 (0,-100) → (500,400).
