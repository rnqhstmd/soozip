# 「soozip」 iOS MVP 설계 문서 v4

> 2026-08-10 확정. v3(`2026-07-31-moumzip-mvp-design-v3.md`)를 대체한다.
>
> **v3 대비 근본 변경:** 지역 수집 → **자유 수집**. 책·링 바인더 메타포와 여행·행정구역 컨셉을 전부 걷어내고,
> **흰 캔버스 + 자유 배치 에디터 + 사용자가 만드는 모음집** 셋만 남긴다.
>
> **v2·v3의 "되돌릴 수 없는 확정" 3개의 처분:**
> ① `layoutJSON` 한 덩어리 — **유지**
> ② 논리좌표 1080×1920 고정 — **폭 1080 고정 + 높이 2종(1350 / 1920)으로 완화**
> ③ `regionCode` 10자리 법정동코드 — **폐기**
>
> 코드가 아직 한 줄도 없으므로 ②③을 바꿀 수 있는 시점은 지금뿐이다.

## 1. 앱 개요

- **앱 이름:** soozip — "수집"에서 왔다. **표시 표기는 전부 소문자 `soozip`**, 코드 식별자·Xcode Product Name·모듈명은 `Soozip`, 번들 ID는 `com.<팀>.soozip`.
  - v3까지는 「모음 집(Moeum Zip)」이었으나 2026-08-10에 바꿨다. **앱 이름과 사용자가 만드는 엔티티 이름(모음집)이 같아서**, 문서에서 띄어쓰기로 둘을 구분해야 하는 지경이었다. 사용자가 그 구분을 알아챌 리 없고 "모음집 앱에서 모음집을 만든다"는 문장이 계속 나온다. 이름을 분리해 해소했다.
  - 여행 컨셉을 걷어낸 v4에서 "수집"은 무엇이든 모은다는 뜻이라 방향과도 맞는다.
- **컨셉:** 무엇이든 모아서 꾸미는 **나만의 모음집**. 흰 캔버스 위에 사진·텍스트·도형을 자유롭게 배치해 한 장을 만들고, 그 장들을 사용자가 만든 모음집에 담는다.
- **플랫폼:** iOS 17+ (빌드는 Xcode 26 / iOS 26 SDK), SwiftUI, SwiftData + CloudKit. **서버·계정 없음**
- **UX 원칙**
  1. **흰 종이가 기본이다** — 배경은 비켜서고 사진·도형·글씨가 주인공이다
  2. **모음집은 사용자가 정한다** — 앱이 카테고리를 강요하지 않는다
  3. **만들기는 두 번의 탭** — 모음집 안에서 [+] → 비율 → 에디터
  4. **강제하지 않는다** — 제목도, 사진도, 꾸밈도 전부 선택이다

### 1.1 v3에서 무엇을 버렸고 왜인가

v3는 "다녀온 지역을 파스텔 12색으로 물들이고, 그 색들이 메시 그라디언트로 섞여 콜렉트북 표지가 된다"는 **색 수집 메커닉 하나에 차별점 전체를 싣고** 있었다. 그 위에 행정구역 3계층(17 시·도 / 약 230 시·군·구), 책장 화면, 생성 마법사 3스텝이 얹혀 있었다.

여행·지역 컨셉을 걷어내면 이 구조 전체의 전제가 사라진다. 지역이 없으면 색이 물들 대상이 없고, 대상이 없으면 혼합할 이유가 없으며, 혼합이 없으면 책장 표지를 그릴 근거도 없다. 따라서 **부분 수정이 아니라 뿌리를 갈아내는 변경**이고, 그 대가로 v3 최대 기술 리스크였던 메시 그라디언트 렌더 성능(구 S1)과 색 엔진 구현 플랜 1,650줄이 통째로 소멸한다.

### 1.2 앱 전역 제약

에디터가 좌표 기반이라 아래 셋은 **구현 시작 전에 못 박혀 있어야 한다.** 나중에 바꾸면 좌표·레이아웃 코드를 전부 다시 만져야 한다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 화면 방향 | **세로 · 가로 모두 지원** | 가로에서 캔버스를 크게 볼 수 있고 세밀 배치가 쉬워진다. 대신 **에디터 툴바를 가로에서 좌우로 재배치**하는 설계가 필요하다 (아래) |
| 기기 | **iPhone 우선. iPad는 구현 진행에 따라 결정** | 지금 못 박지 않는다. 다만 좌표계가 논리 1080 기준이라 화면 크기에 독립적이므로, iPad를 나중에 붙여도 레이어 좌표는 손대지 않는다 |
| 다이내믹 타입 | **앱 UI는 대응, 캔버스 내부 텍스트는 고정** | 캔버스 텍스트가 시스템 글자 크기를 따라가면 같은 캔버스가 기기마다 다르게 보인다. 그건 재현성 위반이다 |

**가로 모드 레이아웃.** 캔버스가 세로형(4:5 · 9:16)이므로 가로 화면에서는 **화면 높이에 맞춰 fit**하고 좌우에 여백이 생긴다. 그 여백을 툴바가 쓴다.

| | 세로 | 가로 |
|---|---|---|
| 상단 바 | 뒤로 · 제목 · 완료 | 좌측 세로 스트립으로 이동 |
| 도구 패널 (7종) | 화면 하단 가로 스트립 | **우측 세로 스트립** |
| 선택 레이어 속성바 | 도구 패널 위 | 우측 스트립 상단 |
| 캔버스 | 폭에 맞춰 fit | **높이에 맞춰 fit** |

**회전 시 레이어 좌표는 변하지 않는다.** 논리좌표 1080 기준으로 저장돼 있고 화면 표시 배율만 달라지기 때문이다. 회전 중 선택 상태·줌 배율·팬 오프셋은 유지하되, **줌 배율은 새 fit 기준으로 재계산**한다(가로에서 100%였던 것이 세로에서는 100%가 아니다).

### 1.3 플랫폼 — 왜 웹(PWA)이 아니라 네이티브인가

2026-08-10에 **모바일 웹 + 홈 화면 추가(PWA)** 방식을 대안으로 검토하고 **네이티브로 확정했다.** 웹이 macOS·Xcode·개발자 계정·심사를 전부 면제해 주고 안드로이드까지 커버하는데도 그렇게 정한 이유는, **iOS Safari가 이 앱의 핵심 기능에 필요한 API를 아예 제공하지 않기 때문**이다. 구현 난이도 문제가 아니라 불가능의 문제다.

| 기능 | iOS 웹 | 결과 |
|---|---|---|
| **햅틱** | **Vibration API 미지원** (안드로이드는 지원) | 5.8.3의 스마트 가이드 햅틱 4종이 통째로 불가능. **남은 차별점인 조작감의 핵심 장치가 죽는다** |
| **iCloud 동기화** | 불가 | 기기 간 동기화에 서버+계정이 필요해져 "서버·계정 없음" 전제가 무너진다 |
| **로컬 알림 4종** | 로컬 스케줄 알림 API 없음 | Web Push는 서버(VAPID) 필요. 11.3이 성립하지 않는다 |
| **사진 앱 저장** | 다운로드 후 사용자가 길게 눌러 저장 | 인스타 공유가 목적인 앱에서 마찰이 크다 |
| **데이터 영속성** | 홈 화면 아이콘 삭제 시 IndexedDB 전소 | 추억 저장 서비스에서 감당할 수 없는 리스크 |
| 홈 화면 추가 | Safari 공유 → "홈 화면에 추가" | 앱스토어 설치보다 전환 마찰이 **더 크다** |

**다시 검토할 조건:** 안드로이드 진출이 우선순위가 되거나, macOS 환경을 유지할 수 없게 되거나, 햅틱·동기화·알림을 전부 P1로 내려도 좋다고 판단될 때. 그중 하나라도 성립하기 전에는 이 결정을 다시 열지 않는다.

### 1.4 남는 차별점과 그 공백

에디터·필터·재편집·CloudKit 동기화는 그대로 살아남는다. 다만 **차별점이 "색 수집 메커닉"에서 "에디터 품질 + 모음집 구조"로 이동**했고, 이는 Crsel·STIT 같은 기성 꾸미기 앱과 정면 승부한다는 뜻이다. 이 공백은 설계로 메울 수 있는 종류가 아니므로 **21장 남은 리스크**에 명시해 둔다.

## 2. 정보 구조

### 2.1 도메인 2계층

```
모음집 (Collection)   사용자가 만든다 · 이름 · 생성순 · 대표 캔버스가 표지
   └ 캔버스 (Canvas)  4:5 또는 9:16 · 레이어 자유 배치
```

v3에서 사용자가 만드는 객체는 캔버스뿐이었고 상위 2계층은 앱 내장 상수였다. v4에서는 **둘 다 사용자가 생성·수정·삭제한다.** 앱 번들에 들어가는 도메인 데이터는 없다.

- 캔버스는 **정확히 하나의 모음집에 속한다.** 모음집 없이 존재하는 캔버스는 없다.
- 한 캔버스가 여러 모음집에 속하는 다대다는 P0에서 지원하지 않는다(19장 참조).

### 2.2 화면 트리

최상위는 **2탭 — 「모음집」과 「내 정보」**. 앱을 열면 모음집 탭이 뜬다.

```
탭1 「모음집」 (앱 첫 화면)
 ├─ 가로 스크롤 캐러셀
 │   · 맨 좌측 고정 [+ 새 모음집]
 │   · 이후 생성 순서대로 (사용자가 길게 눌러 재배치 가능)
 │   · 카드 = 대표 캔버스 썸네일 + 이름 + 캔버스 수
 │   · 캔버스 0장이면 연한 단색 카드 + 이름만
 ├─ 「전체 보기」 → 모음집 그리드 (캐러셀이 길어졌을 때의 탈출구)
 ├─ 카드 길게 누르기 → 이름 변경 / 대표 캔버스 변경 / 순서 이동 / 삭제
 └─ 검색 (모음집 이름 + 캔버스 제목)

모음집 상세
 ├─ 캔버스 그리드 (최신순 / 오래된순)
 ├─ 초안이 있으면 상단에 "이어서 만들까요?" 배너
 └─ [+] → 비율 선택 시트 → PHPicker 자동 1회 → 에디터

캔버스 뷰어 (전체화면)
 └─ 좌우 스와이프 · 사진에 저장 · 재편집 · 메타 수정 · 삭제

탭2 「내 정보」
 ├─ 통계  모음집 수 · 총 캔버스 · 이번 달 만든 캔버스 · 가장 많이 담은 모음집 · 연속 기록
 └─ 설정  알림 / Face ID / iCloud 상태 / 백업 zip / 캐시 정리 / 정보·라이선스
```

**「전체 보기」를 둔 이유.** 가로 스크롤 한 줄은 모음집이 20개를 넘어가면 끝까지 밀어야 해서 급격히 불편해진다. 캐러셀은 요청대로 유지하되, 늘어났을 때의 탈출구를 하나 마련해 둔다. 초기에는 존재감이 없다가 나중에 값을 한다.

## 3. 캔버스 규격

| 프리셋 | 논리 크기 | 비율 | 용도 |
|---|---|---|---|
| 게시물 | 1080×1350 | 4:5 | 인스타그램 피드 |
| 스토리 | 1080×1920 | 9:16 | 인스타그램 스토리 |

- **폭 1080은 고정**이다. 좌표계·렌더러·익스포트가 y축 높이만 다르게 받으면 되므로 변경 비용이 1차원에 그친다.
- 비율은 **캔버스를 만들 때 고르고, 만든 뒤에는 바꾸지 않는다.** 바꾸면 모든 레이어의 상대 위치가 어긋나고, 재배치 UI를 별도로 설계해야 한다. 다른 비율이 필요하면 새로 만든다.
- 마지막 선택을 기본값으로 기억한다.
- **배경은 흰색(`#FFFFFF`) 고정**이다. 종이 질감·단색 변경은 P1(19장).

## 4. 모음집

| 항목 | 규칙 |
|---|---|
| 생성 | 캐러셀 맨 좌측 [+] → 이름 입력 시트 → 생성 즉시 상세로 진입 |
| 이름 | 필수. 1~20자. 중복 허용(사용자가 같은 이름을 원할 수 있다) |
| 정렬 | 생성 순서가 기본. 길게 눌러 드래그 재배치하면 `sortIndex`로 고정 |
| 표지 | `coverCanvasID`가 지정돼 있으면 그 캔버스, 비어 있으면 **가장 최근 캔버스**의 `renderedPNG` |
| 표지 지정 | 뷰어 또는 카드 길게 누르기에서 "대표로 지정" |
| 캔버스 0장 | 연한 단색 카드 + 이름. 표지 계산 없음 |
| 삭제 | 안에 캔버스가 있으면 개수를 명시해 경고 후 cascade (12.7) |

## 5. 에디터

### 5.1 도구 7종

사진 · 텍스트 · **도형** · 날짜 도장 · 펜 · 배경 · 필터

배경 도구는 P0에서 흰색 고정이므로 **자리만 두고 비활성**한다(P1에 질감·단색이 들어올 슬롯).

### 5.2 레이어 5종

| 타입 | 렌더 | 비고 |
|---|---|---|
| `photo` | 원본 이미지 | 필터·투명도 적용 |
| `text` | 번들 폰트 5종 | 크기·색·정렬 |
| `shape` | SwiftUI Shape | **v4 신규.** 파스텔 12색 채움 + optional 내부 텍스트 |
| `stamp` | 날짜 도장 | 스타일 프리셋 |
| `drawing` | PencilKit을 이미지로 베이크 | 획 재편집 불가 |

선택·이동·핀치·회전·z-order·투명도는 **5종이 완전히 동일한 경로**를 탄다. 타입별로 다른 것은 렌더러와 속성바뿐이다.

### 5.3 도형 (v4 신규)

**9종:** 원 · 사각 · 둥근사각 · 선 · 별 · 하트 · 말풍선 · 화살표 · 삼각형

- **채움 색은 파스텔 12색 팔레트**에서 고른다(5.4 색 상수). 12색은 v3의 색 수집 메커닉에서 분리되어 **도형·텍스트 팔레트로만 남는다.**
- **도형은 텍스트를 품지 않는다.** 말풍선 안에 글자를 넣고 싶으면 도형 위에 텍스트 레이어를 얹는다. 도형에 텍스트 속성을 따로 두면 "글자를 넣는 방법이 두 가지"가 되어 폰트·크기·색 편집 경로가 이중화된다. 대신 도형과 텍스트를 함께 옮기는 편의는 P1의 그룹 기능으로 푼다.
- **마지막 사용 색을 세션 내에서 기억한다.** 같은 색 동그라미를 여러 개 찍는 것이 이 앱의 전형적 사용 패턴인데, 매번 색을 다시 고르게 하면 흐름이 끊긴다.
- 삽입은 **캔버스 중앙에 기본 크기(짧은 변의 20%)로 놓고 자동 선택 상태**로 만든다.

### 5.4 파스텔 12색 (앱 상수)

명도·채도를 고정하고 색상만 30° 등간격으로 나눈다.

| idx | 이름 | HSL | idx | 이름 | HSL |
|---|---|---|---|---|---|
| 0 | 로즈 | `hsl(0, 55%, 82%)` | 6 | 아쿠아 | `hsl(180, 55%, 82%)` |
| 1 | 피치 | `hsl(30, 55%, 82%)` | 7 | 스카이 | `hsl(210, 55%, 82%)` |
| 2 | 버터 | `hsl(60, 55%, 82%)` | 8 | 블루 | `hsl(240, 55%, 82%)` |
| 3 | 라임 | `hsl(90, 55%, 82%)` | 9 | 라벤더 | `hsl(270, 55%, 82%)` |
| 4 | 세이지 | `hsl(120, 55%, 82%)` | 10 | 모브 | `hsl(300, 55%, 82%)` |
| 5 | 민트 | `hsl(150, 55%, 82%)` | 11 | 체리 | `hsl(330, 55%, 82%)` |

**v3의 메시 그라디언트 혼합 로직·시드 배치·상위 6색 절단·인접색 흡수는 전부 삭제된다.** 12색은 이제 단순 팔레트 상수다.

### 5.5 폰트 5종 (번들)

텍스트 입력 시트 하단에 가로 스크롤 스와치로 노출하고, 각 스와치는 자기 폰트로 "가나다 Aa"를 그린다.

| # | 폰트 | 성격 | 라이선스 |
|---|---|---|---|
| 1 | Pretendard | 기본 산세리프 · 가독성 | SIL OFL |
| 2 | 고운바탕 | 감성 세리프 · 명조 | SIL OFL |
| 3 | 고운돋움 | 둥근 고딕 · 부드러움 | SIL OFL |
| 4 | 나눔손글씨 | 손글씨 | SIL OFL |
| 5 | Playfair Display | 세리프 타이틀 *(영문 전용)* | SIL OFL |

**SIL OFL로만 제한한 이유.** OFL은 앱 번들 임베딩을 명시적으로 허용하고 고지 표기만 요구한다. 반면 "상업용 무료"로 배포되는 국내 폰트 상당수는 웹·인쇄는 허용해도 **앱 임베딩은 별도 협의 대상**이라, 심사를 통과해도 사후에 권리 문제가 생길 수 있다. v3에서 "폰트 라이선스"를 남은 리스크로 잡아둔 것이 이 지점이며, OFL 제한으로 해소한다.

**실질 문제는 라이선스가 아니라 용량이다.** 한글 폰트는 완성형 2,780자를 다 담으면 한 종에 4~8MB이고 5종이면 앱 용량이 20~30MB 늘어난다. **KS X 1001 2,350자로 서브셋**하면 종당 1.5~2MB로 떨어진다. P0는 서브셋 정적 번들, 폰트를 늘릴 때 온디맨드 리소스(ODR)로 전환한다(스파이크 S3).

`Info.plist`의 `UIAppFonts`에 등록하고, 설정 > 정보에 5종의 OFL 고지를 싣는다.

### 5.7 선택 UI — 바운딩 박스와 핸들

v3의 "우하단 코너 핸들 하나가 크기와 회전을 겸한다"는 방식을 폐기한다. 크기와 회전이 한 제스처에 얽혀 있으면 **둘 중 하나만 바꾸고 싶을 때 반드시 다른 하나가 딸려 움직인다.** PPT·Keynote·Canva가 모두 이 둘을 분리해 둔 이유다.

```
        ↻                     ↻  회전 핸들 (원형, 박스 위 28pt)
        │
  ✕ ─── ■ ─────── ■           ■  코너 핸들 (사각, 비율 유지 크기 조절)
  │               │           □  변 핸들 (사각, 한 축만 — 도형·텍스트 레이어 전용)
  □               □           ✕  삭제 (좌상단)
  │               │
  ■ ─────── ■ ─── ■           ─  바운딩 박스 (1.5pt 실선, 흰 테두리 + 그림자)
```

| 요소 | 동작 | 적용 레이어 |
|---|---|---|
| 바운딩 박스 | 선택 표시. 레이어와 함께 회전한다 | 전 타입 |
| 코너 핸들 4개 | **비율 유지 크기 조절.** 대각 반대편 코너가 고정점 | 전 타입 |
| 변 핸들 (좌우) | 폭만 조절 | `shape` · `text`(텍스트 박스 폭 = 줄바꿈 지점) |
| 변 핸들 (상하) | 높이만 조절 | `shape` |
| 회전 핸들 | 회전 전용. 레이어 중심이 회전축 | 전 타입 |
| 삭제 ✕ | 즉시 삭제 + 스낵바 실행 취소 | 전 타입 |

**`photo` · `stamp` · `drawing`에 변 핸들을 주지 않는다.** 사진을 한 축으로 늘이면 얼굴이 찌그러지고, 그건 되돌릴 방법을 알려주기 전까지는 사용자가 실수로 인식하지 못하는 종류의 훼손이다. 자유 변형이 필요하면 P1의 크롭 도구로 푼다.

**터치 타깃.** 핸들의 시각 크기는 12pt지만 **히트 영역은 44×44pt**다(Apple HIG 최소치). 시각 크기를 44pt로 키우면 캔버스가 핸들로 뒤덮인다.

**핸들 겹침 방지.** 레이어가 작아져 핸들이 서로 겹치기 시작하면(짧은 변 < 88pt) **변 핸들을 먼저 숨기고**, 더 작아지면(< 56pt) 코너 핸들을 박스 바깥으로 밀어낸다. 안쪽에 그리면 핸들끼리 붙어 어느 것을 잡았는지 알 수 없다.

**회전 핸들 위치.** 기본은 박스 위쪽이지만, **박스 상단이 캔버스 상단에서 40pt 이내면 아래쪽으로 뒤집어 배치**한다. 위에 그리면 화면 밖이거나 툴바에 가린다.

**크기 하한·상한.** 짧은 변 논리 40px 미만으로 줄일 수 없고, 캔버스 긴 변의 4배를 넘을 수 없다. 하한이 없으면 레이어가 점이 되어 다시 잡을 수 없고, 상한이 없으면 스케일 값이 발산해 렌더가 무너진다.

### 5.8 스마트 가이드 — 정렬·간격·크기

사진 여러 장을 격자로 놓는 것이 이 앱의 가장 흔한 사용 패턴이다. **눈대중으로는 절대 맞출 수 없고**, 맞지 않으면 결과물이 즉시 조잡해 보인다. 따라서 PPT·Keynote·Figma가 쓰는 스마트 가이드를 P0에 넣는다.

#### 5.8.1 감지 대상

드래그·리사이즈 중 **실시간으로 계산**해 걸리는 것마다 가이드선을 그리고 햅틱을 준다.

| 종류 | 기준 | 표시 |
|---|---|---|
| **정렬 (드래그 중)** | 캔버스 수직·수평 중심선 | 캔버스를 가로지르는 실선 |
| | 다른 레이어의 좌 · 중앙 · 우 (X축) | 두 레이어를 잇는 실선 |
| | 다른 레이어의 상 · 중앙 · 하 (Y축) | 두 레이어를 잇는 실선 |
| **균등 간격 (드래그 중)** | 같은 축에 3개 이상 있을 때, 간격이 균등해지는 지점 | 간격마다 **이중 화살표 + 같은 길이 표시** |
| **크기 일치 (리사이즈 중)** | 다른 레이어와 폭 또는 높이가 같아지는 지점 | 해당 변에 굵은 강조선 |
| **회전** | 15° 단위 (0°·15°·30°…) | 각도 배지 표시 |

#### 5.8.2 스냅 규칙

- **임계는 화면 좌표 8pt.** 논리좌표가 아니라 화면 좌표로 계산해야 줌 배율과 무관하게 항상 같은 감각으로 걸린다
- 회전 스냅은 **±3°** 에서 흡착
- **회전된 레이어는 정렬·간격 가이드 대상에서 제외한다.** 회전체의 바운딩 박스는 실제 형태와 어긋나서, 박스를 맞춰도 눈에는 안 맞아 보인다. 회전값이 0°인 레이어끼리만 계산한다
- 동시에 여러 가이드에 걸려도 **햅틱은 한 번만** 준다. 매 가이드마다 울리면 드래그 내내 진동이 끊이지 않는다
- 같은 가이드에 계속 붙어 있는 동안에는 재발화하지 않는다. **걸리는 순간에만** 발화한다(enter 이벤트)

#### 5.8.3 햅틱 설계

진동만으로 "무엇에 맞았는지" 구분되어야 한다.

| 이벤트 | 햅틱 | 의미 |
|---|---|---|
| 정렬선에 붙음 | `impact(.light)` | 일직선이 됐다 |
| 균등 간격에 붙음 | `impact(.medium)` | 간격이 고르게 맞았다 — 더 찾기 어려운 정렬이므로 더 세게 |
| 크기 일치 | `selection` | 다른 레이어와 크기가 같아졌다 |
| 회전 15° 스냅 | `selection` | 각도가 딱 맞았다 |

#### 5.8.4 성능

레이어가 최대 43개(사진 8 + 펜 5 + 텍스트·도형·도장 30)이므로 드래그 프레임마다 전수 비교해도 부담이 없다. 다만 **회전 0°인 레이어만 후보에 넣고**, 화면 밖으로 완전히 벗어난 레이어는 제외해 후보를 줄인다.

**2026-08-10 실측 (`docs/reports/2026-08-10-spike-results.md` S1-a)**

| 레이어 수 | 1회 호출 | 60fps 예산 점유율 |
|---|---|---|
| 42 (설계 상한) | **14.64 µs** | **0.088%** |
| 100 (상한 2배) | 27.56 µs | 0.165% |

계산 복잡도는 O(n)이고, 상한 상황에서도 프레임 예산의 **0.1% 미만**을 쓴다. 회전 레이어 필터링도 실제로 비용을 줄인다(전부 회전 시 0.16 µs — early return).

**따라서 스냅 계산은 병목이 아니며, 아래 두 대응책은 폐기한다.**

- ~~스냅 계산을 매 프레임이 아니라 스로틀링~~ — 이미 0.088%인 것을 줄여 얻을 게 없다
- ~~후보를 화면 안 레이어로만 축소~~ — 같은 이유

**실기기에서 60fps가 미달하면 원인은 렌더링 축이다.** 가이드선 그리기 방식, 뷰 갱신 범위, `drawingGroup()` 적용 등에서 대응책을 찾는다. 단, 렌더링 실측은 Task 7의 실기기 측정을 기다린다 — 위 수치는 x86_64 데스크톱에서 잰 **계산 비용만**이다.

### 5.9 캔버스 줌·팬과 제스처 우선순위

9:16 캔버스를 화면에 맞추면 폭이 좁아 세밀한 배치가 어렵다. 따라서 **캔버스 자체의 핀치 줌·팬이 필요하고, 레이어 핀치와 충돌한다.** 규칙으로 가른다.

| 상태 | 한 손가락 드래그 | 두 손가락 핀치·회전 | 두 손가락 드래그 |
|---|---|---|---|
| **선택된 레이어 있음** | 레이어 이동 | **레이어 크기·회전** | 캔버스 팬 |
| **선택 없음** | 캔버스 팬 | **캔버스 줌** | 캔버스 팬 |

- 캔버스 줌 범위는 **50% ~ 400%** (fit = 100%). **fit 아래로도 내려간다** — 캔버스 밖으로 밀어낸 레이어를 보고 다시 잡기 위해서다 (5.10)
- **더블탭으로 fit 복귀**
- **캔버스 팬은 캔버스 영역을 넘어 작업 영역(캔버스의 2배 범위)까지** 이동할 수 있다. 그 이상은 갈 이유가 없으므로 고무줄 효과로 되돌린다
- 줌 상태에서도 핸들의 화면상 크기는 일정하다 — 핸들은 논리좌표가 아니라 **화면 오버레이 레이어**에 그린다
- 제스처 인식기는 **배타(exclusive)** 로 묶어 한 번에 하나만 활성화한다. 동시에 물리면 레이어가 순간이동한다

### 5.10 캔버스 경계와 레이어 이탈

**레이어는 캔버스 밖으로 자유롭게 나갈 수 있고, 캔버스 경계에서 잘려 보인다.** 다시 안으로 밀면 잘린 부분이 그대로 돌아온다. 위치를 제한하지 않는다.

| 구분 | 동작 |
|---|---|
| **에디터 표시** | 캔버스 영역은 정상 렌더. **캔버스 밖으로 나간 부분은 30% 불투명도의 고스트**로 그려 "여기 있지만 결과물에는 안 나온다"를 보여준다 |
| **경계 처리** | 캔버스 사각형으로 클리핑. 잘린 데이터는 버리지 않는다 — `x, y`만 밖에 있을 뿐 레이어는 온전하다 |
| **익스포트 · 썸네일** | 캔버스 영역만 렌더. 고스트는 그리지 않는다 |
| **회수** | ① 줌 아웃(최소 50%)하면 캔버스 밖 작업 영역이 보이므로 직접 잡아 끌어온다 ② 캔버스를 팬해 밖 영역으로 이동해도 된다 |
| **완전 이탈 방지** | 레이어 중심이 **작업 영역(캔버스의 2배 범위)** 밖으로는 나가지 않는다. 그 밖은 줌 아웃으로도 볼 수 없어 영영 잡을 수 없게 된다 |

**클램프하지 않고 클리핑을 택한 이유.** 사진 일부만 화면에 걸치게 두는 배치(가장자리에서 잘린 사진, 화면 밖으로 흘러나가는 도형)는 콜라주의 기본 문법이다. 중심을 캔버스 안에 가두면 이 표현이 통째로 불가능해진다. 대신 "영영 못 잡는 레이어"만 작업 영역 경계로 막는다.

### 5.11 z-order (겹침 제어)

겹치는 배치는 제한하지 않는다. 사용자가 순서를 직접 지배한다.

| 조작 | 동작 |
|---|---|
| **맨 앞으로** | z를 최댓값으로 |
| **앞으로** | z를 한 단계 위로 |
| **뒤로** | z를 한 단계 아래로 |
| **맨 뒤로** | z를 최솟값으로 |

- 4종 모두 **선택 레이어 속성바에 상시 노출**한다. 하위 메뉴에 숨기지 않는다 — 겹침 조정은 콜라주 편집 중 가장 자주 하는 조작이다
- **같은 지점을 탭하면 z-order 최상단이 선택된다.** 아래 레이어를 잡으려면 위 레이어를 뒤로 보내거나, 위 레이어를 잠시 옮긴다. 별도의 레이어 목록 팝업은 두지 않는다 — 조작 경로가 둘로 갈리면 사용자는 어느 쪽도 확신하지 못한다
- z 값은 `layoutJSON`에 정수로 저장되며, 재정렬 시 **0부터 다시 촘촘히 매긴다**(빈 번호가 쌓이면 상한에 부딪힌다)

### 5.12 복제와 붙여넣기

같은 요소를 여러 개 쓰는 것은 콜라주의 기본 동작이다. 같은 색 동그라미 다섯 개, 같은 스타일의 번호 텍스트 여섯 개 — 매번 처음부터 만들게 하면 색·크기·폰트를 다시 맞춰야 한다.

#### 5.12.1 레이어 복제

- **선택 레이어 속성바의 [복제]** — 전 타입(`photo` · `text` · `shape` · `stamp` · `drawing`) 지원
- 원본에서 **논리좌표 +40, +40 오프셋**된 자리에 생성하고, **복제본이 선택 상태**가 된다. 같은 자리에 겹쳐 놓으면 어느 것이 새것인지 알 수 없다
- 크기·회전·투명도·색·폰트 등 **모든 속성을 그대로 승계**한다. z는 원본 바로 위
- **`photo` 복제는 `assetId`를 공유한다.** 같은 원본을 참조하므로 사진 데이터가 두 배로 늘지 않는다. 대신 `filter` · `opacity` 같은 **레이어 속성은 각자 독립**이다
- 복제본도 `photo` 레이어 상한 8개에 포함된다. 메모리상으로는 여유가 있지만, "사진은 8장까지"라는 안내를 일관되게 유지하는 편이 낫다

#### 5.12.2 클립보드 붙여넣기

다른 앱에서 복사한 이미지(스크린샷, 웹 이미지, 메신저 사진)를 바로 얹는다.

- 사진 도구 안의 **[붙여넣기]** — `UIPasteboard`에 이미지가 있을 때만 활성화
- **`UIPasteControl`을 쓴다.** iOS 16+에서 `UIPasteboard`를 직접 읽으면 시스템 붙여넣기 허용 프롬프트가 매번 뜨는데, `UIPasteControl`은 사용자가 버튼을 누른 것 자체를 동의로 간주해 프롬프트가 뜨지 않는다
- 붙여넣은 이미지도 **2000px 사본으로 정규화**해 일반 사진과 동일하게 다룬다
- 텍스트 클립보드는 다루지 않는다. 텍스트 레이어의 입력 시트에서 시스템 기본 붙여넣기가 이미 동작한다

#### 5.12.3 투명 배경 이미지 — 누끼의 실질적 대체 경로

**iOS 사진 앱은 「피사체 들어올리기」(사진을 길게 눌러 배경에서 분리)를 기본 제공한다.** 사용자가 거기서 복사한 뒤 우리 앱에 붙여넣으면 **투명 배경 PNG**가 들어온다. 앱이 누끼를 구현하지 않아도 사용자는 OS 기능으로 같은 결과를 얻고, 붙여넣어진 것은 평범한 `photo` 레이어이므로 바운딩 박스·핸들·회전이 전부 그대로 동작한다. 이것이 누끼를 P0에서 제외할 수 있었던 실질적 근거다(5.15).

**투명도는 파이프라인 전 구간에서 보존되어야 한다.** 붙여넣을 때는 투명한데 저장 후 다시 열면 흰 사각형이 되는 것은 **기능 오류로 간주한다.**

#### 알파가 죽는 세 지점

```
클립보드 이미지 (투명)
   │
   ├─ ① 2000px 리사이즈    ← 가장 흔한 소실 지점
   │      opaque = true 이면 투명 영역이 배경색으로 칠해진다.
   │      이 시점에 픽셀이 이미 구워지므로 이후 무엇을 해도 되살릴 수 없다.
   │
   ├─ ② 인코딩            ← JPEG는 알파를 지원하지 않는다
   │
   └─ ③ 필터 적용          ← Core Image 출력 픽셀 포맷
```

#### 보존 규칙

| 단계 | 규칙 |
|---|---|
| **판정** | `CGImageAlphaInfo`로 알파 채널 유무를 보고, 있으면 **64×64로 다운샘플해 실제 투명 픽셀을 스캔**한다. 채널 유무만으로 판정하면 안 된다 — 스크린샷은 알파 채널이 있어도 전부 불투명이라, PNG로 저장하면 용량만 몇 배가 된다. 반대로 전수 스캔(2000×2000 = 400만 픽셀)은 비싸므로 다운샘플로 충분하다 |
| **리사이즈** | **`UIGraphicsImageRendererFormat.opaque = false` 강제.** 투명 이미지 경로에서는 예외 없이 |
| **인코딩** | 투명 픽셀 있음 → `pngData()` / 없음 → `jpegData(0.9)` |
| **필터** | Core Image 출력 시 알파 보존 픽셀 포맷 사용 |
| **로드** | `UIImage(data:)`는 PNG의 알파를 유지한다. 다만 표시용 캐시를 만들 때 다시 `opaque = false` |
| **CloudKit** | CKAsset은 바이너리를 그대로 실어 나르므로 포맷과 무관하다 |

**용량 트레이드오프를 감수한다.** 2000px PNG는 3~8MB로 JPEG(0.5~1MB)보다 크지만, 투명 배경 이미지는 사용자가 의도적으로 만들어 온 것이므로 그 의도를 지키는 편이 낫다. 사진 8장 상한이 이미 용량 상한 역할을 한다.

#### 알파 트림

애플의 피사체 들어올리기는 대체로 피사체에 맞춰 잘라주지만, 다른 앱이나 웹에서 복사한 투명 PNG는 여백이 클 수 있다. 그러면 바운딩 박스가 투명 여백까지 잡아 **핸들이 피사체에서 떨어진 허공에 뜬다.**

- 붙여넣기 시점에 **알파 바운딩 박스를 계산해 크롭**하고, 그 크기를 레이어 초기 크기로 삼는다
- 폐기했던 누끼의 트림과 달리 **되돌릴 원본 개념도, 유지할 상태도 없다.** 한 번 자르고 끝이므로 비용이 사실상 없다
- 완전 투명 이미지면 트림 결과가 0×0이 된다 → **붙여넣기를 거부하고 "빈 이미지예요" 토스트**
- 히트 판정은 바운딩 박스 기준이다. 트림 후에도 박스 안에는 투명 영역이 남지만(팔과 몸통 사이 등), 알파 기반 정밀 히트테스트는 비용 대비 이득이 적다

**별도 안내·힌트는 두지 않는다.** 복사·붙여넣기가 제대로 동작하는 것으로 충분하다.

### 5.13 레이어 상한

병목은 익스포트 출력이 아니라 **디코딩된 비트맵**이다. 따라서 상한은 전체 개수가 아니라 타입별로 건다.

| 대상 | 상한 | 근거 |
|---|---|---|
| `photo` | **8개** | PHPicker 선택 상한과 동일. 2000px 사진 한 장이 디코딩되면 약 16MB다. 복제본은 `assetId`를 공유하므로 메모리가 늘지 않지만 개수에는 포함한다 |
| `drawing` | **5개** | PencilKit을 캔버스 크기 비트맵으로 굽기 때문에 한 장이 사진과 맞먹는다 |
| `text` + `shape` + `stamp` 합 | **30개** | 메모리보다 조작성 문제. 이 이상은 단일 선택 UI로 다루기 어렵다 |

상한 도달 시 해당 도구를 비활성화하고 "사진은 8장까지 넣을 수 있어요" 형태로 안내한다. 익스포트는 `autoreleasepool`로 감싼다.

### 5.14 빈 캔버스

사진이 하나도 없어도 저장된다. 흰 배경만 있는 `renderedPNG`가 정상 생성되어야 하며, **제목이 비어 있으면 목록에 `날짜`만 표시**한다(예: `8월 10일`).

### 5.15 명시적 제외

캐러셀 분할 · 영상 · AI 이미지 생성 · 워터마크 · 무한 캔버스 · 레이어 그룹 · 다중 선택 · 자유 변형(비율 무시 사진 늘이기) · 도형 내부 텍스트 · **누끼(배경 제거)**.

**누끼를 뺀 이유.** v3~v4 초안에서는 P0였다. Vision 온디바이스로 무료라 비용은 낮지만, 딸려오는 것이 많았다 — 지원 확인·비동기·인디케이터·취소·10초 타임아웃·실패 원복의 6단계 처리, 결과 트림과 위치 보정(트림하지 않으면 바운딩 박스가 투명 여백까지 잡혀 핸들이 피사체에서 떨어진다), 원본 보존을 위한 `cutoutPNG` 별도 필드, 그리고 머리카락·유리·유사 색상에서의 품질 편차. **결정적으로, OS가 이미 같은 것을 제공한다.** iOS 사진 앱의 「피사체 들어올리기」로 복사한 뒤 우리 앱에 붙여넣으면 투명 배경 이미지가 그대로 들어오고, 평범한 `photo` 레이어이므로 바운딩 박스·핸들·회전이 전부 동작한다(5.12.3). 앱이 중복 구현할 이유가 약하다.

**따라서 P0 범위를 좁히기 위해 기능 자체를 제외한다.** 다시 넣는다면 `layoutJSON`에 `cutout` 플래그와 `CanvasPhoto.cutoutPNG` 필드를 추가하는 것으로 시작하며, 후자는 CloudKit additive-only 제약 아래에서도 optional 필드 추가라 가능하다.

## 6. 워크플로우 · 비즈니스 로직

### 6.1 캔버스 생명주기

```
        [+]                  [완료]              [편집]
없음 ──────→ 초안(Draft) ──────→ 저장됨 ⇄ 초안(재편집)
             │  ↑ 자동 임시저장     │            │
             │  └─ 1.5초 디바운스   │            └ [취소] → 원본 유지
             └─ [나가기] → 3지선다  └ [삭제] → 확인 → 소멸
```

### 6.2 초안은 SwiftData에 넣지 않는다

초안은 앱 샌드박스의 `Application Support/Drafts/<uuid>/`에 `layout.json` + 사진 사본으로 둔다. 저장을 확정하는 순간에만 `Canvas`로 **승격**된다. 근거가 셋이다.

1. SwiftData에 넣으면 **CloudKit이 미완성 캔버스를 다른 기기로 동기화**한다. 아이패드에서 만들다 만 것이 아이폰 그리드에 뜨는 것은 사고다.
2. 모음집 그리드·통계·검색이 전부 `Canvas` 쿼리 기반인데, 초안이 섞이면 **모든 쿼리에 `isDraft == false` 필터**를 달아야 한다. 하나만 빠뜨려도 새어 나온다.
3. 초안 폐기가 폴더 삭제 한 번으로 끝난다.

### 6.3 생성 워크플로우

| 단계 | 화면 | 규칙 |
|---|---|---|
| 1 | 모음집 상세에서 [+] | 소속 모음집이 이미 정해져 있으므로 선택 단계 없음 |
| 2 | 비율 시트 (4:5 / 9:16) | 마지막 선택을 기본값으로 기억. 저장 후 변경 불가 |
| 3 | PHPicker 자동 1회 | 최대 8장. **취소하면 빈 캔버스로 진입** (백지 공포 방지 장치) |
| 4 | 에디터 | 선택 사진이 계단식 오프셋으로 자동 배치, 첫 장이 선택 상태 |
| 5 | [완료] → 저장 시트 | 제목(선택) · 날짜(기본 오늘) |
| 6 | 저장 | 6.6의 순서대로 |
| 7 | 저장 완료 | `[사진에 저장]` `[모음집으로]` |

### 6.4 도구별 조작

| 도구 | 삽입 | 선택 시 속성바 |
|---|---|---|
| 사진 | PHPicker(남은 슬롯만큼) → 계단식 배치 / **클립보드 붙여넣기** | 필터(12종+강도) · 투명도 · **복제** · **z-order 4종** · 삭제 |
| 텍스트 | 입력 시트(키보드 + 폰트 5종 + 크기·색·정렬) → 삽입 | 재편집(더블탭) · 폰트 · 색 · 투명도 · **복제** · **z-order 4종** · 삭제 |
| 도형 | 9종 그리드에서 탭 → 중앙 삽입 + 자동 선택 | **파스텔 12색** · 채움/테두리 · 투명도 · **복제** · **z-order 4종** · 삭제 |
| 날짜 도장 | 스타일 선택 → 삽입 | 날짜 · 스타일 · **복제** · **z-order 4종** · 삭제 |
| 펜 | 전체화면 PencilKit → [완료] 시 이미지로 베이크 | 투명도 · **복제** · **z-order 4종** · 삭제 (획 재편집 불가) |
| 필터 | 선택된 `photo` 레이어에만 | 톤 12종 + 강도 0~100% |
| 배경 | P0 비활성 (흰색 고정) | — |

- **z-order 4종 = 맨 앞으로 / 앞으로 / 뒤로 / 맨 뒤로** (5.11). 전 타입 공통이며 속성바에 상시 노출한다.
- **복제**도 전 타입 공통이다 (5.12.1). +40, +40 오프셋에 생성하고 복제본이 선택된다.

### 6.5 중간 저장 (자동 임시저장)

- **트리거:** 레이어 추가·삭제·이동·속성 변경 등 모든 변경 → **1.5초 디바운스** → `Drafts/<uuid>/layout.json` 덮어쓰기
- **사진 사본은 삽입 즉시** draft 폴더에 기록한다(디바운스 대상 아님 — 크래시 시 사진이 날아가면 복구가 무의미하다)
- **명시적 "임시저장" 버튼은 없다.** 항상 켜져 있고, 대신 나가기 시점에 의사를 묻는다
- **[뒤로] 3지선다:** `계속 편집` / `임시저장하고 나가기` / `삭제하고 나가기`
- **크래시·강제 종료 후 재실행:** 모음집 상세 진입 시 "이어서 만들까요?" 배너. 무시해도 초안은 유지되며, **24시간 방치 시 "이어서 작성" 알림**(11.3)
- **초안은 모음집당 1개.** 다른 캔버스를 새로 만들려 하면 "만들던 캔버스가 있어요 — 이어서 / 버리고 새로"를 묻는다. 여러 초안을 허용하면 초안 목록 UI가 필요해지는데 P0에 그럴 값어치가 없다. 뒤집으려면 `Drafts/` 하위를 모음집별 다중 폴더로 바꾸고 목록 화면을 추가하면 되므로 **P1에서 되돌릴 수 있는 결정**이다

### 6.6 저장 (승격) 처리 순서

```
1. 검증        레이어 상한 · 사진 슬롯 · 손상 레이어 제거
2. 렌더        ImageRenderer(scale 1.0) → renderedPNG   ※ autoreleasepool
3. 사진 이관    Drafts/ 사본 → CanvasPhoto (2000px, externalStorage)
4. DB 쓰기     Canvas 삽입(또는 갱신) + Collection 연결 + updatedAt
5. 표지 갱신    Collection.coverCanvasID 가 비어 있으면 이 캔버스로
6. 정리        Drafts/<uuid>/ 폴더 삭제
7. 실패 시     draft 폴더를 그대로 두고 "저장에 실패했어요, 다시 시도해 주세요"
```

**2~5가 전부 성공해야 6을 실행한다.** 순서를 바꿔 초안을 먼저 지우면 저장 실패 시 작업물이 증발한다.

### 6.7 수정 (재편집)

- 뷰어 → [편집] → `layoutJSON` 로드 → **새 초안 세션 시작.** 원본 `Canvas`는 저장 전까지 손대지 않는다
- [저장] → 6.6과 같은 순서, 단 4번이 갱신이고 `renderedPNG` **재생성**
- **[취소] → 초안 폐기, 원본 그대로.** 편집 중 앱이 죽어도 원본은 무사하다
- 편집 중 **제거된 사진 레이어의 `CanvasPhoto`는 저장 시점에 정리**한다(고아 레코드가 externalStorage 용량을 계속 먹는다)
- **메타 수정 시트**(제목·날짜·소속 모음집 이동)는 에디터를 거치지 않고 뷰어에서 바로. `renderedPNG` 재생성이 필요 없다
- **소속 모음집을 옮길 때는 양쪽 모음집의 표지를 모두 재계산한다.** 옮겨간 캔버스가 원래 모음집의 대표였다면 `coverCanvasID`를 비워 최근 캔버스로 승계시키고, 목적지 모음집이 비어 있었다면 이 캔버스를 대표로 지정한다. 이 처리를 빠뜨리면 원래 모음집 표지가 **다른 모음집에 있는 캔버스를 계속 가리킨다**

### 6.8 삭제

| 대상 | 확인 | 처리 |
|---|---|---|
| 레이어 | 없음 | 즉시 삭제 + 스낵바 "실행 취소"(5초) |
| 캔버스 | "이 캔버스를 삭제할까요?" | `CanvasPhoto` cascade → 대표 캔버스였으면 `coverCanvasID`를 비우고 최근 캔버스로 자동 승계 |
| 모음집 (빈) | "삭제할까요?" | 즉시 |
| 모음집 (캔버스 N장) | **"캔버스 N장이 함께 삭제됩니다"** | cascade. 되돌릴 수 없음을 문구로 명시 |
| 초안 | "만들던 캔버스를 삭제할까요?" | 폴더 삭제 |

**휴지통은 두지 않는다.** 확인 다이얼로그 + 레이어 단위 실행취소로 충분하고, 휴지통은 "삭제했는데 iCloud 용량이 안 줄어요"라는 민원을 부른다.

### 6.9 엣지 케이스

구현 착수 전에 답이 있어야 하는 것들이다. 여기서 비워두면 구현 중에 각자 다르게 처리되고, 그때는 이미 여러 파일에 흩어진 뒤다.

#### 조작 · 좌표

| 상황 | 동작 |
|---|---|
| **레이어를 캔버스 밖으로 밀어냄** | **캔버스 경계에서 잘려 보이고, 다시 밀어 넣으면 그대로 돌아온다.** 밖으로 나간 부분은 에디터에서 30% 고스트로 표시하고 익스포트에서는 제외한다 (5.10) |
| **레이어가 화면에서 완전히 사라짐** | 줌 아웃(최소 50%) 또는 캔버스 팬으로 작업 영역까지 보고 잡아 끌어온다. 레이어 중심은 **작업 영역(캔버스의 2배) 밖으로는 못 나간다** |
| 레이어가 캔버스보다 큼 | 핸들을 화면 안쪽으로 인셋해 그린다. 박스 변이 화면 밖이면 그 변의 핸들은 가장 가까운 화면 안쪽 지점에 붙인다 |
| 레이어를 최소 크기까지 축소 | 짧은 변 논리 40px에서 정지. 변 핸들 → 코너 핸들 순으로 숨기거나 바깥으로 밀어낸다 (5.7) |
| 회전 상태에서 코너 핸들 드래그 | 역회전 행렬로 로컬 좌표 변환 후 계산 (스파이크 S1) |
| 회전된 레이어의 스마트 가이드 | **정렬·간격 가이드 대상에서 제외.** 회전체의 바운딩 박스는 실제 형태와 어긋난다 (5.8.2) |
| 핀치와 핸들 드래그가 동시에 인식됨 | 제스처 인식기를 배타로 묶어 먼저 시작된 쪽만 유지 |
| 줌 상태에서 레이어 조작 | 핸들은 화면 오버레이라 크기 불변. 스냅 임계는 화면 좌표 기준 8pt |
| 겹친 레이어 선택 | z 최상단이 선택된다. 아래 것을 잡으려면 위 레이어를 **뒤로 보내기**로 내린다 (5.11) |
| 여러 가이드에 동시에 걸림 | 햅틱은 한 번만. 붙어 있는 동안 재발화 없음 (enter 이벤트에만) |
| 텍스트 박스 폭을 한 글자 미만으로 축소 | 가장 긴 글자 폭을 하한으로 정지 |
| **기기 회전 (세로 ⇄ 가로)** | 레이어 논리좌표는 불변. 선택 상태·팬 오프셋은 유지하되 **줌 배율을 새 fit 기준으로 재계산**한다 (1.2) |

#### 저장 · 초안

| 상황 | 동작 |
|---|---|
| 저장 중 백그라운드 진입 | `beginBackgroundTask`로 렌더·쓰기 완주 보장 |
| 저장 중 저장공간 부족 | 초안 유지 + 안내. 사진 추가 시점에도 사전 체크 |
| 저장 중 강제 종료 | 6.6의 순서상 초안이 아직 남아 있다 → 재실행 시 "이어서 만들까요?" |
| **크래시로 남은 고아 초안 폴더** | **앱 시작 시 `Drafts/` 스캔 → 소속 모음집이 없거나 7일 이상 방치된 폴더 삭제.** 정리하지 않으면 사진 사본이 계속 쌓여 사용자가 원인을 알 수 없는 용량을 먹는다 |
| 편집 중이던 모음집이 다른 기기에서 삭제됨 | 저장 시점에 소속 모음집 존재를 확인, 없으면 "모음집이 삭제됐어요. 어디에 저장할까요?" |
| 메모리 경고 수신 | 초안을 즉시 flush(디바운스 무시)하고 캐시된 썸네일을 비운다 |
| `renderedPNG` 없는 캔버스 (저장 부분 실패) | 그리드·표지에서 플레이스홀더. 뷰어 진입 시 `layoutJSON`으로 재생성 시도 |

#### 동기화 · 데이터

| 상황 | 동작 |
|---|---|
| **두 기기에서 같은 캔버스를 편집** | **last-write-wins, 판정 시점은 「저장을 누른 순간」.** 병합하지 않는다. 편집 중에는 초안이 로컬 파일이라(6.2) CloudKit에 아무것도 올라가지 않으므로, **충돌 가능 구간이 저장 트랜잭션 한 순간으로 좁혀진다.** 두 기기에서 몇 시간씩 나란히 편집해도 실제로 부딪히는 것은 저장 시각이 겹칠 때뿐이며, 그때는 나중에 누른 쪽이 이긴다 |
| 두 기기에서 모음집 순서를 동시 변경 | `sortIndex` 중복 시 `createdAt` 오름차순으로 타이브레이크 |
| 캔버스 삭제 시 그것이 대표였음 | `coverCanvasID`를 비우고 가장 최근 캔버스로 자동 승계 |
| **캔버스를 다른 모음집으로 이동** | 양쪽 모음집 표지를 모두 재계산 (6.7) |
| 대표로 지정된 캔버스가 다른 기기에서 삭제됨 | `coverCanvasID`가 가리키는 대상이 없으면 빈 값으로 간주해 최근 캔버스로 폴백 |
| iCloud 미로그인·용량 초과 | 로컬 모드 자동 격하 + 설정에 배너. 초안은 원래 로컬이라 영향 없음 |

#### 입력 한계

| 항목 | 상한 | 비고 |
|---|---|---|
| 모음집 이름 | 1~20자 | `Character` 단위(이모지 1자 = 1) |
| 캔버스 제목 | 0~40자 | 비어 있으면 날짜로 표시 |
| `text` 레이어 문자열 | 200자 | 초과 시 입력 차단 |
| 기록 날짜 | 미래 날짜 허용 | 예약 기록을 막을 이유가 없다 |

**상한은 이 셋뿐이다.** 도형 내부 텍스트는 기능 자체가 없고(5.3), 나머지는 레이어 개수 상한(5.13)으로 이미 통제된다.

#### 기타

| 상황 | 동작 |
|---|---|
| 레이어 상한 도달 | 해당 도구 비활성화 + 안내 |
| **상한 도달 상태에서 복제 시도** | [복제] 버튼 비활성화 + 같은 안내 문구 |
| **클립보드에 이미지가 없음** | [붙여넣기] 비활성화 |
| 사진 앱 저장 권한 거부 | 설정 이동 안내. 캔버스는 이미 저장돼 있으므로 손실 없음 |
| 같은 캔버스를 반복 저장 | 중복 저장 허용 (사진 앱의 정상 동작) |
| 잠금 상태에서 알림 탭 | Face ID 인증 후 해당 캔버스로 이동 |
| 번들 폰트 로드 실패 | 시스템 폰트 폴백. `layoutJSON`의 `font` 값은 보존해 다음 실행에서 복구 |

## 7. 데이터 모델

```swift
@Model final class Collection {
    var id: UUID = UUID()
    var name: String = ""
    var createdAt: Date = Date()
    var sortIndex: Int = 0              // 생성순 기본, 사용자 재배치 반영
    var coverCanvasID: String = ""      // 비면 가장 최근 캔버스가 표지
    var canvases: [Canvas]? = []
}

@Model final class Canvas {
    var id: UUID = UUID()
    var aspect: Int = 0                 // 0 = 4:5(1080×1350), 1 = 9:16(1080×1920)
    var title: String = ""
    var createdAt: Date = Date()        // 사용자가 지정하는 기록 날짜
    var updatedAt: Date = Date()
    var layoutJSON: Data = Data()
    var photos: [CanvasPhoto]? = []
    @Attribute(.externalStorage) var renderedPNG: Data?   // 캐시, 재편집 시 재생성
    var collection: Collection?
}

@Model final class CanvasPhoto {
    var id: UUID = UUID()
    @Attribute(.externalStorage) var data: Data = Data()  // 원본 2000px 사본 → CKAsset
    var canvas: Canvas?
}
```

**v3에서 삭제된 필드:** `regionCode` · `provinceCode` · `colorIndex`, 그리고 `ShelfPreference` 모델 전체.
**추가된 것:** `Collection` 모델, `Canvas.aspect`, `Canvas.collection` 관계.

### 7.1 설계 판단

- **`coverCanvasID`를 관계가 아니라 문자열로** — `Collection → Canvas` 관계가 이미 있는데 대표 캔버스로 관계를 하나 더 걸면 CloudKit에서 순환 참조 구성이 까다로워진다. UUID 문자열 한 개로 충분하고, 대상이 삭제돼도 빈 문자열 취급하면 안전하게 폴백된다.
- **`aspect`를 Int 열거값으로** — 폭·높이를 직접 저장하면 이후 프리셋을 추가할 때 기존 데이터의 유효성을 재검증해야 한다. 열거값은 앱 상수 테이블을 갈아 끼우면 끝난다.
- **사진 사본 포맷은 알파 유무로 가른다** — 불투명하지 않은 픽셀이 하나라도 있으면 PNG, 없으면 JPEG 0.9. 전부 JPEG로 저장하면 「피사체 들어올리기」로 가져온 투명 배경이 **저장 후 흰 사각형이 된다**(5.12.3). 반대로 전부 PNG로 저장하면 일반 사진 용량이 몇 배가 된다.
- **사진 복제는 `CanvasPhoto`를 새로 만들지 않는다** — 레이어가 `assetId`로 같은 사진을 참조한다. 한 사진을 다섯 번 써도 저장 용량과 디코딩 메모리는 한 장분이다. 저장 시 고아 정리는 **어떤 레이어도 참조하지 않는 `CanvasPhoto`** 를 기준으로 판정해야 한다 — 레이어 하나를 지웠다고 지우면 나머지 복제본이 깨진다.

### 7.2 CloudKit 제약

전 속성 기본값 또는 optional · `@Attribute(.unique)` 불가 · 관계는 양방향 optional · **첫 심사 전 스키마 동결 후 additive-only** · iCloud 미로그인/용량 초과 시 로컬 모드 자동 격하 + 설정에 상태 배너.

## 9. 저장 · 익스포트

```
논리 캔버스 1080×(1350|1920) → ImageRenderer(scale: 1.0) → JPEG 0.9
   → PHPhotoLibrary 직접 저장
```

- **P0의 내보내기는 「사진에 저장」 하나다.** 저장 완료 화면과 뷰어에 버튼으로 노출한다.
- **최종 결과물은 흰 배경 위에 합성되므로 JPEG로 내보내도 무방하다.** 투명 배경 레이어가 있어도 캔버스 배경이 불투명 흰색이라 알파가 남지 않는다. 사진 *사본*의 저장 포맷(§7.1)과는 별개 문제다.
- `NSPhotoLibraryAddUsageDescription` 필요. 권한 거부 시 설정 이동 안내.
- 워터마크 없음.
- **공유(인스타그램·스레드·카카오톡)는 P1로 미룬다.** 각각 사정이 다르기 때문이다 — 인스타그램은 스토리 딥링크(`instagram-stories://share`)만 공식 지원되고 피드 게시는 API가 없다. 스레드는 공식 이미지 딥링크가 없어 시스템 공유 시트를 경유해야 한다. 카카오톡은 Kakao SDK + 디벨로퍼스 앱 등록 + 네이티브 앱키가 필요하다. P1에서 붙일 때는 **시스템 공유 시트 + 인스타 스토리 딥링크**를 먼저 검토한다(둘 다 외부 SDK 의존이 없다).

## 10. 검색

**모음집 이름과 캔버스 제목을 한 필드에서 통합 검색**한다. 결과는 모음집 섹션 / 캔버스 섹션으로 구분해 표시하고, 각각 해당 화면으로 이동한다. 무제목 캔버스는 날짜로 걸린다.

| 데이터 | iCloud 동기화 상태·사용 용량, 백업 zip 내보내기/가져오기, 캐시 정리 |
| 정보 | **폰트 OFL 고지 5종**, 오픈소스, 개인정보 처리방침, 문의(mailto), 앱 평가(`SKStoreReviewController`), 버전 |

**Face ID 잠금이 켜져 있으면 앱 스위처 스냅샷도 가린다.** 덮는 시점은 **`scenePhase == .inactive`**다 — `.background`에서만 덮으면 위로 스와이프해 앱 스위처를 여는 동안 화면이 그대로 노출된다. `.active`로 돌아올 때 인증을 요구하고, 인증 전까지 커버를 유지한다.

## 12. 첫 실행

온보딩 화면 없음. 캐러셀에 **[+ 새 모음집] 카드 하나**와 고스트 힌트("첫 모음집을 만들어보세요", 탭하면 사라짐).

v3에서는 회색 콜렉트북 17권이 화면을 채워 빈 상태가 자연스러웠지만, **v4의 첫 화면은 카드 한 장뿐이라 심사자에게 미완성으로 읽힐 위험이 있다.** 대응으로 **샘플 모음집 1개(캔버스 2~3장)를 첫 실행 시 생성**하고, 사용자가 삭제할 수 있게 한다. 샘플 이미지는 번들 자산이며 저작권이 정리된 것만 쓴다.

**샘플은 일반 `Canvas`로 생성되므로 통계(11.1)와 검색(10장)에 그대로 잡힌다.** 별도 플래그를 두어 제외하면 모든 쿼리에 필터를 달아야 하고(6.2와 같은 이유), 사용자가 삭제하면 자연히 사라지므로 그대로 둔다.

## 16. 테스트

- 레이어 JSON 인코딩 → 디코딩 라운드트립 (5종 전부, 캔버스 밖 좌표를 가진 레이어 포함)
- 회전 상태 드래그 좌표 변환
- **코너 핸들 드래그 시 대각 반대편 코너가 고정점으로 유지되는가** (회전 0°·45°·90° 각각)
- **변 핸들이 `photo`·`stamp`·`drawing`에는 나타나지 않는가**
- **캔버스 밖으로 나간 레이어가 익스포트에서는 잘리고, 다시 안으로 옮기면 온전히 복원되는가**
- 레이어 중심이 작업 영역(캔버스 2배) 밖으로 나가지 않는가
- 크기 하한(짧은 변 40px)·상한(캔버스 긴 변 ×4)에서 정지하는가
- 회전 15° 스냅이 ±3° 범위에서 흡착되는가
- **정렬·균등 간격·크기 일치 가이드가 각각 올바른 지점에서 발화하는가**
- **회전된 레이어가 정렬·간격 가이드 후보에서 제외되는가**
- **여러 가이드에 동시에 걸려도 햅틱이 한 번만 발화하는가**
- z-order 4종(맨 앞/앞/뒤/맨 뒤) 후 z 값이 0부터 촘촘히 재정렬되는가
- 캔버스 줌 200% 상태에서 핸들의 화면상 크기와 히트 영역이 100%일 때와 같은가
- 선택 유무에 따라 핀치가 레이어/캔버스로 올바르게 갈라지는가
- **기기를 회전해도 레이어 논리좌표가 변하지 않고, 줌 배율만 새 fit 기준으로 재계산되는가**
- 재편집: 저장 → 로드 → 재저장 시 레이아웃 불변
- **초안 승격:** 저장 성공 시에만 `Drafts/` 폴더가 삭제되는가
- **저장 실패 시** 초안이 보존되는가
- **재편집 취소 시** 원본 `Canvas`와 `renderedPNG`가 변하지 않는가
- **제거된 사진 레이어의 `CanvasPhoto`가 저장 시점에 정리**되는가
- 캔버스 삭제 시 대표 캔버스였다면 `coverCanvasID`가 자동 승계되는가
- **캔버스를 다른 모음집으로 옮길 때 양쪽 표지가 모두 재계산되는가**
- **앱 시작 시 고아 초안 폴더(소속 모음집 없음 / 7일 초과)가 정리되는가**
- 모음집 cascade 삭제 시 `Canvas`·`CanvasPhoto`가 모두 정리되는가
- 두 비율(4:5 / 9:16) 각각의 익스포트 크기가 정확한가
- 레이어 0개 캔버스의 익스포트·썸네일이 흰 배경만으로 정상 생성되는가
- 무제목 캔버스가 목록에서 날짜로 표시되는가
- 타입별 레이어 상한 도달 시 해당 도구가 비활성화되는가
- **레이어 복제 시 모든 속성이 승계되고 +40,+40 오프셋에 놓이며 복제본이 선택되는가** (5종 전부)
- **사진 복제본이 `assetId`를 공유해 `CanvasPhoto`가 늘어나지 않는가**
- **복제본 하나를 지워도 나머지가 참조하는 `CanvasPhoto`는 남는가**
- 상한 도달 시 [복제]가 비활성화되는가
- 클립보드 이미지 붙여넣기가 2000px 사본으로 정규화되는가
- **투명 배경 PNG를 붙여넣고 저장 → 재실행 시 투명도가 보존되는가** (흰 사각형이 되지 않는가) — **붙여넣기 직후 / 저장 직후 / 앱 재실행 후 / 재편집 진입 후 4시점 모두**
- **2000px 리사이즈가 `opaque = false`로 수행되는가** (여기서 죽으면 이후 PNG로 저장해도 못 살린다)
- **투명 레이어에 톤 필터를 적용해도 알파가 유지되는가**
- **알파 채널은 있으나 전부 불투명한 이미지(스크린샷)는 JPEG로 저장되는가** (불필요한 PNG 용량 증가 방지)
- 여백이 큰 투명 PNG를 붙여넣으면 알파 트림 후 바운딩 박스가 피사체에 맞는가
- 완전 투명 이미지를 붙여넣으면 거부되고 토스트가 뜨는가
- 투명 레이어가 있는 캔버스의 익스포트 결과가 흰 배경으로 합성되는가
- 번들 폰트 5종이 모두 로드되고, 없을 때 시스템 폰트로 폴백되는가
- CloudKit 동기화 실기기 2대 수동 검증 (초안이 동기화되지 **않는지** 포함)

## 18. 구현 순서

```
S1(제스처 · 선택 UI · 스마트 가이드) 스파이크
  → 데이터 레이어 (SwiftData + CloudKit, Collection ↔ Canvas)   ← S2를 여기서 함께 검증
  → 초안 저장소 (Drafts/ 파일 I/O + 승격 로직)      ← UI 없이 단위 테스트로 완성
  → S3(폰트 번들) 스파이크
  → 에디터 (레이어 5종 · 복제·붙여넣기 · 필터 · 폰트, 공수 45%)
  → 모음집 홈 · 상세
  → 저장 · 재편집 · 뷰어 · 사진에 저장
  → 검색
  → 내 정보 · 설정 · 알림
  → 잠금 · 백업
```

초안 저장소를 에디터보다 앞에 두는 이유는, 파일 I/O와 승격 트랜잭션이 **UI 없이 완전히 테스트 가능한 순수 로직**이면서 에디터 전체가 그 위에 얹히기 때문이다.

## 21. 남은 리스크

1. **차별점 공백 (최대 리스크).** v3는 색 수집 메커닉 하나에 차별점을 몰아뒀는데 그것이 사라졌다. 이제 Crsel·STIT 같은 기성 꾸미기 앱과 **에디터 품질로 정면 승부**하게 되며, "모음집으로 묶인다"는 구조만으로 충분한지는 검증되지 않았다. 설계로 메울 수 있는 종류가 아니므로 초기 사용자 반응으로 판단해야 한다.
2. **빈 앱의 첫인상.** 지역 230칸이 "채워야 할 목록"으로 동기를 주던 자리가 비었다. 12장의 샘플 모음집이 완화책이지만, 재방문 동기를 무엇으로 만들지는 미해결이다.
3. **폰트 용량.** 서브셋 후 실측이 필요하다(S3). 5종이 예상보다 크면 P0를 3종으로 줄이거나 ODR을 앞당긴다.
4. **CloudKit 스키마 동결.** 첫 심사 전 `Collection` 포함 모델을 확정해야 한다. 특히 P2의 "캔버스 다중 모음집 소속"은 관계 구조를 바꾸므로, 지금 스키마에서 additive-only로 도달 가능한지 미리 확인해 둘 것.
5. **선택 UI 구현 난이도(S1).** 바운딩 박스·다중 핸들·캔버스 줌·제스처 배타 처리는 서로 얽혀 있어 하나를 고치면 다른 하나가 깨지는 종류의 코드다. v3에서 사라진 기술 리스크 자리를 이것이 대신 채웠다. **에디터 본체보다 먼저 스파이크로 뼈대를 세우고, 그 위에 도구를 얹는 순서를 지킬 것**(18장).
