# sync (저장 · 동기화)

다른 도메인이 부르는 저장소. SwiftData + CloudKit, 초안 파일 I/O, 백업을 담당한다. **도메인 규칙은 담지 않는다.**

## 배경

서버도 계정도 없는 앱이므로 데이터의 집은 두 곳뿐이다.

| 저장소 | 담는 것 | 동기화 |
|---|---|---|
| **SwiftData + CloudKit** | `Collection` · `Canvas` · `CanvasPhoto` | 사용자의 iCloud 계정으로 기기 간 자동 |
| **`Drafts/` 로컬 파일** | 편집 중인 초안 (`layout.json` + 사진 사본) | **없음. 기기 로컬 전용** |

이 분리가 v4에서 가장 중요한 저장 설계다. v3는 초안까지 SwiftData에 넣었는데, 그러면 미완성 캔버스가 CloudKit을 타고 다른 기기로 흘러간다.

## 안 하면 어떻게 되는가

**CloudKit 스키마는 첫 심사 후 additive-only로 얼어붙는다.** 속성 타입 변경, 삭제, 관계 구조 변경이 전부 막힌다. 지금 잘못 정한 모델은 앱 수명 내내 짊어져야 한다. 그래서 심사 전에 반드시 실기기 2대로 검증해야 한다(스파이크 S2).

**초안을 DB에 두면** 미완성 캔버스가 다른 기기에 뜨고, 모든 쿼리에 `isDraft == false` 필터가 붙고, 폐기가 레코드 삭제 + 관계 정리 + 사진 GC로 번진다.

## 사용자와 규모

20~30대 여성, 인스타그램 공유층. iCloud 무료 5GB를 쓰는 사용자가 다수일 것으로 가정한다.

사진이 캔버스당 최대 8장 × 2000px 사본이므로, **용량 초과가 현실적인 시나리오다.** 그래서 로컬 모드 격하와 상태 배너가 P0에 들어간다.

## 성공 기준

- 기기 2대에서 만든 캔버스가 **양방향으로 보인다**
- iCloud 미로그인·용량 초과에서도 **앱이 정상 동작한다** (로컬 모드)
- **초안은 절대 동기화되지 않는다**
- 첫 심사 전 스키마가 확정되어 이후 additive-only로 버틸 수 있다

## 핵심 결정

| 결정 | 근거 |
|---|---|
| 전 속성 **기본값 또는 optional** | CloudKit 제약 |
| **`@Attribute(.unique)` 사용 불가** | CloudKit 제약. 유일성은 앱 로직으로 |
| 관계는 **양방향 optional** | CloudKit 제약 |
| **초안은 SwiftData 밖** | 위 "안 하면 어떻게 되는가" |
| 동시 편집은 **last-write-wins, 판정 시점은 「저장을 누른 순간」** | 병합하지 않는다. 편집 중에는 초안이 로컬 파일이라 CloudKit에 아무것도 올라가지 않으므로, **충돌 가능 구간이 저장 트랜잭션 한 순간으로 좁혀진다.** 두 기기에서 몇 시간씩 나란히 편집해도 실제로 부딪히는 것은 저장 시각이 겹칠 때뿐이다 |
| 큰 바이너리는 **`.externalStorage`** | `renderedPNG` · 사진 원본. CKAsset으로 올라간다 |
| 책장 순서를 배열이 아닌 **`sortIndex` Int** | SwiftData + CloudKit에서 배열 속성은 스키마 제약에 걸릴 여지가 있다. 첫 심사 이후 additive-only로 묶이는 스키마에서 위험을 질 이유가 없다 |
| 레이어 정보는 **`layoutJSON` 한 덩어리** | v2부터 유지되는 확정. 레이어 스펙이 아무리 늘어도 CloudKit 스키마를 건드리지 않는다 — v4에서 `shape` 레이어와 스마트 가이드 관련 속성이 추가됐지만 스키마는 그대로였다 |
| iCloud 실패 시 **로컬 모드 자동 격하** | 앱이 멈추지 않는다. 설정에 상태 배너만 띄운다 |
