# media (미디어)

사진을 가져오고, 색을 입히고, 최종 이미지로 내보낸다. 레이어에 들어갈 **픽셀**을 다루는 도메인.

## 배경

editor가 레이어의 위치·크기·순서를 다룬다면 media는 그 안에 들어갈 내용을 다룬다. 경계는 "좌표냐 픽셀이냐"다.

v4에서 두 가지가 바뀌었다.

**1. 내보내기 축소.** v3는 시스템 공유 시트를 경유했지만, v4 P0는 **사진 앱 저장 하나**로 줄였다. 인스타그램·스레드·카카오톡 공유는 P1로 미뤘는데, 셋의 사정이 전부 다르기 때문이다.

| 대상 | 사정 |
|---|---|
| 인스타그램 | 스토리 딥링크(`instagram-stories://share`)만 공식 지원. **피드 게시는 API가 없다** |
| 스레드 | **공식 이미지 딥링크가 없다.** 시스템 공유 시트를 경유해야 한다 |
| 카카오톡 | Kakao SDK + 디벨로퍼스 앱 등록 + 네이티브 앱키 필요 |

시스템 공유 시트를 띄우면 기기에 깔린 세 앱이 자동으로 상단에 뜨므로, 사용자 입장에서는 전용 버튼 없이도 셋 다 된다. P1에서 붙일 때는 **공유 시트 + 인스타 스토리 딥링크**를 먼저 검토한다(둘 다 외부 SDK 의존이 없다).

**2. 누끼(배경 제거) 제외.** v3~v4 초안까지 P0였으나 2026-08-10에 뺐다. 아래 「누끼를 왜 뺐는가」 참조.

## 안 하면 어떻게 되는가

**내보내기가 없으면 만든 것을 밖으로 꺼낼 수 없다.** 인스타 공유가 타깃 사용자의 목적 그 자체이므로, 저장이 안 되면 앱을 쓸 이유가 없다.

**복사·붙여넣기가 없으면** 같은 사진을 두 번 쓰려고 PHPicker를 다시 열어야 하고, 다른 앱에서 복사한 이미지를 넣을 방법이 아예 없다.

## 누끼를 왜 뺐는가

Vision 온디바이스라 **비용은 0원**이었지만 딸려오는 것이 많았다.

| 딸려오는 것 | 내용 |
|---|---|
| 처리 규칙 6단계 | 지원 확인 · 비동기 · 인디케이터 · 취소 · 10초 타임아웃 · 실패 원복 |
| 트림과 위치 보정 | 트림하지 않으면 바운딩 박스가 투명 여백까지 잡아 **핸들이 피사체에서 떨어진다.** 트림하면 위치가 튀지 않게 `x, y`를 보정해야 한다 |
| 데이터 모델 확장 | 원본 보존을 위한 `cutoutPNG` 별도 필드 + 메모리 두 배 |
| 품질 편차 | 머리카락 가장자리 · 유리 · 배경과 유사한 색은 거칠게 잘린다. 수동 브러시가 사실상 세트로 필요했다 |

**그리고 결정적으로, OS가 이미 같은 것을 제공한다.**

iOS 사진 앱의 **「피사체 들어올리기」**(사진을 길게 눌러 배경에서 분리)로 복사한 뒤 우리 앱에 붙여넣으면 **투명 배경 이미지가 그대로 들어온다.** 붙여넣어진 것은 평범한 `photo` 레이어이므로 바운딩 박스·핸들·회전이 전부 동작한다. 사용자 입장에서는 "누끼 → 크기 조절"이 그대로 되는 셈이고, 앱은 아무것도 구현하지 않는다.

**P0 범위를 좁히기 위해 기능 자체를 제외했다.** 다시 넣는다면 `layoutJSON`에 `cutout` 플래그와 `CanvasPhoto.cutoutPNG` optional 필드를 추가하는 것으로 시작한다 — 후자는 CloudKit additive-only 제약 아래에서도 가능하다.

### 대신 반드시 지켜야 할 것

OS 경로에 기대는 대신, 붙여넣기 파이프라인이 투명 이미지를 제대로 다뤄야 한다. **여기가 무너지면 누끼를 뺀 결정 자체가 무의미해진다.**

**1. 알파 보존 — 붙여넣을 때 투명한 것이 저장 후에도 투명해야 한다.** 불일치는 기능 오류로 간주한다.

알파가 죽는 지점이 셋인데, **가장 흔한 것은 저장 포맷이 아니라 리사이즈다.** `opaque = true`로 2000px 정규화를 하면 그 순간 투명 영역이 배경색으로 구워지고, 이후 PNG로 저장해도 되살릴 수 없다. 포맷 분기(PNG/JPEG)는 필요조건이지 충분조건이 아니다. 상세 규칙은 [architecture.md](architecture.md) 참조.

**2. 알파 트림** — 여백이 큰 투명 PNG는 바운딩 박스가 투명 영역까지 잡아 **핸들이 피사체에서 떨어진다.** 붙여넣는 순간 알파 바운딩 박스로 한 번 크롭한다. 폐기한 누끼의 트림과 달리 되돌릴 원본도 유지할 상태도 없어 비용이 사실상 없다.

**안내·힌트는 두지 않는다.** 복사·붙여넣기가 제대로 동작하는 것으로 충분하다.

## 사용자와 규모

20~30대 여성, 인스타그램 공유층. 캔버스당 사진 최대 8장, 원본은 2000px 사본으로 보관.

## 성공 기준

- 익스포트 결과가 인스타그램에 올렸을 때 재압축으로 뭉개지지 않는다
- 같은 사진을 다섯 번 써도 저장 용량과 디코딩 메모리가 **한 장분**이다
- 다른 앱에서 복사한 이미지를 **권한 프롬프트 없이** 붙여넣을 수 있다
- **사진 앱에서 피사체만 떠서 복사한 것이 투명 배경 그대로 들어오고, 저장 후 다시 열어도 투명하다**

## 핵심 결정

| 결정 | 근거 |
|---|---|
| 사진은 **2000px 사본**으로 저장 | 원본을 그대로 들고 있으면 CloudKit 용량과 디코딩 메모리가 함께 터진다 |
| **리사이즈 시 `opaque = false` 강제** | 알파 소실 1순위 지점. 여기서 죽으면 이후 무엇을 해도 못 살린다 |
| **사본 포맷은 투명 픽셀 유무로 가름** (PNG / JPEG) | 전부 JPEG면 투명 배경이 흰 사각형이 되고, 전부 PNG면 일반 사진 용량이 몇 배가 된다 |
| 판정은 **채널 유무 + 64×64 다운샘플 스캔** 2단계 | 채널만 보면 스크린샷까지 PNG가 되고, 400만 픽셀 전수 스캔은 비싸다 |
| **붙여넣기 시 알파 트림 1회** | 여백 큰 투명 PNG에서 핸들이 허공에 뜨는 것을 막는다. 되돌릴 상태가 없어 비용이 없다 |
| 익스포트는 **흰 배경 합성 후 JPEG** | 캔버스 배경이 불투명 흰색이라 알파가 남지 않는다. 사본 포맷과는 별개 문제 |
| **사진 복제는 `assetId` 공유** | 같은 원본을 참조하므로 데이터가 두 배로 늘지 않는다. `filter`·`opacity`는 레이어별 독립 |
| 고아 `CanvasPhoto` 판정은 **어떤 레이어도 참조하지 않을 때** | 레이어 하나 지웠다고 지우면 나머지 복제본이 깨진다 |
| 붙여넣기는 **`UIPasteControl`** | iOS 16+에서 `UIPasteboard`를 직접 읽으면 허용 프롬프트가 매번 뜬다. `UIPasteControl`은 버튼을 누른 것 자체를 동의로 간주한다 |
| 붙여넣은 이미지도 **2000px 정규화** | 일반 사진과 동일한 경로로 다룬다 |
| 익스포트는 **`scale: 1.0` + JPEG 0.9** | 논리 캔버스가 이미 1080폭이라 스케일 업이 필요 없다 |
| 익스포트를 **`autoreleasepool`로 감쌈** | 피크 메모리를 낮춘다 |
| **워터마크 없음** | |
| P0 내보내기는 **사진 앱 저장 하나** | 위 표의 사정. 공유는 P1 |
| **누끼 제외** | 위 「누끼를 왜 뺐는가」 |
