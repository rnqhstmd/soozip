# media 아키텍처

## 파이프라인

```
사진 투입 경로 2가지
 ├─ PHPicker (최대 8장, 남은 슬롯만큼)
 └─ UIPasteControl (클립보드 이미지)
        │    └─ 알파 있으면 트림 1회 (0×0이면 거부)
        ↓
   2000px 사본 생성
        └─ 불투명하지 않은 픽셀 있음 → PNG
           없음                    → JPEG 0.9
        ↓
   Drafts/<uuid>/photos/ 즉시 기록      ← 디바운스 제외
        ↓
   photo 레이어로 계단식 배치
        └─ [필터] Core Image 톤 매핑 (12종 × 강도)

저장 시
  → CanvasPhoto (externalStorage) 로 이관 → CKAsset 동기화
  → 고아 CanvasPhoto 정리 (어떤 레이어도 참조하지 않는 것)

내보내기
  논리 캔버스 1080×(1350|1920)
    → ImageRenderer(scale: 1.0)          ※ autoreleasepool
    → JPEG 0.9
    → PHPhotoLibrary 직접 저장
       └─ [P1 슬롯] 시스템 공유 시트 / 인스타 스토리 딥링크 / Kakao SDK
```

## 사진 복제와 참조 공유

```
CanvasPhoto (assetId: A)
     ↑         ↑         ↑
  layer1    layer2    layer3      ← 복제로 만들어진 세 레이어
  filter:5  filter:9  filter:nil  ← 레이어 속성은 각자 독립
```

- 복제해도 `CanvasPhoto`는 늘지 않는다. **저장 용량과 디코딩 메모리는 한 장분**
- `photo` 레이어 상한 8개에는 복제본도 포함된다. 메모리상 여유가 있지만 "사진은 8장까지"라는 안내를 일관되게 유지하는 편이 낫다
- **고아 정리 판정은 참조 카운트 기준.** layer2 하나를 지웠다고 `CanvasPhoto`를 지우면 layer1·layer3이 깨진다

## 데이터 모델

```swift
@Model final class CanvasPhoto {
    var id: UUID = UUID()
    @Attribute(.externalStorage) var data: Data = Data()  // 원본 2000px 사본 → CKAsset
    var canvas: Canvas?
}
```

누끼 제외로 `cutoutPNG` 필드가 사라졌다. 나중에 누끼를 되살린다면 optional 필드 추가라 CloudKit additive-only 제약에서도 가능하다.

## 메모리

병목은 익스포트 출력이 아니다 — 1080×1920 RGBA는 약 8MB에 불과하다. 실제 압박은 **디코딩된 비트맵**이다.

- 2000px 사진 한 장 디코딩 ≈ 16MB
- 그래서 `photo` 상한이 8개 (editor 도메인)
- 누끼가 빠지면서 "누끼 뜨면 두 배" 압박은 사라졌다

## 클립보드 붙여넣기

- 사진 도구 안의 **[붙여넣기]** — 클립보드에 이미지가 있을 때만 활성화
- **`UIPasteControl`을 쓴다.** iOS 16+에서 `UIPasteboard`를 직접 읽으면 시스템 허용 프롬프트가 매번 뜨는데, `UIPasteControl`은 사용자가 버튼을 누른 것 자체를 동의로 간주한다
- 텍스트 클립보드는 다루지 않는다. 텍스트 레이어 입력 시트에서 시스템 기본 붙여넣기가 이미 동작한다

## 투명 배경 이미지 — 누끼의 대체 경로

**iOS 사진 앱의 「피사체 들어올리기」** 로 복사한 것을 붙여넣으면 투명 배경 이미지가 들어온다. 앱은 아무것도 하지 않고, 평범한 `photo` 레이어라 바운딩 박스·핸들·회전이 그대로 동작한다.

| 단계 | 처리 |
|---|---|
| 붙여넣기 | 알파 바운딩 박스로 **트림 1회.** 결과가 0×0이면 거부 + "빈 이미지예요" 토스트 |
| 사본 저장 | 아래 「알파 보존」 규칙 |
| 조작 | 일반 `photo` 레이어와 완전히 동일 |
| 히트 판정 | 바운딩 박스 기준. 알파 기반 정밀 히트테스트는 비용 대비 이득이 적다 |
| 익스포트 | 흰 배경 위에 합성되므로 최종 결과에 알파가 남지 않는다 |

**별도 안내·힌트는 두지 않는다.** 복사·붙여넣기가 제대로 동작하는 것으로 충분하다.

### 알파 보존 — 붙여넣을 때 투명한 것이 저장 후에도 투명해야 한다

**붙여넣을 때는 투명한데 저장 후 다시 열면 흰 사각형이 되는 것은 기능 오류다.** 알파가 죽는 지점이 셋이다.

```
클립보드 이미지 (투명)
   │
   ├─ ① 2000px 리사이즈    ← 가장 흔한 소실 지점
   │      opaque = true 이면 투명 영역이 배경색으로 칠해진다.
   │      픽셀이 이미 구워지므로 이후 PNG로 저장해도 되살릴 수 없다.
   │
   ├─ ② 인코딩            ← JPEG는 알파를 지원하지 않는다
   │
   └─ ③ 필터 적용          ← Core Image 출력 픽셀 포맷
```

| 단계 | 규칙 |
|---|---|
| **판정** | `CGImageAlphaInfo`로 알파 채널 유무 확인 → 있으면 **64×64 다운샘플에서 실제 투명 픽셀 스캔.** 채널 유무만으로 판정하면 스크린샷(알파 채널 있음·전부 불투명)까지 PNG가 되어 용량이 몇 배가 된다. 반대로 400만 픽셀 전수 스캔은 비싸다 |
| **리사이즈** | **`UIGraphicsImageRendererFormat.opaque = false` 강제** |
| **인코딩** | 투명 픽셀 있음 → `pngData()` / 없음 → `jpegData(0.9)` |
| **필터** | Core Image 출력 시 알파 보존 픽셀 포맷 |
| **로드** | `UIImage(data:)`는 PNG 알파를 유지. 표시용 캐시 생성 시 다시 `opaque = false` |
| **CloudKit** | CKAsset은 바이너리를 그대로 실어 나르므로 포맷과 무관 |

**용량 트레이드오프를 감수한다.** 2000px PNG는 3~8MB로 JPEG(0.5~1MB)보다 크지만, 투명 배경 이미지는 사용자가 의도적으로 만들어 온 것이므로 그 의도를 지키는 편이 낫다. 사진 8장 상한이 이미 용량 상한 역할을 한다.

**검증은 4시점 모두** — 붙여넣기 직후 / 저장 직후 / 앱 재실행 후 / 재편집 진입 후.
