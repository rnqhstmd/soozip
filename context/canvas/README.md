# canvas (캔버스)

사용자가 만드는 한 장. 규격·생명주기·저장 트랜잭션을 담당한다.

## 배경

캔버스는 v1부터 존재한 유일한 사용자 생성 객체였고, v4에서도 앱의 최소 단위다. 다만 **규격과 생명주기가 둘 다 바뀌었다.**

- **규격**: v2·v3에서 "되돌릴 수 없는 확정"이던 1080×1920 고정이, 인스타그램 게시물(4:5)과 스토리(9:16) 두 프리셋으로 완화됐다. 폭 1080은 여전히 고정이라 좌표계·렌더러·익스포트 변경 비용이 y축 한 방향에 그친다.
- **생명주기**: v3는 초안을 SwiftData의 `layoutJSON`에 계속 덮어썼다. v4는 **초안을 DB에서 분리해 로컬 파일로 내렸다.** 저장을 확정하는 순간에만 `Canvas` 레코드로 승격된다.

## 안 하면 어떻게 되는가

초안을 SwiftData에 두면 세 가지가 동시에 무너진다.

1. **CloudKit이 미완성 캔버스를 다른 기기로 동기화한다.** 아이패드에서 만들다 만 것이 아이폰 그리드에 뜨는 것은 사고다.
2. 모음집 그리드·통계·검색이 전부 `Canvas` 쿼리 기반인데, 초안이 섞이면 **모든 쿼리에 `isDraft == false` 필터**를 달아야 한다. 하나만 빠뜨려도 새어 나온다.
3. 초안 폐기가 레코드 삭제 + 관계 정리 + 사진 GC로 번진다. 파일이면 폴더 삭제 한 번이다.

## 사용자와 규모

20~30대 여성, 인스타그램 공유층.

한 캔버스의 레이어는 최대 43개(사진 8 + 펜 5 + 텍스트·도형·도장 30). 한 모음집당 캔버스는 수십 장 수준을 가정한다.

## 성공 기준

- 만들기 시작부터 에디터 도착까지 **탭 2회** (모음집 상세 [+] → 비율 선택)
- 저장 실패·크래시·강제 종료 어느 경우에도 **작업물이 증발하지 않는다**
- 재편집을 취소하면 원본이 **한 픽셀도 변하지 않는다**
- ❓ 평균 편집 시간 — 출시 후 실측 필요

## 핵심 결정

| 결정 | 근거 |
|---|---|
| 비율은 만들 때 고르고 **이후 변경 불가** | 바꾸면 모든 레이어의 상대 위치가 어긋나고, 재배치 UI를 따로 설계해야 한다. 다른 비율이 필요하면 새로 만든다 |
| **초안은 SwiftData가 아닌 `Drafts/` 파일** | 위 "안 하면 어떻게 되는가" 3가지 |
| **초안은 모음집당 1개** | 여러 개를 허용하면 초안 목록 UI가 필요해진다. P1에서 되돌릴 수 있는 결정 |
| 사진 사본은 **삽입 즉시** 기록 (디바운스 제외) | 크래시로 사진이 날아가면 레이아웃만 복구해도 의미가 없다 |
| 저장 순서에서 **초안 삭제를 맨 마지막에** | 먼저 지우면 저장 실패 시 작업물이 증발한다 |
| 재편집은 **원본을 건드리지 않고** 새 초안 세션 | 편집 중 앱이 죽어도 원본은 무사하다 |
| 빈 캔버스(레이어 0개)도 **저장 가능** | "강제하지 않는다"는 UX 원칙. 흰 배경만 있는 `renderedPNG`가 정상 생성되어야 한다 |
| 휴지통 없음 | 확인 다이얼로그 + 레이어 단위 실행취소로 충분. 휴지통은 "삭제했는데 iCloud 용량이 안 줄어요" 민원을 부른다 |

## 현재 상태

**초안 저장소와 캔버스 데이터 레이어 완료.** 초안 파일 I/O는 `Packages/SoozipDraft`(테스트 24), `Canvas` 모델과 CRUD·이동·표지 재계산은 Phase 1(PR #1)에서 끝났다. 둘 다 UI 없이 단위 테스트로 완성할 수 있는 순수 로직이라 에디터보다 먼저 만들었다.

**남은 핵심은 저장 트랜잭션 7단계(Phase 2)이며, 스파이크 S2가 전제다** — 초안이 CloudKit에 올라가지 않는다는 것이 설계 전체의 바닥이라 실기기 확인 없이 착수하지 않는다.
